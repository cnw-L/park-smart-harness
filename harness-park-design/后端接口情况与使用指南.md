> 面向 AI 服务(harness / 防腐层)的后端梳理。
> 数据源:`业务平台.md`(prod-api 接口文档)。结论用于指导防腐层怎么 compose+cache。
> 关联文档:[devicectrl-接口改造建议.md](devicectrl-接口改造建议.md)、[harness落地设计-讨论总结.md](harness落地设计-讨论总结.md)。

## 一、总判断

**后端是一个成熟的 `业务平台/project/*` 管理后台系统(CRUD + SCADA),不是给 agent 用的干净能力 API。**

- 动词是后台式的:`分页 / 获取 / 新增 / 修改 / 删除 / 发布下架 / 导入`。
- 它给的是**原料**(分页查询、点位写、字典、权限),不是"回答一个问题"。
- 所以 harness 不直接消费它,**中间隔一层防腐层**:把原料 compose 成干净能力、cache 掉慢变数据。
- **后端基本固定**,但可改、可加语义映射层/模块契约——改动遵循一条尺子:**任何客户端都受益的契约缺陷→改后端;只有 NL agent 需要的便利→留防腐层**。

## 三、红线路径的真实接口(已读正文)

### 1. 设备查询 / 读回 —— `getDevicePage`

```
POST /common/device/getDevicePage
入参(分页 + 过滤): { pageNum, pageSize, data: {
  systemId, pointTypeIdList, pointStatusList, deviceName,
  deviceIds[], floorId, buildingId, regionId, roomId, parkId, ... } }
返回: { data: { total, list: [ {
  deviceId, pointId, deviceNo, deviceName, regionName,
  status, value, pointTypeId, pointTypeNo, pointTypeName, ... } ] } }
```
**用途**:既是"查状态",也是控制后的"**读回**"。过滤维度(building/floor/room/pointType)是 grounding 收窄候选的依据。

### 2. 设备控制下发 —— `deviceCtrl`(红线)

```
POST /common/device/deviceCtrl
入参 DeviceControlEvent: { deviceId, pointTypeNo, paramValue, paramStatus,
                           deviceIds[], pointIds[], extraParam, ... }  // 15字段全可选
返回 RBoolean: { code, msg, data: true|false }   // 裸布尔
```
**关键缺陷**(详见 deviceCtrl 改造文档):
- **无幂等键** → 重复下发会重复执行(对非状态型动作有害)。
- **返回只有布尔** → 无 commandId、无状态查询 → 动作发出即匿名、不可追踪、不可对账。
- `paramValue` 是**绝对写**("把点位设成某值"),所以开/关/设定值这类是**状态型**(读回可兜底);**相对调节/触发脉冲/扣费**才是需要后端幂等的非状态型。

### 3. 点位参数字典 —— `sycPointParamType`(校验/grounding 的基石)

```
POST /syc/sycPointParamType/page
返回 list 每项: {
  paramTypeNo, paramTypeName, paramType, unit, decimalPlaces, inputType,
  isCtrl,                       // ★该参数可不可控(后端权威的读/控标志)
  maxValue, minValue,           // ★数值范围(执行前校验抓手)
  paramStatuses: [ { status, paramValue, workModel, isAble } ],  // ★取值枚举:status↔paramValue
  paramCommons: [ { paramValue, status } ],
  currentValue, pointTypeId, ... }
```
**这张表是杠杆最大的资产**:`isCtrl` 编码了读/控分叉;`paramStatuses` 让 grounding("开"→paramValue)和读回校验(status 值=开?)**两头都能做成规则**;`max/min` 给数值控制执行前校验抓手。

### 4. 权限(标题已确认,正文待读)

- `GET 根据角色获取设备类型获取权限参数`、`POST 根据设备类型获取权限参数`、`POST 角色授权设备` → **按"角色 × 设备类型"的控制权限**。
- `GET 获取当前用户信息(内部使用)` → 当前用户 + 角色。
- 结论:**权限走后端、不在中枢镜像**可行。具体入参/返回**待读正文**再定。

### 5. 其它设备相关(备用)

设备健康、设备组态公共接口(deviceCtrl/getDevicePage 在此域)、告警记录、场景联动(`PUT 执行动作`)、事件上报、巡检/维保计划。本期按需接入。

## 四、能力落点三分表(harness 视角)

| harness 需要的能力 | 后端现状 | 落点 |
|---|---|---|
| 设备状态查询 | `getDevicePage` | ① 直接有 |
| 控制后读回 | `getDevicePage` 读 status/value | ① 直接有 |
| 取值枚举 / 范围(校验) | `sycPointParamType`(paramStatuses/max/min) | ① 直接有 |
| 读/控分叉判定 | `isCtrl` 字段 | ① 后端已编码 |
| 权限(可不可控) | 角色×设备类型 + 当前用户 | ① 有(正文待读) |
| 控制下发 | `deviceCtrl`(裸布尔) | ① 有,但安全包络缺 |
| 解析"3号楼空调"→id | 无 resolve,只有分页过滤 | ② 防腐层合成 |
| 控制幂等/去重(跨客户端) | 无幂等键 | ① 须改后端 / ② 防腐层只能挡自己 |
| 崩溃后对账 | 无指令句柄 | ② 防腐层(状态重读) |
| 确认"设备到位" | 返回只给布尔 | ② 防腐层(读回校验) |
| 动作不可观测 / 状态有噪 | —— | ③ 降级给人 |

## 五、防腐层怎么用(compose + cache 模式)

### 1. grounding 管线("开3号楼空调" → 可执行指令)

```
NL → 槽位抽取(LLM,只产意图)→ 逐槽解析(规则,查权威字典,不编id):
  "3号楼" →(楼栋/区域树*)→ buildingId
  "空调"  →(pointType字典)→ pointTypeId
  getDevicePage(buildingId,pointTypeId) → 候选
    0 → 澄清 / 1 → 进 / N → 消歧(返回候选,交 harness 决定)
  sycPointParamType(pointTypeId,isCtrl=true) → 开关参数 → paramStatuses["开"]→paramValue
  (数值类:校验 ∈ [minValue,maxValue],越界即拒)
→ 输出: { deviceId, pointTypeNo, paramTypeNo, paramValue, 当前状态, 友好名 }
```
*楼栋/区域树接口 = `获取公共点位设备管理空间机构树`(业务平台.md:18505,A2/A3)/`获取空间加设备树`(19144,空间到楼层+设备)。grounding 第一跳用它,空间树狠缓存。

### 2. 下发→读回→对账 时序

```
正常(状态型):
  requestId 先落账 → deviceCtrl(grounded, requestId)
  等 t0 → 轮询 getDevicePage 读回, 对照字典目标值
    到位→成功 / 超时 T 未到位→降级给人("已下发,X秒未确认,请核对")
触发型(道闸/重启): 读回无意义 → 依赖后端 commandStatus(若改) 或 标注"已下发不可自动确认"
对账(崩溃恢复):
  日志有"将发 requestId=R"无结果 → 读回当前态:
    已是目标→推定完成(标注) / 非目标: 状态型→同R安全重发; 非状态型→查commandStatus/降级给人
时间参数(t0/Δt/T)按 pointType 配置,不硬编码。
```

### 3. 缓存分层(顺手解延迟)

| 数据 | 频率 | 策略 |
|---|---|---|
| 点位参数字典、楼栋/区域树、设备类型/别名 | 极少 | 启动加载 + 长TTL(小时) |
| 角色权限 | 少-中 | 按角色缓存,中TTL(分钟) |
| 设备台账(id/名/位置) | 中 | 中TTL 或按需+失效 |
| **设备实时状态 status/value** | **高** | **绝不缓存,实时读** |

**优雅简化**:把"需失效"的(实时态)直接划为"不缓存",剩下能缓存的全是"几乎不变"的 → 缓存层几乎不需要复杂失效逻辑。一个"4跳查询"塌成"1跳热读 + 3缓存命中"。

## 六、治理:五道护栏关卡归属(读/写缝,详见 `harness护栏安全子系统设计说明.md`)

1. **可不可控** → 后端 `isCtrl`(权威,只读)
2. **这个用户准不准控** → 后端权限接口(权威,只读)
3. **要不要人确认** → **harness 自己的 policy**(按可逆性/影响分级)

前两闸后端持笔(写权威外置),第三闸 harness 持笔——**这是 harness 唯一该自己拥有的判断**。后端若标了设备危险等级就用,没标则 harness 维护一张 pointType→风险图。**别把"要不要确认"塞回后端。**
