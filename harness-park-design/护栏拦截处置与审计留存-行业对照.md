## 一、问题与范围

围绕"护栏检测未通过后系统怎么处理"，本文归纳四个问题的查证与结论：

1. 被拦的原话进不进消息日志？进不进运行记录？
2. 用户追问"上一个请求为什么不能回答"时，模型如何应答？
3. 触发类型 + 原文在运行记录里怎么存？
4. 行业（AWS / Google / OpenAI）怎么做？

行业资料来源均为一线厂商官方文档（URL 见第十节），开源工具 README 不作为权威依据。

## 二、核心区分：消息记录 vs 运行记录

这是全文的承重区分。被拦内容"进哪种记录"决定了它会不会污染模型上下文。

|  | 消息记录（`messages`） | 运行记录 / 审计 |
|---|---|---|
| 给谁看 | 给**模型**看（拼上下文） | 给**人**看（运维、安全、追责） |
| 模型会读吗 | **会**，下一轮续聊时拼进上下文 | **不会**，模型从不读审计 |
| 项目落点 | Redis `:messages` LIST | `GuardAuditEvent`（护栏事件流）+ PG `agentloop_audit`（会话审计） |
| 被拦原话能进吗 | **绝不能进** | 可以进（明文或 hash 均可） |

**关键因果链**：进消息记录 = 进模型上下文。所以被拦的原话无论如何不能写进 `messages`——否则下一轮模型再次接触违规输入，护栏等于白拦。

## 三、拦截后的处置链路

### 3.1 三步分开（行业共性）

1. **检测器只吐判定信号**：未过 / 触犯哪类 / 程度多高。被拦内容本身不返回（Google 原文："The content that was blocked is not returned"）。
2. **应用层决定怎么办**：硬拒 / 请用户换说法 / 升级确认——是应用层选择，不是检测器定。
3. **给用户一句预先写好的客气话**：不是报错、不是空白、不是技术细节。

OpenAI 官方示例的占位回话：

> "We're sorry, but your input has been flagged as inappropriate."

### 3.2 三档未通过（项目 `GuardDecision.verdict`）

| verdict | 含义 | 下游行为 |
|---|---|---|
| `block` | 拒绝 | 返回拒绝话术 + 记录审计 + 终止当前链路 |
| `challenge` | 需确认 | 生成 challenge token + idempotency_key，进确认流程 |
| `clarify` | 需澄清 | 返回澄清问题，不改状态 |

注意：不存在 `review` verdict。紧急词命中时返回 `block`/`challenge`，**异步**发 review 事件到人工复核队列——复核是旁路动作，不阻塞、不是决策值。

### 3.3 兜底铁律

- **默认拒绝**：护栏自身异常 / 超时 / 字段缺失，一律 `block`（fail-safe）。
- **规则层 mandatory，语义层 optional + 显式降级**：规则层超时 -> `block`；语义层超时 -> `allow` 带 `degraded=1`，不静默放行。
- **护栏只读**：不修改会话状态、不直接执行工具、不写审计后端（只发事件）。block 发生在进 `run_loop` 之前——对话根本没开始，没有半截状态要回滚。

## 四、被拦原话的落点

按项目当前设计（"只读 + block 终止当前链路"），被拦的那句原话落点如下：

| 数据 | 进 messages？ | 进 agentloop_audit？ | 进 GuardAuditEvent？ | 模型看得到？ |
|---|---|---|---|---|
| 原话本身 | 不进 | 不进 | 进（`payload_hash`） | 否 |
| 占位符标注 | 进（建议，见第五节） | — | — | 是（知被拦，不知原话） |
| 拒绝话术 | 进（建议，见第五节） | — | — | 是（知原因） |

- **不进 `messages`**：没进 `run_loop`、没 commit boundary，`messages` 里没有这条 user message。模型续聊看不到它。
- **不进 `agentloop_audit`**：会话 boundary 审计，被拦没 boundary，自然没东西写。
- **只进 `GuardAuditEvent`**：护栏审计事件流，含 `payload_hash`（指纹），不留原文。事件发到 MQ，消费者落"只读审计存储"留 180 天。

## 五、上下文断层问题与占位符解法

### 5.1 问题

若严格按"被拦原话完全不进 `messages`"，则用户追问"上一个请求为什么不能回答"时，模型看到的 `messages` 是：

```
[之前正常对话…]
[user: 上一个请求为什么不能回答？]
```

被拦的那句不在，模型**不知道上一个请求是什么、也不知道被拦过**——上下文断层，只能含糊应付或瞎编原因。

### 5.2 解法：占位符入 messages，原话不入

核心思路：把那句被拦的话分两层处理——

- **原话**：不进 `messages`（切断上下文污染），只进审计。
- **占位记录**：进 `messages`，替换成不含原话的标注。

`messages` 形态：

```
[之前正常对话…]
[user: 此消息因违反安全策略已被拦截，原文未保留]      ← 占位符，不含原话
[assistant: 抱歉，你的上一个请求触发了安全策略，我无法处理。可以换个说法。]
[user: 上一个请求为什么不能回答？]
```

模型这下能答："你上一条触发了安全策略被拦了，可以换个说法再问。" 知道发生了拦截、知道大概原因，但看不到原话。

### 5.3 红线

"护栏只读、不修改会话状态"需稍微松动：**允许护栏往 `messages` 写一条记录，但只能写不含原话的占位符，不能写原话。** 红线是"原话不进模型上下文"，不是"什么都不进 messages"。

给用户看的拒绝话用通用说法（"触发了安全策略"，不甩内部判定）；`messages` 里的占位记录可带 `reason_code`（如 `prompt_injection`）供模型续聊参考。

> 取舍提示：占位符带不带 `reason_code` 是个权衡。带——模型能准确回答"为什么被拦"，但暴露护栏机制，攻击者可反复试探边界；不带——模型只能说"被拦了"，护栏机制不泄露。真实部署需拍板。

## 六、触发类型 + 原文怎么存（落地设计）

补 [`harness护栏安全子系统设计说明.md`](harness护栏安全子系统设计说明.md) 的空白：现有 `GuardAuditEvent` 只有 `payload_hash`，没有原文字段；对"原文怎么存"未作规定。

### 6.1 触发类型：现有字段直接填

| 字段 | 存什么 | 例子 |
|---|---|---|
| `layer` | 哪层护栏拦的 | `input` |
| `policy` | 命中的策略 ID | `bert_cn_prompt_attack_detection` |
| `verdict` | 决策 | `block` |
| `reason_code` | 具体原因码 | `cn_prompt_injection_high` |
| `policy_version` | 策略版本（可回滚归因） | `v3.2` |

不用加字段。

### 6.2 原文：新增字段 + 四件套保护

```python
@dataclass(frozen=True)
class GuardAuditEvent:
    # ... 现有字段不变 ...
    payload_hash: str                       # 指纹（必留，去重/验证/不泄露）
    payload_raw_enc: str | None = None      # 脱敏 + 加密后的原文（可选留）
    payload_raw_kid: str | None = None      # 密钥版本（便于轮换）
```

存的时候过四件套：

1. **脱敏**：先打码 PII（手机号 / 身份证 / 地址），存的是"脱敏后的原文"。
2. **加密**：AES-GCM at rest，密钥走 KMS / 独立密钥管理，不与审计库同库。
3. **访问控制**：只有安全 / 审计角色能解密读；应用层、模型读不到。
4. **TTL**：180 天（与现有"关键拦截事件保留 180 天"一致），过期删除。

### 6.3 存哪：独立护栏审计存储

| 候选 | 存原文吗 | 为什么 |
|---|---|---|
| `messages`（消息记录） | 绝不 | 进了就进模型上下文 |
| PG `agentloop_audit`（会话审计） | 不进 | 会话 boundary 审计，被拦没 boundary；受众是会话恢复，敏感原文混进去污染恢复路径、访问控制级别不对 |
| **独立 `guard_audit_event`** | 进这里 | 专给安全 / 合规用，访问控制最严 |

护栏自己不落库（"只发事件，不写审计后端"）——把加密后的事件发到 MQ，**消费者**落进独立的 `guard_audit_event` 表（PG 独立表即可；将来要检索攻击模式可上 ES）。密钥只在消费者侧 / KMS，护栏服务不碰密钥。

### 6.4 开关

`retain_payload_raw` 配置项（按租户 / 场景）：

- **开**（默认，要排查）：留脱敏 + 加密原文，能回溯 badcase。
- **关**（合规最严）：只留 `payload_hash`，泄露面最小但排查拿不到原文。

## 七、行业做法（权威资料归纳）

### 7.1 AWS Bedrock

**Model Invocation Logging**（被拦内容存运行记录的官方对应）：

- **存什么**：完整 input + output + metadata，一条 JSON 记录（最大 100KB）。被拦原话在 input 里，**明文**。
  > "collect the full request data, response data, and metadata"
  > "each record will contain the invocation metadata, and input and output JSON bodies of up to 100 KB"
- **存哪**：Amazon S3（Gzipped JSON 批量）或 CloudWatch Logs（JSON 事件），独立于模型和会话。
  > "Supported destinations include Amazon CloudWatch Logs and Amazon Simple Storage Service (Amazon S3)"
- **明文**：被拦内容以 plain text 存（可关）。
  > "All blocked content ... will appear as plain text in Amazon Bedrock Model Invocation Logs"
  > "You can disable Amazon Bedrock Invocation Logs if you do not want your blocked content to appear as plain text"
- **加密**：AWS 默认 at-rest 加密，可配 SSE-KMS；用 Amazon Macie 事后发现敏感数据。
  > "Use AWS encryption solutions"
- **保留期**：无自动 TTL，存到配置被删为止。
  > "logs are stored until the logging configuration is deleted"
- **默认关**：disabled by default，要主动开。
- **访问控制**：IAM。
- **查询**：S3 Select / Athena / CloudWatch Logs Insights。

**ApplyGuardrail API**：

- `action: NONE | GUARDRAIL_INTERVENED` + `actionReason` + `assessments`（命中哪类）+ `outputs`（护栏处理后的输出，可自定义）。
- `outputScope=FULL`："return the entire output, including any detected and non-detected entries for enhanced debugging"——返回被检测到的内容条目用于调试。

### 7.2 Google Gemini

- 拦下后返回 `promptFeedback.blockReason`（输入被拦）或 `finishReason=SAFETY` + `safetyRatings`（分类 + 概率）。
  > "If response content was blocked and the finishReason was SAFETY, you can inspect safetyRatings for more details."
- **被拦内容不返回**：
  > "The content that was blocked is not returned."
- 概率分级：`HIGH / MEDIUM / LOW / NEGLIGIBLE`，按概率（非严重度）拦截。
- 界面交互："Content blocked" 警告，悬停看触犯哪类。

### 7.3 OpenAI Moderation

- 接口只回判定信号：`flagged` + 命中分类 + `category_scores`。**不回 / 不存输入原文**（输入是应用层传的，存不存自理）。
- 被拦后回占位话，不采纳 LLM 回复：
  > "If your moderation gets triggered you send back a placeholder response."
  > "return the LLM response only if the moderation returns False"

### 7.4 行业共性

1. **检测 / 决策 / 回话分开**：检测器只出判定信号，应用层决定处置，给用户客气话。
2. **被拦内容不送给模型**：三家一致（Google 不返回、OpenAI 不调 LLM、AWS `GUARDRAIL_INTERVENED`）。
3. **护栏服务无状态，不管会话历史**：被拦输入进不进会话日志是应用层决定。项目把护栏设计成"只读、不修改会话状态"与此一致。
4. **审计独立于会话**：AWS 进 S3/CloudWatch（独立），不混进会话恢复路径。

## 八、项目 vs 行业对照

| 维度 | AWS Bedrock | Google Gemini | OpenAI Moderation | 本项目（第六节方案） |
|---|---|---|---|---|
| 拦下后给用户 | 可配置返回消息 | "Content blocked" 警告 | placeholder response | 占位拒绝话 + 占位符入 messages |
| 被拦原话进模型上下文 | 否 | 否 | 否 | 否 |
| 被拦原话存运行记录 | 进（明文） | 不返回 | 不存 | 进（脱敏 + 加密） |
| 存哪 | S3 / CloudWatch | — | — | 独立 `guard_audit_event` |
| 加密 at rest | 是（SSE-KMS） | — | — | 是（AES-GCM） |
| 脱敏 | 不自动（Macie 事后） | — | — | **事前脱敏**（更严） |
| 保留期 | 无 TTL，存到删 | — | — | **180 天 TTL**（更严） |
| 默认开关 | 默认关 | — | — | `retain_payload_raw` 开关 |
| 访问控制 | IAM | — | — | 安全 / 审计角色 |

**结论**：方向与三家一致（独立存储 + at-rest 加密 + 访问控制 + 开关 + 被拦内容不进模型上下文）。两处比 AWS 更严：

1. **事前脱敏 vs 事后发现**：AWS 不打码存全量明文，靠 Macie 事后扫；本项目存前先打码。园区输入含手机号 / 工号 / 地址，事前脱敏泄露面更小。
2. **180 天 TTL vs 无限留存**：AWS 存到删为止；本项目设自动过期。合规"数据最小化 + 定期删除"更稳。

## 九、结论与落地建议

1. **被拦原话不进 `messages`**：切断"进消息记录 = 进模型上下文"的因果链。这是红线，三家行业做法一致。
2. **补占位符入 messages**：解决"用户追问为什么不能回答"的上下文断层。占位符不含原话，可带 `reason_code`（权衡见 5.3）。这是现有设计需松动的一处。
3. **补原文留存字段**：`GuardAuditEvent` 加 `payload_raw_enc` + `payload_raw_kid`，脱敏 + 加密 + TTL 180 天 + 独立 `guard_audit_event` 表 + `retain_payload_raw` 开关。取 AWS 裸明文与纯 hash 之间——既能排查 badcase，又控泄露面。
4. **触发类型用现有字段**：`layer` / `policy` / `verdict` / `reason_code` / `policy_version`，不用加。
5. **护栏只发事件不落库**：保持现有架构（发 MQ，消费者落库），密钥只在消费者侧 / KMS。

> 现状标注：护栏子系统目前为设计稿，`src/` 与 `scripts/demo_server.py` 均未接入护栏调用。以上为设计意图与落地建议，非运行行为。
