## S2 — gate 接缝(allow / ask / deny)

**依据**:§二(闸 seam 给 allow/ask/deny → 循环 执行/挂起/跳过)、§四(统一 ask/allow/deny;deny 抄 Hermes "block→合成结果→继续")、§五、§六:111-119、§六补不变式(executor 拒绝内联控制是类型保证,保留)。

**Files**:新 `gate.py`;`loop.py`(改 工具批处理段);`dispatch.py`(配合);Test `tests/test_agent_loop_gate.py`。
- `gate.py`:`Verdict = Literal["allow","ask","deny"]`;`Gate(Protocol): classify(call: ToolCallReq, tool: LoopTool, ctx: ToolContext) -> Verdict`。`DefaultGate(denied: Callable[[ToolCallReq, LoopTool], bool] | None = None)`:`denied(...)→True` ⇒ `deny`(无权限,桩:默认无人被 deny);`tool.is_control` ⇒ `ask`;否则 `allow`。(权限/工单内部实现在接缝外,此处桩。)
- `loop.py` 工具批处理段**重构为逐调用过闸**(§六:111):
  - `v = gate.classify(call, tool, ctx)`
  - `deny` → append **合成 blocked tool 结果**(`[blocked] 无权限/已拦截`,role=tool、配 tool_call_id;disposition 视作 executed-业务否,**不**计入 max_tool_failures;抄 Hermes block→合成→继续),模型看得见。
  - `ask` → `control.freeze(call)` → 收进 pending_batch + 填 `[pending_confirmation]` 占位(同现状)。
  - `allow` → `executor` 执行该(只读)调用,拿 outcome。
- executor 的 `is_control` 拒绝内联**保留**为类型后盾(§六补:可回滚迭代只能装幂等操作)。若控制工具被误判 allow 到达 executor,仍拒绝。
- **不变式**:不可逆动作只能走 ask,绝不内联。
- **Test**:只读工具→allow→执行;控制工具→ask→挂起(未执行);被 deny 的工具→合成 blocked 结果、handler 未跑、不计失败;deny 结果模型可见(在 conversation 里)。

## S3 — verify 接缝(business_ok / is_error 回灌)

**依据**:§二(verify seam 给 ok/fail → 循环 终止/重规划)、§五补(verify 不是循环闸,在子系统,每能力校验结果;`validation_policy` 结果边界跑,规则优先;**校验失败必须作为 `is_error:true` 的 tool 结果让模型看见**,自然触发重规划;控制的 verify=读回对账,无引擎级末端 verify 闸)。

**Files**:新 `verify.py`;`messages.py`(加 `is_error`);`tools.py`/`dispatch.py`(传递);`loop.py`(allow 执行后跑 verify);Test `tests/test_agent_loop_verify.py`。
- `verify.py`:`@dataclass VerifyVerdict{ business_ok: bool, note: str = "" }`;`Verifier(Protocol): async verify(call, tool, result: ToolResult, ctx) -> VerifyVerdict`。`NullVerifier`:`business_ok = result.ok`(默认放行,接缝就位)。
- `messages.py`:`Message` 加 `is_error: bool = False`(tool 消息用;映射 provider 的 tool 结果 error 标志)。
- `loop.py`:**仅对 allow 执行的结果**跑 `verifier.verify(...)`;`business_ok=False` → 该 tool 结果消息 `is_error=True` + 内容标注(如前缀 `[verify-failed] {note}`),让模型看见 → 模型自然重规划(循环不强制重规划,只保证回灌;§五补"自然触发重规划")。`business_ok=True` → 正常结果。
- verify **不**改 deny/ask 路径(deny 是合成、ask 走确认后读回对账=控制能力子系统的事)。
- **Test**:allow 工具 business_ok=True→正常;Verifier 判 business_ok=False→结果 `is_error=True`、内容含标注、模型下一轮看得见;verify 失败**不**直接计 max_tool_failures(它是业务否/触发重规划,不是基础设施失败)。

## S5 — steer + 挂起模态门(人在回路第三触发器)

**依据**:§五补(interrupt=丢整轮;steer=停+append+重入,不 mid-loop 注入)、§六补(挂起期间来新消息=模态门:按**形状**分,结构化确认→解析,自由文本新请求→**不在 pending 上起新轮**,要么先批/先拒、要么显式 cancel=reject-all→干净边界→再处理;**绝不让新意图穿过 pending**;初期单 thread 单 pending)。

**Files**:`loop.py`(resume 入口模态门)、`runcontrol.py`(按需);Test `tests/test_agent_loop_steer.py`。
- `run_loop` 恢复入口:最后边界 `awaiting_confirmation` 时按形状分流——
  - 给了 `resolution`(结构化 `{tool_call_id: approve/reject}`)→ 解析整批(现状)。
  - 给了 `cancel=True` → reject-all 整批 → 干净边界 → 落入正常循环(处理新意图)。
  - 既无 resolution 又无 cancel,但带了新自由文本 user 消息 → **拒绝起新轮**,返回 `awaiting_confirmation`(要求先决策/cancel)。**新意图不穿过 pending。**
- 加 `cancel: bool = False` 参数。单 thread 单 pending(已是)。
- steer 语义:新消息 = RunControl.request_interrupt()(安全停)+ append → 下次调用带"旧进展+新消息"重规划(loop 已有 interrupt;此任务确立模态门契约 + cancel)。
- **Test**:pending 态下传新自由文本(无 resolution/cancel)→ 仍 awaiting_confirmation、未起新轮;传 cancel=True → 整批 reject、继续到 completed;传 resolution → 正常解析。
