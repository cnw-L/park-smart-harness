## 〇、定位(✅)

- 园区 AI 服务 = **服务任务 × 不可逆**,对标 Claude Code 极,非 Hermes。
- **治理工具 = 确认(非围栏)**:真实设备控制不可逆、不可沙箱、不可回滚。
- harness = AI 服务的**管理/边界/编排层**,消费后端能力,**不持业务权威**。
- 北极星五层:`C端入口 → AI对话中枢 → 子Agent能力层(MCP) → 数字底座`。中枢+能力层是主战场。
- **现阶段是讨论收敛期,不急落地**;急着写的代码注定返工。

## 一、编排核(内圈)

### 1.1 一个递归 ReAct 循环(✅)
每轮 = 思考 + 执行。**显 = plan/todo**(给用户看进度 + 结构化便于代码管理 + 拼回上下文当状态),**隐 = thought**(驱动循环、不给用户看、压缩时优先丢)。

### 1.2 plan 偏 Plan-and-Execute(✅)
plan **稳定、按需修订**,不是纯 ReAct 每轮重写——为的是**可验收性**。

### 1.3 plan 写模型(✅ **地基已定,真实 harness 背书**)
> 我们一度纠结"in-place 改 vs 事件溯源+投影"——这是个伪二分。**两个真实 harness 给同一个更简单的答案:**
- **Claude Code**:todo = `TodoWrite` **全量快照**,append 进 append-only 会话 JSONL(`~/.claude/projects`);最新快照=当前态;replay/fork/rewind 白送;compaction 丢旧快照。
- **Hermes**:todos 是 agent 拦截工具,状态存 session DB;plan 表示为 skill prompt,**无显式 AST**。

**结论**:
> **plan = 全量快照 append 进 append-only 消息日志(文件=唯一真相);"当前 plan"=取最新快照;任何可查询 DB/索引 = 从日志派生、可重建、不持权威。** 不建 plan AST,不做粒度事件溯源。

Hermes 的 **state.db 损坏事故**反证了这条:多进程(CLI/网关/子agent)并发写 DB → 损坏 → 跨会话记忆全丢;修法正是"**JSON session 文件做真相源,DB 当派生索引**"。
对你域注意:Claude Code todo 很轻;你的 plan 带富 spec/grounding 结果会更重 → **plan 保持精瘦**(大产物走归一化结果/外部句柄,别嵌进每张快照)。

### 1.4 重规划(✅)
- **触发 = 当前 plan 不再达成原目的**:① 工具失败;② 工具成功但**结果不合理**;③ **用户 steer/改目标**(人在回路=主循环一等公民,第三触发器)。
- **探测器 = 执行后校验**(既是质量闸,也是"plan 还成不成立"传感器);**要有规则抓手**(规则 > 视觉 > LLM-judge)。
- **重规划 = 增量**(append、基于已获取结果继续),需**放弃分支/上报用户的终止口**(防沉没成本锁死)。

### 1.5 "原目的"锚点的风险(⬜)
用户中途改目标 → 原目的要可更新;首轮 grounding 立错目标 → 后续校验全绿却在做错事(单步校验抓不住"目标本身立错")。

## 二、上下文与状态(中圈)

> **落地设计见 `上下文管理子系统-设计.md`**(已收敛定稿):五层(固定/记忆/历史/任务/知识)+ 存储生命周期 + 统一组装管线全部收敛;重注砍掉(上下文有界+闸兜底)。本节是方向纲要。

### 2.1 五层组装(✅) + **缓存决定层序(✅ Hermes 实证)**
固定 / 记忆 / 知识 / **任务(plan)** / 历史。
**关键约束(之前漏掉)**:Hermes 系统提示 `stable → context → volatile`,**会变的东西全压在 volatile 最后**;"中途写盘更新磁盘,但 rebuild 前不动缓存系统提示";临时内容贴当轮 user message。
→ **层序不能只按逻辑分组,要按变更频率排,服务缓存**:固定/知识在前(进缓存前缀),**任务层(plan,每轮变)、历史层必须靠后或进当轮 user message**。**plan 摆错位置=每轮炸缓存=延迟翻倍。**
> **落地修正(`上下文管理子系统-设计.md` §二)**:分层的目的是**功能标签划分**(让模型分清指令/数据/历史/任务),**缓存是副产品、不是设计驱动**;位置只三段(系统头/消息流/尾部),plan 折尾。

### 2.2 plan 放任务层(✅)
结构化(status: done/doing/todo + spec),**保真不压缩**;历史层可压;plan 文本不在历史层重复存。

### 2.3 长上下文真相丢失(✅ Hermes 教训)
Hermes 实测 700K token 后模型把"工具描述里的警告"当成真实环境(环境幻觉)。→ **关键不变量必须每轮重新注入**(volatile/user message),不能只在缓存前缀里说一次。
> **落地修正(`上下文管理子系统-设计.md` §八):重注砍掉。** 这病是"超长上下文埋没头部";我们历史压缩使上下文**始终有界**、且控制红线有**确认闸兜底**,没这病。留 contingency:qwen 真机测若漏红线/漂目标再加一行。折叠序简化为 `用户原文 → plan`。

### 2.4 重放必须压缩(✅ Hermes 教训,存在性问题)
Hermes field report:长对话静默分裂成多 session,每 session **全量重放历史**,12 小时烧 190 万 token、**89% 是重放浪费**。→ **"消息即状态+朴素全量重放"在规模上是灾难**:重放须**压缩摘要**,session 边界 + token 数**可见**,超阈值告警。

## 三、工具组织层(= 防腐层 / 能力层 / MCP 封装层)

> 主身份是**工具/agent 的组织·路由·治理·归一化**;grounding/读回/缓存只是"某个工具内部"的事。核心 M3:**选择可靠性靠组织结构(分组/分层/隔离)根治,不靠把描述写好。**(Hermes 实证:registry 自动发现 + toolsets 分组 + check_fn 门控。)

### 3.1 工具注册表(✅)
元数据:`group / desc / input / output / output_hint / output_budget / over_budget / risk / permission / norm`。
**output + output_hint** = 输出稳定来源;**norm** 把后端杂乱返回压成声明 output,模型永不见原始 JSON。

### 3.2 路由管线(✅)
**分组是地基,语义检索叠在其上,串联不是二选一**:`模块判定(粗筛)→ 模块内语义检索(精筛)→ 组装/执行`。先定模块,检索池才干净。
**每跳机制(语义 or 模型思考)按 延迟×精度 定**:语义=快/浅,适合"模型开口前预筛、缩短提示";模型思考=已在循环里时几乎免费(那轮 thought),适合模糊/混合意图。默认:首跳能语义就语义,末跳交循环 thought。

### 3.3 分级(✅)
- **规则:节点候选 ≤ ~7,超了才分;深度参差、最小化**(每级=一次可能错的路由+一跳延迟;agent 隔离边界尤其贵)。
- **现在统一 2 跳**:`L0 选域(设备/工单/知识)→ L1 域内选工具`。
- **设备 = agent-as-tool**(隔离+自有循环+归一化回吐);工单/知识 = 扁平。
- 设备 L2 子组 = 预留口(能力 >9 或要读/控分治时加,切法沿读/控)。

### 3.4 输出预算 / 限 token(✅,= 延迟"输出半")
top-k/分页封顶、字段投影、**聚合摘要(防腐层算,不丢给模型数)**、硬截断+**"请收窄"结构化信号**、大产物外部化。**读路径可截断;控路径绝不静默截断**(完整计数 + 收窄或显式批量确认)。

### 3.5 grounding / 下发读回对账 / 缓存(✅,细节见后端使用指南)
单个工具内部实现:grounding 管线、下发→读回→对账时序、缓存分层。

## 四、治理(外圈)

### 4.1 五道护栏关卡归属（三个关键决策，详见 `harness护栏安全子系统设计说明.md`）
1. 可不可控 → 后端 `isCtrl`(权威,只读)
2. 用户准不准控 → 后端权限(权威,只读)
3. **要不要确认 → harness policy**(按可逆性/影响分级)——harness 唯一该自己持笔的判断。

### 4.2 读/控分叉是贯穿全局的尺子(✅)
**安全、延迟、输出限额、对账策略**都沿这条分。

### 4.3 确认疲劳(✅ 原则,⬜ 机制)
只对不可逆/高影响弹确认;批量聚合;监测"秒确认"。**问太多=没问**。风险分级一个杠杆同时解确认疲劳和延迟。

### 4.4 预算 / 死循环(✅ 模板已得,Hermes 实证)
Hermes 主循环:`max_iterations` + `iteration_budget.remaining` + **一次 grace call**(耗尽给一次收尾,即"如实降级收尾")+ 硬超时(cron 3 分钟)+ `if interrupt_requested: break`。→ 直接作为我们预算闸的模板。

### 4.5 控制路径治理(✅ 定稿;细节是工具/控制能力子系统的内容,**不在内圈循环**)
> 内圈循环只懂"闸说 ask → 挂起、带不透明句柄;恢复交回执行"(见 `内圈循环-收敛定稿.md` §五)。以下全是子系统的活,从循环里挪出。

**闸 = ask/allow/deny,逐调用、执行前**:
- **deny** = 无权限 → 主要靠"不进候选集"(工具可见性层过滤)+ 后端数据过滤;敏感工具可"可见但运行时拒"留越权审计痕。借 Hermes "block→合成结果→继续"。
- **allow** = 准入 + 只读 → 自动执行。
- **ask** = 准入 + 不可逆 → 冻结 + 挂起确认。

**权限作用在两层(不是一道闸)**:① 工具可见性(无权限工具不进候选集,工具管理子系统);② 数据级(透传身份到后端,**后端按身份过滤数据**)。权限集 = 登录身份(员工企微SSO/市民微信openid)→ 后端查权限(缓存)∩ 工具注册的 permission 元数据。harness 不镜像,问后端。

**ask 的冻结-挂起-恢复(P1,无 Hermes 模板,我们造)**:
- **复用现有 `control_ticket.prepare`**:工单本就是"冻结动作 + id + requires_confirmation"——**工单 id 直接当幂等键**,不另造平行机制。
- 冻结工单存挂起记录(持久化层),**不进易变消息流**。
- 恢复批准 → **直接执行冻结工单,绝不重问模型**(双重必要:幂等 + 残缺消息序列不能喂 provider);查 dedup(工单 id)已执行则取存储结果、不重发。
- 执行 = `deviceCtrl`(带幂等键)→ **读回 `getDevicePage` 对账** → outcome(applied/unverified/reconcile-failed)。
- **幂等键真实承重面**:纯状态型("设成X")读回即兜底、幂等是 belt-and-suspenders;**只有非状态型(相对/扣费/触发)才真要它**——取决于本期是否含非状态型控制(待确认事实)。
- **TOCTOU 对不可逆默认开**:恢复执行前重读设备态,与 propose 时不一致 → 拒/重确认。
- **崩溃窗口完整 in_flight 协议留后续**(窗口毫秒级、概率低,不可观测动作最终降级给人);v1 = 发完即标 executed + 读回兜底对账。

**批量确认(接 4.3 防确认疲劳)**:一轮多个 ask 攒成一批一次挂起 → 前端一次列出可逐条批准,而非逐个弹。

**事务正确性把以上钉成硬保证(独立设计+审查后,详见 `内圈循环-收敛定稿.md` §六·补)**:
- **`is_control` 是注册表上的类型,不是运行时判定**:executor **拒绝内联执行任何 control**(只能返回 `awaiting_confirmation`);子 agent **结构上不能执行控制**,只回吐提案给主。理由——可回滚的迭代里只能装幂等操作,所以"控制绝不内联"是事务回滚安全逼出来的,不是治理外加。
- **幂等键在挂起时铸造冻结、绑会话态**(Temporal 同款),重复 resume/重连/崩溃重发用同一键 → 后端去重 exactly-once。
- **存储分层(多用户服务端,不用 SQLite)**:热会话+pending → Redis(thread_id,TTL);**审计 + 幂等键账本(unique 约束)→ Postgres(append-only)**;崩溃后用 Postgres 边界日志重建 Redis。
- **★ 硬依赖**:`deviceCtrl` 加 `commandId`+幂等前,**不可逆控制不能上线**——持久执行救不了非幂等后端,崩溃重发会双发。harness 侧只能"下发前读回查命令是否已存在"收窄 TOCTOU(非保证)。这把 `devicectrl-接口改造建议.md` 从"建议"提成**上线前硬阻塞**。

### 4.6 子会话治理(✅ Hermes 实证)
`delegate_task`,**leaf 角色(默认)不能 delegate / 不能碰 memory / clarify / send_message**;隔离上下文+终端,父阻塞,父中断级联取消;**深度上限 2、并发上限 3**。
→ 坐实"子权限⊆父",并多一条治理洞见:**子 agent 不持写权威(碰不了 memory)**——写权威留在 orchestrator,不下放。这是 M5 的缝在子会话上的落地。

## 五、延迟(横切尺,✅ 框架)

- **每加一样东西先问:读路径还是控路径。**
- **输入半**:路由小候选→短提示;模型分层;并行(无依赖 DAG 节点);缓存;快慢双路(简单读短路、不进重循环)。
- **输出半**:输出预算(3.4)。
- 两半 → 每轮 token 双向有界 → 延迟有界。
- **控路径确认延迟是治理、不可优化掉**(不可逆域地板价);只能改感知(prepare 立刻推前端)。
- **流式**改善首字时间,但与**事实护栏**冲突:安全关键输出不能边流边撤。
- 安慰:延迟主因在赋能层 → 随模型变强、单轮干更多活而好转(别把赋能脚手架堆太重,它既会被作废、现在又是延迟)。

## 六、与现有代码 / 后端的关系(✅)

- 防腐层 **== MCP 封装层**(别建两遍);能力 = 声明式 **manifest**。
- 后端是富 CRUD/SCADA,原料齐全;**唯一真缺陷=deviceCtrl 安全包络**,其余 compose+cache。
- 现有 `capability_platform`(单轮流水线 + 两段校验 + policy 读控分叉 + 条件DAG + 工具注册表/分组 + grounding/防腐)是**已实现大半的可复用资产**;落地=在其上消重运行时 + 补缺口(见 `实施计划.md`)。
