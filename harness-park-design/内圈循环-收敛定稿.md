# 内圈循环 · 收敛定稿

> 经多轮讨论 + Hermes 源码对照 + **两次独立 agent 评估** + 边界自审后的内圈定稿。
> 评估结论:路子站得住、可建;Hermes 引用六条核对准确。
> **本版要点:把确认/幂等等子系统内容从循环里挪出去了**——循环只剩它真正该管的,逻辑闭环。
> 控制路径(闸/工单/幂等/读回/TOCTOU)的设计见 `harness落地设计-讨论总结.md` 的治理章,不在本文。

## 一、核心模型

**内圈不是"跑到底的循环",是"在持久态上推进到某个退出原因"的步进函数。**

```
每次调用 = 载入持久会话态 → 推进若干步 → 撞上退出原因 → 持久化 → 返回原因
退出原因 ∈ {
  completed             非空 assistant 文本、无 tool_call
  awaiting_confirmation 闸说 ask —— 可恢复(携带一个不透明 pending 句柄)
  budget_exhausted      预算耗尽(grace 收尾后)
  failed                连续失败/模型错误到上限
  interrupted           用户中断
}
恢复 = 用更新后的持久态再调一次(服务端每条 WS 消息本就调一次,恢复≈又一次调用)
```

## 二、责任边界(瘦引擎 + 接缝)—— 这是本文的纪律

| 循环 own | delegate 给接缝(循环只 act on verdict) |
|---|---|
| while 推进 + 退出原因判定 | 上下文组装 → ContextAssembler |
| 每轮防御性 repair | 模型 I/O → ModelCaller |
| 预算 / grace / 中断 / 深度 | 工具执行(串/并) → ToolExecutor |
| 终止判定(非空文本;空→重试) | 持久化 → ConversationStore |
| 循环级错误处理 + stall 守卫 | **准入 allow/ask/deny + 冻结 pending 句柄 → 闸 seam** |
| 携带不透明 pending 句柄、挂起、恢复交回 | **结果对不对 ok/fail → verify seam** |
| **消息合法性**(下次调模型前填满挂起 tool_call 的结果) | |

> **循环对治理只懂两句话**:闸 seam 给 `allow/ask/deny` → 循环 `执行/挂起/跳过`;verify 给 `ok/fail` → 循环 `终止/重规划`(verify **不是独立循环步**,裁决经工具结果的 `business_ok`/`is_error` 回灌,见 §五补)。**幂等、工单、读回、权限、TOCTOU 全在接缝外,循环完全不知情。**

## 三、三个硬骨头:两个抄 Hermes,一个我们造(均核过源码)

| 硬骨头 | 解 | 来源 |
|---|---|---|
| 恢复时状态重建 | **每轮防御性 repair**(丢孤儿 tool 消息、合并连续 user、修持久化游标),不求精确重建 | 抄 `agent_runtime_helpers.py:347 repair_message_sequence`(docstring 明列 session resume) |
| 挂起期间预算被墙钟烧 | **预算=迭代/token 计数,弃墙钟**(挂起无模型调用=自然不消耗) | 抄 `iteration_budget.py:32` 纯计数器、零时间 |
| 恢复处幂等 | **不在循环里**——见治理章(控制能力子系统:复用 control_ticket 的 id 当幂等键) | 我们独有,Hermes 无 |

## 四、对照 Hermes 的有意背离(核过源码,非闭门造车)

| 决策 | 我们 | Hermes | 为什么背离 |
|---|---|---|---|
| 确认 | 挂起-持久-恢复(`awaiting_confirmation` 退出原因) | handler 内阻塞回调等人 | 服务端+异步+不可逆;它终端+可逆 |
| 闸 | 统一 ask/allow/deny(在子系统) | 分散 block + handler 内零散 approval | 读控分叉是核心,须统一可审计;deny 仍抄它"block→合成结果→继续" |
| 子预算 | 共享池(硬总闸) | 独立预算可超父 | 不可逆,爆炸半径必须有总上限 |
| 并发工具 | 单→直/多→并发保序/交互→串行 | 同 | 抄(agent-loop.md:132) |

## 五、内圈在"确认"上的真实职责(很薄——自审修正)

> 上一版我把冻结记录/幂等键/dedup/读回/TOCTOU 都写进了循环——**错了,那些是控制能力子系统的内容**。循环在确认上只有四样:

1. 多一个退出原因 `awaiting_confirmation`,**携带闸给的不透明 pending 句柄**;
2. 闸 seam 说 `ask` → 循环持久化会话 + 句柄 → 返回(**句柄由闸造,循环不造**);
3. 恢复(批准/拒绝事件)→ 把句柄**交回工具子系统执行**,拿回结果;
4. **消息合法性规则**:挂起时那个 control 的 tool_call 没有结果(残缺序列),**下次调模型前必须先把结果填上**——所以恢复路径**先执行句柄填结果、再继续**,**绝不在残缺态下重问模型**。

> 句柄不透明 = 循环不知道里面是工单/幂等键/冻结 args;它只负责"挂起时带着、恢复时交回去执行、把结果填进对的槽"。

## 五·补 · 人在回路(中断/steer)与 verify(独立评估 + Claude API 契约后定稿)

**verify —— 不是循环的闸,在子系统(每能力校验自己的结果)**
- 能力 `validation_policy` 在结果边界跑(规则优先),结果带 `business_ok`;**校验失败必须作为 `is_error:true` 的 tool 结果让模型看见**(不是静默 flag),自然触发重规划。
- 控制的 verify = 读回对账。**无引擎级末端 verify 闸**——Claude 也没有(它 Stop hook 是答完后才拦、对不可逆太晚);我们在结果边界、每步校验,更对。

**interrupt(停)—— 丢弃进行中的整轮,绝不合成(纠正:之前"合成 [interrupted] 填充"是错的)**
- Claude/Claude API 契约:未完成 tool_use 块**根本不进历史**,从**最近完整边界**恢复,**绝不合成**。
- 我们:interrupt = **放弃这一轮**(assistant + 部分 tool 结果整轮不落盘)→ 从上条 user 恢复 → 重入重生成。
- 实现:**整轮原子持久化**(assistant + 它所有 tool 结果轮末一起落盘),mid-turn 中断=这轮没落=天然干净。
- **不变式:任何不可逆动作绝不在工具批里内联执行,一律走 ask 挂起** → 中断时跑过的只有幂等读,无半截控制要回滚。
- interrupt(放弃整轮)≠ suspend(暂停:持久化 assistant+pending-action、恢复填),机制不同不冲突。

**steer(改方向)—— 停 + append + 重入,不 mid-loop 注入**(Claude 同款:排队→做完当前→当下一轮 user 输入→重决策)。我们 per-message+持久态:新消息 set 中断(安全停)+ append → 下次调用带"旧进展+新消息"重规划。

**Claude 的 Stop-hook 我们不需要**:它用它 block 强制续跑;我们完成度由 plan+每步校验保证。它"下发前拦动作"的诉求 = 我们的 ask/allow/deny 闸(且在不可逆下发前拦,位置更对)。

## 六、闭环逻辑(收敛定稿)

```
run_loop(conversation, budget, seams, depth):
  # —— 恢复快路:有待解决的 pending(批准/拒绝到达)——
  if conversation.pending_resolved():
      result = tools.execute_pending(handle, resolution)   # 幂等/工单/读回全在这,循环不管
      conversation.append(tool_result for handle.tool_call_id)   # 填残缺槽
      # 落入正常循环(此刻消息态补全,可调模型)

  while True:
      repair(conversation.messages)                  # 每轮防御性(Hermes)
      if budget.interrupted:  return interrupted
      if budget.exhausted():  grace 一轮 or return budget_exhausted   # 计数,挂起安全
      prompt = assembler.assemble(conversation)      # 上下文子系统
      turn   = call_model_with_retry(prompt)         # 模型子系统;重试 N → return failed
      budget.consume(iters=1, tokens=turn.usage)
      append assistant(content, reasoning, tool_calls)

      if not turn.tool_calls:                        # 终止判定
          if turn.content 非空:  return completed(content)
          else:                  空文本重试;超限 → return failed

      # 工具处理:逐调用过闸(整轮缓冲,轮末原子落盘;mid-turn 中断=整轮丢弃,天然干净)
      pending = []
      for call in turn.tool_calls:
          if ctrl.interrupted:  放弃整轮(不落盘) → return interrupted   # 跑过的只有幂等读,无半截控制
          v = gate.classify(call)                    # 工具子系统:allow/ask/deny
          if v == deny:   append 合成 blocked 结果      # 抄 Hermes
          if v == allow:  out = executor.execute(call); append 结果   # allow=只读;校验失败以 is_error 让模型看见
          if v == ask:    pending.append(gate.freeze(call))   # ★不可逆一律走 ask,绝不内联执行
      if pending:
          persist(conversation, pending); emit 确认事件
          return awaiting_confirmation(pending)       # 中途退出,等恢复
      persist_turn_atomic()                          # 整轮(assistant + 所有 tool 结果)原子落盘
      if stall(同 name,args 连发 N 次):  return failed   # stall 守卫
```

退出原因五个、入口两种(新消息 / 恢复),**逻辑闭环**:每条路径都终于一个退出原因或回到循环顶,无悬空分支。

> 注:此为**骨架**。持久化(`store.commit(boundary)` 原子提交)、挂起的**合成占位**、中断的精确回滚、**统一中断标志(伪码里 `budget.interrupted` 与 `ctrl.interrupted` 应合一)**——**精确事务语义以 §六·补 为准**(伪码的 `persist_turn_atomic`/挂起处 `persist` 是简写)。

## 六·补 · 事务化模型(独立设计 agent + 审查 + Temporal/LangGraph 对照后定稿)

> **术语统一:本节"迭代"= 上文"一轮"(model→tools 一次)。** §六 是骨架;本节把骨架里"持久化/挂起/中断"的语义**钉成精确的事务语义,以本节为准**——**粒度不变**(仍按迭代,与 §五补/§六 的"整轮原子落盘"一致),新增的是 boundary marker / 挂起合成占位 / `is_control` 类型保证 / 存储分层。

**核心:消息日志是一个事务性持久状态机。一个迭代(一轮 model→tools)= 一个事务;持久态永远停在合法边界(boundary marker),绝不是撕裂的半截。**

- **事务的原子单元 = 一个迭代(model→tools 一轮),不是整次调用。** 每个迭代末(assistant + 它所有 tool 结果都齐)本就是一个**合法边界**,提交一个 `boundary{status, turn_id, seq}`。这比"整次调用提交一次"安全:崩溃/中断只丢**在途的那一个迭代**,不丢全部(对照 LangGraph **每 super-step 提交一次 + pending writes**)。
- **持久态合法 ⟺ 最后一条是 boundary marker。** 载入时:若尾部不是 marker → **丢到上一个 marker**(多用户版的 Hermes 防御性 repair)。
- **提交 = `store.commit(thread_id, 本迭代新消息, boundary)` 一次原子写**(Postgres 事务 / Redis MULTI)。**删掉逐条 append**——逐条持久化就是撕裂态的根源。

**中断 = 回滚 = 丢弃在途迭代(不提交),不抄 LangGraph 的保留已完成。**
理由:内联跑过的只有**幂等读**,重生成重跑无害且便宜;治理系统里"恢复路径越简单越安全"比省几次读划算。回滚不需要 undo log——**"回滚"就是"不提交"**。

**关键不变式 = 事务正确性本身(不是额外治理规矩):**
> 可回滚的事务里只能装幂等操作(回滚→重生成会重跑)。所以**不可逆控制绝不能内联**——它必须在提交一个 pending 边界**之后**、恢复时用幂等键执行一次。
- 落地成**类型保证,不是运行时纪律**:`LoopTool.is_control` 在注册表声明;**executor 拒绝内联执行任何 control**,只能返回 `awaiting_confirmation`;子 agent **结构上不能执行控制**,只回吐提案给主。随工具增长不会塌。

**挂起 = 提交 pending 边界(用合成占位,且这不违反 Claude 的"不合成"):**
- 控制的 tool_call 块是**完整的**(模型已吐完),我们只是**推迟执行、不是重建内容**——所以给每条悬空控制 tool_call 填一条 `[pending_confirmation]` 占位 tool 结果,**保持序列对 provider 合法**,并作为恢复时的**读回锚点**。(Claude"不合成"针对的是**截断未收全的** tool_use,两码事。)
- boundary 带 `pending_batch:[{tool_call_id, idem_key, frozen_action, handle}]`(对循环不透明)。
- **append-only 只对审计日志成立**;热会话(模型看的那份)那条占位**在恢复时被真结果替换**——两层不矛盾(审计记"pending→resolved"两事件)。

**恢复 = 解析整批:** 逐条 approve→`capability.resolve(idem_key, action)`(读回)→替换占位内容;reject→替换为"已拒绝"。全部悬空槽填齐 → 序列合法 → 提交 completed 边界 → 继续。
- **幂等键在挂起时铸造冻结**(非恢复时)→ 重复 resume / 重连 / 崩溃后重发**用同一键** → 后端去重 = exactly-once。**但 exactly-once 只在后端认这个键时成立**(见下硬依赖)。崩溃恢复加**"下发前先读回查命令是否已存在"**收窄 TOCTOU(缓解非保证)。

**循环↔能力的最小接口:** outcome 升三态 `disposition: executed|failed|awaiting_confirmation` + 不透明 `PendingAction` + `resolve(pending, decision)`。幂等/冻结/去重/读回/TOCTOU **全在控制能力子系统**,循环只搬不透明句柄。

**预算:** 已耗计数要**持久进 boundary、恢复时 rehydrate**(否则恢复的迭代拿满预算);Hermes 的进程内 `threading.Lock` 计数器跨进程无意义。删 `deadline_s` 墙钟。 ✓ `deadline_s` 已删(`budget.py:8-10` 纯计数)。

**存储(多用户服务端,不用 SQLite):**
- 热会话 + 当前边界(含 pending_batch)→ **Redis**(按 thread_id,挂起态加 TTL)。
- 审计(每个边界/冻结控制/idem_key/决策/读回结果,append-only)→ **Postgres**。
- 幂等键账本(idem_key → 状态/结果,unique 约束让重复 resume 变 no-op)→ **Postgres**。
- 不用 SQLite:单写者 + 多进程会损坏(Hermes `state.db` 事故)。崩溃后用 Postgres 边界日志重建 Redis 热态。

**挂起期间来新消息 = 模态门:** 按**形状**分(带 `{tool_call_id:approve/reject}` 的结构化确认 → 解析;其余 → 新请求)。**新自由文本请求不在 pending 上直接起新轮**——要么先批/先拒,要么显式 cancel=reject-all→到干净边界→再处理。**绝不让新意图穿过 pending 态**。初期**单 thread 单 pending**。

**外部对照(都核过):** Temporal(幂等键绑工作流态、重放不重跑已执行、持久执行救不了非幂等后端)· LangGraph(每 super-step 提交 + pending writes + interrupt-resume 填值 + thread_id 租户)· Claude API(截断 tool_use 不合成)· Hermes(每轮防御 repair)。

**★ 硬阻塞依赖(审查点对的):** **后端 `deviceCtrl` 加 `commandId`+幂等(`devicectrl-接口改造建议.md`)之前,不可逆控制不能上线。** Temporal 明说持久执行做不到把非幂等后端变 exactly-once;崩溃后重复 resume 能真双发。harness 侧只能读回收窄,非保证。**这是整个不可逆控制的地基依赖,不是 polish。**

## 八、定稿判断

内圈**设计闭环、可建**,且事务化模型经**独立设计 agent + 审查 + Temporal/LangGraph/Claude/Hermes 对照**核过(§六·补)。本质很小:**消息日志上的事务机**——按迭代提交合法边界、中断=不提交、挂起=提交 pending 边界、恢复=解析整批。**所有治理细节(闸判定、工单、幂等、读回、TOCTOU、权限、verify)都不在循环里**,见治理章。

**一条贯穿不变式(= 事务正确性本身):任何不可逆动作绝不内联,`is_control` 在注册表声明、executor 拒绝内联**——同时保证了中断回滚安全(在途只有幂等读)和写权威外置。

**★ 上线硬依赖**:后端 `deviceCtrl` 加 `commandId`+幂等之前,**不可逆控制不能上线**(持久执行救不了非幂等后端,崩溃重发会双发)。雏形可先用**桩控制能力**把挂起/恢复/pending/幂等接口跑通,真控制 gated 在后端改造。
