# 工具治理与管理子系统 · 设计(v4 · 完整 · 真机已验)

> **方法**:工具层是 harness 不变内核(Claude Code ∩ Hermes 都有)——从这两家提**规范**;旧代码是**经验非样板**;真接口 grounding 以 `业务平台.md`(prod-api 完整文档,RuoYi)为准,关键点已真机勘探(2026-06-22);定位 = 服务任务 × 不可逆 × 不可沙箱 → 取 CC 那一极、治理用"确认"非"围栏"。
> **v4 主轴**:① 缺省从"信任"翻成"不信任"(gate **deny-first** + 可逆性 **fail-safe**);② 权限接真(RuoYi 两层 + org 策略 + 登录快照 + 按权限加载);③ **统一治理**(任何工具一视同仁,不分 agent/leaf);④ 元数据极瘦(`capability_code` ⊥ `is_control`,组织归 toolset)。
> **状态**:设计层定稿、实现层可开工。唯一外部依赖 = 真权限码样例(后端 auth 端点 AI token 够不到,§十三 #2);grounding/可逆性已真机坐实。

## 一、定位与职责边界

**一句话**:后端 = 数据/执行底座,harness = 治理层,用户 = 写的笔。

| 关切 | 归属 |
|---|---|
| 注册 + 元数据 + 组织 / 五道护栏关卡判决 / grounding / 控制提案→执行→读回 | **本子系统** |
| 审计:治理事件的记录与情况管理(内容我们出,存储 append-only 外置、模型不可写) | **本子系统** |
| 作用域分层 + 基于权限决定调用 | **本子系统** |
| 闸机制(suspend/confirm/pending)、append-only 存储 | 委托引擎 |
| 数据级权限(返回哪些数据) | 委托后端 token |
| 输出预算/截断、防注入(非指令框) | **不归我们**(中圈/护栏) |

## 二、统一治理原则(v4 核心)

**只要是工具,一律注册 + 带元数据 + 受权限管理——不分顶层/agent/叶子。**

- agent-as-tool 只是**组织手段**(内部跑子 loop 是 handler 实现细节);从治理视角它就是一个工具,它的叶子也是工具,同等待遇。
- 唯一还存在的"区分"不是治理的,是**组织的**:哪些工具暴露给哪个 loop。这是可见性/加载,用 **toolset 名单**表达,不是治理特例。
- 收益:deny-first 真闭环(无"不在 catalog 故放行"的缝)、叶子也被治理、子⊆父靠 capability_code 而非仅"只读"。

## 三、组件化结构(两条链)

harness 不被后端格式卡住:契约 = 权限结果进 → 加载好的工具集出。

```
【登录链 · 确权一次】
  后端 /user/info(permissions/apiPermissions/devicePermission/dataScope/roleKey)
   → PermissionMapper   : RuoYi 码 → harness 能力码(只取 permissions+apiPermissions)
   → PrincipalResolver  : 叠 org 策略(按 roleKey 强制收紧)→ 有效能力集 → 冻进 session
   → ToolLoader         : 按有效能力集过滤主 toolset → 主模型只看见有权的工具
        资源级(devicePermission/dataScope)不进 harness,留后端 token 过滤

【调用链 · 每次】
  ToolCatalog(扁平注册表:全部工具 + 治理元数据)
   → CatalogGate        : 查 capability_code ∈ ctx.principal(deny 纵深兜底;身份自动加载、LLM 不传)
   → [读] 执行 → Audit
   → [写] Grounding → Proposal → 用户确认 → 确定性执行 → 读回对账 → Audit
   （同一 CatalogGate 传进子 loop,叶子调用同等受查）
```

每段是接缝:后端变只动 Mapper;org 策略变只动 Resolver;主链路不重构。

> **串联入口 = `agent_tools/runtime.py::build_park_runtime(...)` → `ParkToolRuntime`**(composition root):
> 一处把运行链(`build_tool_subsystem`)+ 登录链(`.login()` = user_info→Mapper→Resolver→Principal)+
> 加载层(`.toolset_for()` = ToolLoader)接起。run_loop 接线:`conv.principal=await rt.login(…)`、
> `cfg.toolset=rt.toolset_for(p)`、`gate=rt.subsystem.gate`、`control=rt.subsystem.control`。

## 四、工具组织

- **从业务切,不从 API 模块切**:真接口 ~40 模块多是后台 CRUD;助手按"用户脑子里的业务域"切 = 设备/事项/生活/知识(+控制)。40 模块按域包 agent = 选择爆炸,本末倒置。
- **五类功能(主模型顶层 = 8,按功能命名;2026-07-08 核码 `composition.py`)**:**设备管理(agent)/ 运行管理(flat `record_query`)/ 生活服务(flat×3)/ 知识检索(flat)/ 控制提议(`propose_control`,升顶只读)/ 执行工具(`execute_proposal`,横切)**。
  > 命名按"它干什么"(功能),非"它是什么对象":设备管理=查设备态+控制提案;运行管理=查工单/告警/事件(`record_query` 扁平,无需综合循环);生活服务=会议/停车/餐厅;知识检索=RAG;执行工具=所有写的执行收口。
- **形态判据(收敛成一句)**:子 agent **本身就是一条完整的 ReAct 循环**(M2 递归自相似:自己的 toolset/上下文/预算/plan/动态 think-act-observe,**非写死流水线**);"子"只是所属(子⊆父)+ I/O 契约(task 进、摘要出)+ 父管理生命周期。
  > **判据 = 这个子任务需不需要“自己的一条推理循环”?** 需要 -> 子 agent;单次确定动作 -> flat。消歧(设备:楼->点位)、多步控制编排都是“需要循环”的表现,统一到这一条。(事项的“多记录综合”经评估不够格,返回计数短表、单工具,已扁平为 `record_query`。)
- **子 agent 数 = 1(设施;2026-07-08 核码)**:整个助手能力面里只有设施需要自己的推理循环(消歧、多步控制编排)。事项(records)代码落地时**简化为扁平 `record_query`**(`domains/records.py` 注释:运行事项只一个工具、返回计数短表,不够格当子 agent);其余(能耗=设施叶子、生活查、知识检索)是单次动作 -> flat。**主模型做跨域编排**(诊断设备 = 调设施 agent + `record_query` + 能耗),域 agent 做域内推理,不造 god-agent。(设计早期曾记“设施+事项”双子 agent,代码收敛为单子 agent。)
- **静态组织、不动态选**(规模没到,砍语义检索/tool-search)。
- **组织 = toolset 名单**(非元数据):组合根声明主 toolset;每个 agent 用 `sub_config.toolset` 声明自己暴露的叶子(复用引擎现有概念,不造 parent 反向索引)。
- **多归属天然支持**:一个工具可同时在主 toolset 和某 agent 子 toolset(免费,无需 exposure 字段)。**但策略克制**:本期顶层保持最小(device_status 只做叶子、不双暴露),避免顶层选择退化;简单查询太慢再开。
- **子 agent 隔离**:子只读、隔离上下文、只回吐摘要;子⊆父靠 capability_code。
- **静态组织、不动态选**(规模没到,砍语义检索/tool-search)。

## 五、注册表 + 元数据(极瘦)

**`ToolCatalog` = 扁平注册表**,登记全部工具(顶层/agent/叶子)。每个工具的元数据:

| 字段 | 轴 | 消费者 | 说明 |
|---|---|---|---|
| `tool` | — | 引擎 | LoopTool:name / desc / params / handler / **is_control** |
| **`capability_code`** | 权限 | **gate(deny-first)** | ★每工具**显式声明**(不继承),principal 没有→deny |
| `is_control` | 确认 | gate(ask)/ grounding | 读/控分叉,**注册期钉死** |

**两条设计铁律**:
1. **`capability_code` ⊥ `is_control`(正交两轴)**:权限码管"谁能用",is_control 管"用了要不要确认"。例:`propose_control` = `is_control=False`(只起草不弹确认)+ `capability_code=device:control`(起草控制也要控制权)。`execute_proposal` = `is_control=True` + `device:control`。
2. **每工具显式声明 code,不搞继承**:device_status=`device:read`、propose_control=`device:control`——各写各的,propose_control 自然被控制权限卡,无需"继承+覆盖"机制。

**砍掉的字段**(无运行时消费者 / 可派生 / 不归我们):`parent`、`exposure`(组织归 toolset)、`group`(域=capability_code 前缀,冗余;org 策略"禁设施域"=deny `device:*`)、`keywords`(语义检索砍了)、`output_hint`/`over_budget`/`norm`(输出治理不归我们)。

> 净结论:**统一元数据 = `capability_code` + `is_control`,正交;组织全在 toolset 名单。** 守"无消费者不留"。

## 六、权限模型(两层,RuoYi grounded)

真 `/user/info` 返三权限轴 + dataScope,后端自己就分了能力级/资源级:

| 维度 | 来源 | 落点 |
|---|---|---|
| **能力级**(能不能调这类工具) | `permissions[] + apiPermissions[]`(RuoYi `模块:资源:动作`) | **harness gate** |
| **资源级**(看哪些数据/设备) | `devicePermission[] + dataScope`(全部/本部门/及以下/仅本人) | **委托后端** token |
| 角色(org 策略锚点) | `roleKey / roleType` | PrincipalResolver |

**五铁律**:① 读写全卡、deny-first(工具必声明 code,没有→deny);② 登录确权一次→session 快照,改权限**重登录**生效;③ 调用时自动读 `ctx.principal`,**LLM 绝不传身份**;④ org 策略 harness 自持、按 roleKey 写;⑤ 后端是写的最终权威(纵深防御,快照风险可接受)。

**按权限加载(可见性,减选择)+ deny 闸(纵深兜底)两层并存**:加载层管"看得见什么"、gate 管"调得动什么"(尤其兜子叶子和漏网)。

> 代码修:现 `user_info` 把三轴混成一个 tuple 喂 gate=错,要分开(能力级喂 gate、资源级留后端)。

## 八、可逆性(★fail-safe,真机坐实)

分级轴 = 可逆性,定:确认强度 / 幂等 / **能不能上线**。

| 级 | 对应 | 确认 | 上线 |
|---|---|---|---|
| 只读 | 查询 | 不弹 | 可 |
| 可逆控制 | 状态型(能解析出绝对目标值,读回可验) | 确认 | 可(读回兜底) |
| 不可逆控制 | 非状态型(纯触发/相对/扣费/扇出) | 硬确认 | **不可(后端无 commandId/幂等前硬阻塞)** |

**承重信号 = "能否从字典解析出绝对目标值"(枚举 或 数值范围)**,这正是 grounding 现有 `_resolve_value` 逻辑:
- `paramStatuses` 枚举 → 绝对写到某状态 → **可逆**(读回状态可验)
- `inputType=input/slider` + min/max → 绝对写到某值 → **可逆**(读回数值可验)
- `button`/无枚举无范围 → 纯触发脉冲 → **不可逆**
- 解析不出 → **拒(fail-safe)**

`inputType` 是辅助提示(button/input/slider),**但不单独承重**:实测 `button` 多带枚举(冷却泵启停、盘管风速档)= 设状态 = **可逆**,非纯触发。纯触发才 = button **无**枚举无范围。`reversibility_map` 只留欺骗性例外(能解析但实不可逆,如未来扣费金额)。

> **★真机(2026-06-22)**:AI 可控设备全集 = **暖通专业**(`getIsCtrlTree`:空调机组/风机盘管/新风机组/电动蝶阀/冷却泵),全状态型、**全可逆,无门禁/道闸纯触发**。控制参数实例:温度 input(18–30)/ 阀开度 slider(0–100)/ 风机·风速 button枚举 / 频率 input(50–100)。→ **本期控制管线只需"可逆"路(确认 + 读回);"不可逆硬阻塞"零触发对象、纯防御**(门禁若纳入才触发)。

## 九、控制管线(写治理核心)

- **单步写**(本期=设备状态型,即全部可控设备):提案(grounded 精确参数+可逆性+handle)→ execute_proposal → 用户确认 → 确定性下发 → `getDevicePage` 读回对账 → outcome(applied / 未生效→降级人工)。
- **多步写**(模型组合多步 / 未来场景联动,**后置**):**整 plan 确认意图 + 按可逆性分步执行 + 失败即停**——可逆步批准后直执、不可逆步执行到了单独再确认;复用 `pending_batch`;后端补幂等键再开,届时填 batch 不重构。
- **场景联动 = 多设备扇出触发**(确认卡须展示影响面;结构不可逆 + 读回失效)→ 现阶段当场拒(且当前不在可控全集内)。

## 十三、★架构师核查:已解 / 仍开 / 风险

**真机已解(2026-06-22)**:
- **grounding 路线**:`getMenu` 实测返 `MENU_NOT_EXISTS`(需后端预配菜单,非通用 grounding)→ 排除;**grounding 走 sycPointParamType**(isCtrl+inputType+范围+枚举齐全)。
- **可逆性判定**:承重信号 = 能否解析绝对目标值(=现有 `_resolve_value`);可控全集为暖通状态型、全可逆;不可逆为纯防御。

**仍开(不阻塞设计/实现)**:
2. **真权限码样例**:`/user/info`、`getInfo`、`getRouters` 走 AI token + 公共网关全 404(auth/menu 服务此 token 够不到);`getRoleAuthDevice/{roleId}` 能调但 admin 返空。→ **需后端把 auth 端点开给 AI 服务 / 给 /user/info 样例**;PermissionMapper 接缝(默认直通)先兜。**这是后端协调项,非设计问题。**
4. **org 策略规则**:按 roleKey,具体口径需业务方给;先留配置接口。
5. **dataScope 语义**:需真机确认后端确实按 dataScope 过滤返回。
6. **审计存储落点**:用引擎 PG 账本(A1)还是单独治理事件表,schema 未定。
7. **登录快照失效窗**:靠"后端写时再查"兜——需确认 deviceCtrl 服务端真校验权限,否则纵深防御是空的。
8. **子权限⊆父**:目前靠只读 + capability_code;扩多写域时验"权限子集"严格成立。

**核查结论**:架构骨架自洽、缺省安全(deny-first + fail-safe)对齐 CC/Hermes;元数据极瘦守住"无消费者不留";grounding 与可逆性已真机坐实。**设计层定稿,实现层可开工**——deny-first gate / 元数据收敛(capability_code ⊥ is_control)/ 叶子进 catalog / ToolLoader / 可逆性结构判定 均不被阻塞;唯一外部依赖(真权限码)是后端协调项,接缝已留。
