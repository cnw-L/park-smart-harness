# 智慧园区 Harness 落地实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 把多轮讨论收敛的 harness 设计,落到现有 `capability_platform` 上 —— 不重写,而是消除重复运行时、补齐缺口,按"治理优先+评测先行"分期推进。

**Architecture:** 现有 `assistant_core/capability_platform` 已实现我们设计的核心(读控分叉、两段校验、工具注册表+分组、grounding/防腐、manifest、trace;**条件DAG 将在收敛中移除**,plan 退化为线性 todo 列表)。本计划在其上:① 消除三套重复运行时;② 补 grounding 管线/输出预算/缓存;③ 控制闭环(prepare→确认→读回→对账);④ 升级为递归 ReAct + plan 即状态;⑤ 工具组织(语义检索+agent-as-tool);⑥ MCP 封装+多域+审计。

**Tech Stack:** Python 3.11+, LangGraph + Redis checkpointer, FastAPI(8020), httpx(后端 prod-api), pydantic, pytest。后端=业务平台 prod-api(CRUD/SCADA)。

---

## Context(为什么)

经过长讨论,设计已收敛(详见本文件夹内设计文档,[`README.md`](README.md) 为入口),但落地有三个现实:
1. **现有代码已实现大半设计**,但有**三套重叠运行时**(`capability_platform/`、`platform_runtime/`、`harness/`)需要先收敛成一套,否则后续在哪改都模糊。
2. **后端是富 CRUD/SCADA**,原料齐全;唯一真缺陷是 `deviceCtrl` 安全包络(无幂等/无回执),且仅对"非状态型"控制动作才阻塞 —— 是外部依赖,不阻塞读路径。
3. 几个**设计决策仍未拍板**(见末节 Gate),它们只阻塞对应的后期 Phase,不阻塞前期。

本计划先交付**文档合集(Part A)**,再按**评测先行+治理优先**推进实现(Part B)。

## Phase 0 — 收敛运行时(先清地基)
**问题**:`capability_platform/`(最完整)、`platform_runtime/`、`harness/` 三套重叠。
- [ ] 确认 `capability_platform` 为唯一运行时;`platform_runtime/`、`harness/`(旧)标记删除或归档。
- [ ] 让 8020 graph(`graph.py` 的 capability 节点 `nodes/capability.py`)只走 `capability_platform`。
- [ ] 跑现有相关测试(`tests/test_assistant_core_capability_platform.py`、`test_assistant_core_platform_runtime.py`)确认无回归;删测同步。
- **验收**:仓库只有一套 harness 入口;`compileall` + 相关 pytest 绿。

## Phase 1 — 评测基线 + N=1 读能力端到端(评测先行)
- [ ] 选 `device.status.query` 一条读能力,接真实后端 `getDevicePage`(经 `runtime_adapters`),跑通 NL→意图→路由→grounding→两段校验→归一化→回答。
- [ ] 写 15–20 条评测用例(扩 manifest 的 `eval_cases`,如"302空调状态不得返回前台宽结果"),做一个 eval runner,跑出**基线命中率**。
- [ ] 打开 trace(`TraceRecorder`),确认每模块边界有事件。
- **验收**:基线命中率有数;trace 可见;读路径真实后端跑通。

## Phase 2 — 读路径加固:grounding 管线 + 输出预算 + 缓存
- [ ] **grounding 管线**:LLM 抽槽 → 规则解析(楼栋名→buildingId〔**Gate-依赖**:楼栋/区域树接口待定位〕、"空调"→pointTypeId via `sycPointParamType`、候选检索、消歧)。消歧作为一等结果(返回候选,交编排决定),复用现有 candidates 字段。
- [ ] **输出预算**:在归一化层给工具结果加 `output_budget`(top-k/字段投影/聚合摘要/截断+"请收窄"信号);**读可截断,控不可静默截断**。
- [ ] **缓存分层**:字典/区域树/权限狠缓存(长TTL),设备实时态不缓存。
- **验收**:宽查询不再吐大 blob;一次查询多跳→1热读+N缓存;消歧用例通过。

## Phase 3 — 控制闭环(prepare→确认→执行→读回→对账)
- [ ] 保持 `execute` 在 Python 侧 DENIED(现状正确);控制走 `device.control_ticket.prepare`→前端确认→后端执行。
- [ ] 防腐层实现 **下发→读回→对账**:`requestId` 在下发前 append 落账;`getDevicePage` 读回 status/value 对照字典确认到位;崩溃恢复=状态重读对账。
- [ ] 确认按风险分级(只对不可逆/高影响),防确认疲劳。
- **Gate-依赖**:非状态型动作(相对/触发/扣费)需 `deviceCtrl` 加 `requestId`/`commandId`(见 `devicectrl-接口改造建议.md`);未改前这些动作只能"挡自己重发+读回",并诚实标注更弱保证。
- **验收**:控制走完整闭环;错误/越权动作率→0(红线);重放不重发已发指令。

## Phase 4 — 递归 ReAct + plan 即状态(地基,Gate 后)
- [ ] 把"单能力 bounded loop"上面**加一层顶层递归 ReAct**:显=plan/todo、隐=thought;**plan=全量快照,作为工具调用 append 进消息日志**(Claude Code 模式),任务层在上下文中**靠后排**(缓存)。
- [ ] **预算模板**(Hermes):iteration cap + remaining budget + 一次 grace call 收尾 + 硬超时 + interrupt-break。
- [ ] 重规划触发:工具失败 / 执行后校验不过 / **用户 steer**(第三触发器);增量重规划 + 放弃/上报终止口。
- [ ] **重放压缩**:session 边界可见 + token 计数 + 压缩摘要替代全量重放(Hermes 89% 浪费教训)。
- **Gate**:~~plan↔条件DAG 关系~~(已收敛为线性 todo 列表,砍掉 DAG)、行动闸嵌入位置(已收敛为子系统 seam,循环只负责 `awaiting_confirmation`)。
- **验收**:多轮任务可跨轮维护 plan;预算耗尽如实收尾不死循环;长会话 token 不爆。

## Phase 5 — 工具组织:语义检索 + agent-as-tool
- [ ] 在现有 category 分组上**叠语义检索**(先定模块→模块内检索);路由形状统一 2 跳(L0选域→L1选工具)。
- [ ] **设备域升格 agent-as-tool**(隔离上下文+自有循环+归一化回吐);子权限⊆父、**子 agent 不碰 memory/不可再 delegate**(Hermes 治理)、深度≤2、并发≤3。
- [ ] 候选集按**权限过滤**(check_fn 式),模型看不见越权工具。
- **验收**:每跳候选≤~7;设备子 agent 隔离回吐;权限过滤生效。

## Phase 6 — MCP 封装 + 多域 + 审计持久化
- [ ] 把能力封成 **MCP server**(统一注册/权限/日志元数据);MCP 本身作为治理对象 deny-first。
- [ ] 照设备 manifest 模板复制 **工单域**(报修 `报修表` 接口),证明"加一个域=填模板"。
- [ ] **审计**:`TraceRecorder` 事件**持久化为审计日志**(模型不可写);**append-only 文件=真相,可查询 DB=可重建索引**(Hermes state.db 损坏教训:多进程并发写要锁或走文件真相)。
- **验收**:能力以 MCP 暴露;工单域跑通;审计可复盘"为何走到某步"。
