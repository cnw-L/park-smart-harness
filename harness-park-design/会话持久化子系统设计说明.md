## 一、设计目标

### 1.1 一句话目标

让 `run_loop` 的会话状态**可恢复、可审计、可横向扩展**，通过 **Redis 承载热态工作集 + PostgreSQL 承载冷态审计与幂等**，实现 speed 与 durability 的分离。

### 1.2 具体目标

| 目标 | 说明 |
|---|---|
| **快速恢复** | 用户重新连接时，毫秒级从 Redis 恢复当前会话 |
| **挂起不丢** | awaiting_confirmation 状态有 TTL，过期前可恢复 |
| **审计可追溯** | 每个边界写入 PG append-only 日志，支持事后审查与重建 |
| **幂等去重** | 控制操作（approve/reject）通过 PG 幂等键台账去重，崩溃重试不重复落账 |
| **不阻塞循环** | 热态读写走 Redis；PG 审计和控制台账异步化或轻量同步 |
| **可运维** | Redis key 带 TTL，PG 表自举，配置集中 |

### 1.3 成功标准

| 指标 | 目标值 |
|---|---|
| `load()` p99 延迟 | < 50ms（Redis 本地/同机房） |
| `commit()` p99 延迟 | < 20ms（Redis MULTI/EXEC） |
| `latest_boundary()` p99 延迟 | < 10ms |
| PG 审计写失败时纯对话边界可用性 | 100%（best-effort） |
| PG 审计写失败时控制边界可用性 | 0%（fail-closed，必须成功） |
| 挂起状态 TTL 内可恢复率 | 100% |
| Redis 丢失后从 PG 重建 | 后续能力，本设计预留审计数据 |

## 二、范围边界

### 2.1 In Scope

- 会话消息日志的持久化与加载。
- 边界（Boundary）的原子提交与查询。
- pending 控制动作的原地解析与状态推进。
- Redis 热态存储：messages + boundaries 列表。
- PG 冷态：幂等键台账、边界审计日志。
- 序列化 codec：Message / Boundary / PendingAction 的 JSON-safe 编解码。
- 配置聚合：Redis URL、TTL、PG DSN、LLM 配置。

### 2.2 Out of Scope

- **真 deviceCtrl 下发**：仍依赖后端 commandId + 幂等改造，本系统只提供 harness 侧幂等账本。
- **崩溃后从 PG 重建 Redis 热态**：P3 审计数据已备，重建流程留后续韧性工作。
- **多 writer 并发控制**：当前设计假设同一 thread_id 同一时刻单 writer，由上层 gate/control 保证。
- **消息加密**：当前明文 JSON 存储；如需加密，可在 codec 层扩展。
- **跨地域复制**：Redis/PG 的集群拓扑由运维层决定。

## 三、总体架构

### 3.1 存储分层

| 层级 | 技术 | 用途 | 数据 |
|---|---|---|---|
| **热态** | Redis | 快速读写、恢复、挂起 TTL | messages 列表、boundaries 列表 |
| **冷态** | PostgreSQL | 审计、幂等、重建真相源 | boundary 审计日志、控制幂等键台账 |
| **序列化** | JSON (codec.py) | 跨层传输格式 | Message / Boundary / PendingAction |

### 3.2 组件图

```
                       run_loop
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
AuditedConversationStore       ControlCapability
        │                            │
        │                            ▼
        │                     PgIdempotencyLedger
        │                            │
        ▼                            ▼
RedisConversationStore         PgStore (asyncpg pool)
(Redis LIST)                   ├── agentloop_idem
                               └── agentloop_audit
```

> 注：记忆子系统（MemoryEventPublisher / MemoryExtractor / Outbox）与会话持久化子系统相邻，但不在本系统范围内，详见 `memory-subsystem-design.md`。

### 3.3 数据流

#### 读取流

```
用户重新连接 / run_loop 启动
  → AuditedConversationStore.load(thread_id)
    → RedisConversationStore.load(thread_id)
      → LRANGE messages 0 -1
      → LINDEX boundaries -1（用于 latest_boundary/resolve 与 refresh_on_read）
      → decode_message / decode_boundary
      → derive_plan(messages)
    → 返回 Conversation
```

> 说明：load() 不读取 boundaries 全量列表，仅取最新边界 O(1)。历史边界通过 latest_boundary() 单独查询。

#### 正常提交流

```
run_loop 完成一次迭代
  → AuditedConversationStore.commit(thread_id, new_messages, boundary)
    → RedisConversationStore.commit (MULTI/EXEC: RPUSH messages + RPUSH boundary)
      → 若 boundary.status == awaiting_confirmation → EXPIRE key TTL
      → 否则 → PERSIST key（移除 TTL）
    → 若 boundary.pending_batch 非空（控制边界）
         → PgAuditLog.audit_boundary 强制成功
      否则（纯对话边界）
         → PgAuditLog.audit_boundary best-effort
```

#### resolve_pending 流

```
用户 approve/reject
  → ControlCapability.resolve(pending, decision)
    → approve: PgIdempotencyLedger 保证控制执行幂等
    → 返回 ToolResult
  → run_loop 把 [pending_confirmation] 占位替换为真实 tool 结果
  → AuditedConversationStore.resolve_pending(thread_id, resolved, boundary)
    → RedisConversationStore.resolve_pending
      → LRANGE 读全量消息
      → 内存中替换 [pending_confirmation] 占位
      → MULTI/EXEC: DEL messages + RPUSH 新消息 + RPUSH boundary
      → TTL/PERSIST 处理
    → PgAuditLog.audit_boundary 强制成功
```

> 分层说明：幂等控制执行由 `ControlCapability` 负责，`AuditedConversationStore` 只负责边界持久化 + 强制审计。Ledger 不属于 store 层。

## 四、数据模型与序列化

### 4.1 Message 编码

```python
{
  "role": "user" | "assistant" | "tool" | "system",
  "content": "...",
  "reasoning": "...",
  "tool_calls": [{"id": "...", "name": "...", "arguments": {}}],
  "tool_call_id": "...",
  "name": "...",
  "is_error": false
}
```

### 4.2 Boundary 编码

```python
{
  "status": "iteration" | "completed" | "awaiting_confirmation" | "failed",
  "turn_id": "...",
  "seq": 1,
  "pending_batch": [
    {
      "tool_call_id": "...",
      "idem_key": "...",
      "frozen_action": {"name": "...", "arguments": {}},
      "handle": null
    }
  ],
  "budget_snapshot": {"iters": 0, "tokens": 0, "grace_used": false}
}
```

### 4.3 Codec 纪律

- 纯函数，无 I/O。
- 编码结果可被 `json.dumps` / `json.loads` 安全穿越。
- 解码对缺失可选字段宽容，忽略未知字段。
- 所有 dict 字段深拷贝，避免下游修改污染 live 对象。

## 五、Redis 热态存储设计

### 5.1 Key 设计

```
agentloop:{thread_id}:messages    -> LIST of JSON strings
agentloop:{thread_id}:boundaries  -> LIST of JSON strings
```

### 5.2 操作语义

| 操作 | Redis 命令 | 说明 |
|---|---|---|
| commit | MULTI/EXEC: RPUSH messages + RPUSH boundary | 原子追加 |
| load | LRANGE messages 0 -1 + LINDEX boundaries -1 | 读全量消息 + 最新边界 |
| latest_boundary | LINDEX boundaries -1 | O(1) |
| resolve_pending | LRANGE + DEL + RPUSH messages + RPUSH boundary | 原地重写（见 §5.5 崩溃窗口说明） |
| 挂起 TTL | EXPIRE key TTL | 防止挂起会话永不过期 |
| 活跃恢复 | PERSIST key | 活跃会话不应因旧 TTL 丢失 |

### 5.3 TTL 策略

| 场景 | TTL 行为 |
|---|---|
| boundary.status == awaiting_confirmation | EXPIRE key TTL（默认由 env `ASSISTANT_REDIS_CHECKPOINT_TTL_MINUTES` 控制，必须 > 0） |
| boundary.status == iteration/completed/failed | PERSIST key（移除 TTL） |
| load 时最新边界为 awaiting_confirmation | refresh_on_read=True 时刷新 TTL |

> 注意：
> - `ASSISTANT_REDIS_CHECKPOINT_TTL_MINUTES` 默认 `60` 分钟；
> - `0` 表示禁用 TTL，挂起会话不会因 TTL 释放（不推荐生产环境，需配合其他清理策略）；
> - 负值应被配置校验拒绝。

### 5.4 挂起状态恢复

```python
# run_loop 启动时
last = await store.latest_boundary(thread_id)
if last and last.status == "awaiting_confirmation":
    # 会话仍处于挂起态，等待用户 approve/reject
    return LoopResult(..., status="awaiting_confirmation", pending=last.pending_batch)
```

### 5.5 单 writer 假设与崩溃窗口

`resolve_pending` 使用 read-modify-write 模式：
1. LRANGE 读全量消息。
2. 内存中替换占位。
3. DEL + RPUSH 重写 messages。

不加 WATCH 的原因：
- 同一 thread_id 同一时刻至多一个 pending 集。
- 上层 gate/control 保证无并发 resolve。
- 避免 WATCH 带来的重试复杂度。

> ⚠️ 崩溃窗口：MULTI/EXEC 内部虽然原子，但 `DEL` 与 `RPUSH` 之间若进程崩溃，messages 列表会被清空而 boundaries 尚未追加，导致会话消息永久丢失。该风险由「单 writer + 极短事务时间」降低，但不是零。若未来需要多 writer 或零容忍，应引入：
- Redis Stream 或锁；
- 或改为 append-only 语义（不原地修改 messages）；
- 或使用 `RENAME` / 先写新 key 再原子切换。

## 六、PostgreSQL 冷态设计

### 6.1 Schema

```sql
-- 幂等键台账
CREATE TABLE IF NOT EXISTS agentloop_idem (
    idem_key    text PRIMARY KEY,
    status      text NOT NULL,          -- 'executed' | 'failed' | 'in_flight'
    result_json jsonb,
    created_at  timestamptz NOT NULL DEFAULT now()
);

-- 边界审计日志
CREATE TABLE IF NOT EXISTS agentloop_audit (
    id              bigserial PRIMARY KEY,
    thread_id       text NOT NULL,
    seq             int,
    boundary_status text,
    payload         jsonb,              -- 编码后的 Boundary
    created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_audit_thread_id ON agentloop_audit(thread_id, seq);
```

> 运维说明：
- `agentloop_idem` 以 `idem_key` 主键自带 B-tree 索引，无需额外索引。
- `agentloop_audit` 建议按 `thread_id, seq` 建索引，支撑按会话/序列号的审计查询。
- 审计表为 append-only 增长表，需配套归档/分区策略（见 §14 Phase 1）。

### 6.2 幂等键台账

```python
class PgIdempotencyLedger:
    async def get(self, idem_key: str) -> dict | None: ...
    async def put_if_absent(self, idem_key: str, status: str, result: dict) -> bool: ...
    async def update(self, idem_key: str, status: str, result: dict) -> None: ...
```

- `put_if_absent` 使用 `INSERT ... ON CONFLICT (idem_key) DO NOTHING`。
- 返回 True → 首次写入；False → 已存在，幂等忽略。
- `update` 用于把 in_flight 状态更新为最终状态。

### 6.3 控制执行幂等去重

```python
class PgControlCapability:
    def freeze(self, call: ToolCallReq) -> PendingAction:
        idem_key = uuid4().hex
        return PendingAction(tool_call_id=call.id, idem_key=idem_key, ...)

    async def resolve(self, pending: PendingAction, decision: str) -> ToolResult:
        if decision == "reject":
            return ToolResult(ok=True, content="[rejected] ...")

        # approve
        cached = await ledger.get(pending.idem_key)
        if cached:
            return ToolResult(
                ok=cached.get("ok", True),
                content=cached.get("content", ""),
                error=cached.get("error"),
            )

        result = await execute_control_action(pending)
        result_dict = {
            "ok": result.ok,
            "content": result.content,
            "error": result.error,
        }

        inserted = await ledger.put_if_absent(pending.idem_key, "executed", result_dict)
        if not inserted:
            # 并发竞态：取存储结果
            stored = await ledger.get(pending.idem_key)
            return ToolResult(
                ok=stored.get("ok", True),
                content=stored.get("content", ""),
                error=stored.get("error"),
            )

        return result
```

> 精确一次语义说明：上述流程是「执行后写 ledger + ON CONFLICT 去重」。它保证同一 `idem_key` 最多只在 ledger 里留下一条记录，但**无法保证外部副作用只发生一次**——如果 `execute_control_action` 已产生副作用而进程在写 ledger 前崩溃，重试时会再次执行。
>
true 精确一次需要：
- ledger 先写 `in_flight`；
- 再执行；
- 成功后更新为 `executed`；
- 执行器自身具备幂等或补偿能力。
>
本设计目前提供的是「幂等去重 + 执行窗口内可能重发」，不是严格精确一次。

### 6.4 审计日志写入策略（B/C 路径）

| 边界类型 | 审计要求 |
|---|---|
| 纯对话边界（无 pending_batch） | B-path（best-effort）：失败只记 warning，不阻断会话 |
| 控制边界（pending_batch 非空） | C-path（fail-closed）：失败上抛，但 Redis 侧边界仍可能已提交 |
| resolve_pending | C-path（fail-closed）：控制已解析，审计必须成功 |

说明：
- **B-path**：纯对话丢了审计只是运维损失，不阻塞会话可用性。
- **C-path**：控制边界丢了审计会导致「已挂起但无记录」，配合驱逐可能造成永久丢失，因此审计失败必须上抛。
- ⚠️ **真相源分裂风险**：`AuditedConversationStore.commit()` 先写 Redis，再写 PG。如果 PG 审计失败，异常会上抛给 run_loop，但 Redis 中的边界**已经存在**。下次启动时 `latest_boundary()` 会读到 Redis 中的边界，而 PG 缺少对应审计记录。这不是「边界未持久化」，而是「PG 审计未持久化」。后续若依赖 PG 重建 Redis，这条边界会被漏掉。需要区分「热 store 已提交」与「冷审计已落库」两种状态。

## 七、ConversationStore 协议与装饰器

### 7.1 协议

```python
class ConversationStore(Protocol):
    async def load(self, thread_id: str) -> Conversation: ...
    async def commit(self, thread_id: str, new_messages: list[Message], boundary: Boundary) -> None: ...
    async def latest_boundary(self, thread_id: str) -> Boundary | None: ...
    async def resolve_pending(self, thread_id: str, resolved: dict[str, Message], boundary: Boundary) -> None: ...
```

### 7.2 AuditedConversationStore 装饰器

```python
class AuditedConversationStore:
    def __init__(self, inner: ConversationStore, audit: Any) -> None:
        self._inner = inner
        self._audit = audit

    async def load(self, thread_id: str) -> Conversation:
        return await self._inner.load(thread_id)

    async def latest_boundary(self, thread_id: str) -> Boundary | None:
        return await self._inner.latest_boundary(thread_id)

    async def commit(self, thread_id, new_messages, boundary):
        await self._inner.commit(thread_id, new_messages, boundary)
        if boundary.pending_batch:
            await self._audit.audit_boundary(thread_id, boundary)  # C-path: 强制,失败上抛
        else:
            await self._audit_safe(thread_id, boundary)             # B-path: best-effort

    async def resolve_pending(self, thread_id, resolved, boundary):
        await self._inner.resolve_pending(thread_id, resolved, boundary)
        await self._audit.audit_boundary(thread_id, boundary)       # C-path: 强制,失败上抛
```

> C-path 上抛含义：异常会传播给 run_loop，但 Redis 中的边界可能已提交。详见 §6.4 真相源分裂风险说明。

## 九、失败模型与可靠性

| 故障场景 | 行为 |
|---|---|
| Redis 读失败 | 上抛，无法恢复当前会话 |
| Redis 写失败 | 上抛，本次边界未提交 |
| Redis 挂起 key TTL 过期 | 会话丢失；审计数据已预留，从 PG 重建热态属于 Phase 1 后续能力 |
| PG 审计写失败（纯对话边界） | log warning，不阻断（B-path） |
| PG 审计写失败（控制边界） | 上抛；但 Redis 边界可能已提交，存在 PG 审计缺失风险（C-path） |
| PG 幂等台账写失败 | 上抛，控制操作结果可能未记录 |
| PG 幂等台账读命中 | 返回缓存结果，不重执行 |
| 序列化/反序列化失败 | 上抛，数据损坏需人工介入 |

## 十、性能与扩展性

### 10.1 延迟预算

| 操作 | 预算 |
|---|---|
| Redis commit | < 20ms |
| Redis load | < 50ms |
| Redis latest_boundary | < 10ms |
| PG audit insert | < 30ms |
| PG idem get/put | < 20ms |

### 10.2 扩展性

- Redis：无状态，可多实例；按 thread_id 分片。
- PG：幂等表按 idem_key 索引；审计表按 thread_id + seq 索引。

|---|---|---|
| `store_commit_total` | counter | 提交次数 |
| `store_commit_latency_seconds` | histogram | 提交延迟 |
| `store_load_total` | counter | 加载次数 |
| `store_load_latency_seconds` | histogram | 加载延迟 |
| `store_audit_failed_total` | counter | 审计写失败次数 |
| `store_idem_hit_total` | counter | 幂等命中次数 |
| `store_redis_ttl_expired_total` | counter | Redis TTL 过期次数 |

### 12.2 Logs

- 每次 commit / resolve_pending 记录 thread_id、seq、status。
- 审计失败记录详细异常。
- 幂等命中记录 idem_key。

### 12.3 Traces

- OpenTelemetry span：`store.commit`、`store.load`、`store.audit`、`store.idem`。
- 埋点建议位置：
  - `RedisConversationStore.commit()` / `load()` / `resolve_pending()`：记录 Redis 命令延迟；
  - `AuditedConversationStore.commit()` / `resolve_pending()`：在调用 `_audit.audit_boundary()` 前后记录审计延迟；
  - `PgIdempotencyLedger.get()` / `put_if_absent()`：记录幂等命中与写入延迟。

## 十三、安全与隔离

| 关注点 | 机制 |
|---|---|
| 会话隔离 | thread_id 作为 Redis key 前缀；PG 查询按 thread_id 过滤 |
| 用户身份 | Principal 不持久化到 store，由调用方在会话入口注入 |

| 审计防篡改 | append-only，不更新历史记录 |
| 敏感数据 | 当前明文 JSON；如需加密，在 codec 层扩展 |

## 十五、关键设计决策总结

| 决策 | 选择 | 理由 |
|---|---|---|
| 热态存储 | Redis LIST | 快速追加/读取，天然支持原子 MULTI/EXEC |
| 冷态存储 | PostgreSQL | 事务性审计、幂等键、成熟运维 |
| 边界原子提交 | Redis MULTI/EXEC | 避免消息写了边界没写的撕裂 |
| pending 解析 | 原地替换 messages | 简单、满足单 writer 假设；注意 DEL+RPUSH 崩溃窗口 |
| 审计策略 | 纯对话 B-path（best-effort），控制边界 C-path（fail-closed） | 安全与可用性平衡；C-path 存在 Redis/PG 真相源分裂风险 |
| 幂等执行 | PG unique key + ON CONFLICT DO NOTHING | 幂等去重，执行窗口内可能重发；非严格精确一次 |
| TTL 策略 | 挂起设 TTL，活跃 PERSIST | 防止资源泄漏，同时保护活跃会话 |
| 配置 | 环境变量 + settings.py 聚合 | 集中、可测试、不触发 I/O |
