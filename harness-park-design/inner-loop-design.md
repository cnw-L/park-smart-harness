## 0. 本质

内圈是一个**事务型 ReAct 控制循环**。一条核心决定贯穿全部设计:

> **消息日志即状态(state = the message log)** —— 引擎不另存状态机。模型的思维/决定、工具结果、计划、待确认提案,全在那一条消息日志里;引擎每轮只读它、追加它、提交它。

由此推出:一轮里**唯一不确定的是"模型那句决定"**,其余全是确定性引擎行为。模型负责"想下一步";引擎负责**组上下文、过安全闸、执行工具、把结果穿回、提交边界、兜底**。

## 1. 一轮的工作路径

```
顶部守卫(repair 序列 · 中断检查 · 预算/grace · 本地步数闸)
 → ① 组装上下文(assemble;超阈压缩;空转时注入 nudge,不落日志)
 → ② 问模型(得到 ModelTurn:content / reasoning / tool_calls)
 → ③ 按"这句"分支(完成 / 空响应 / 无进展检测 / 有工具→执行)
 → ④ 执行(gate 两遍:deny 合成 blocked / ask 冻结挂起 / allow 并发跑 + verify)
 → ⑤ 执行后(中断回滚 / 挂起提交 / 熔断 / 无进展核查)
 → ⑥ 正常:提交 iteration 边界,回顶
```

模型每轮出一个决定,引擎据这句的内容决定怎么走。**意图永远在模型,引擎是接住决定去干活的底盘 + 护栏。**

### 1.1 ModelTurn 三字段:为什么 `reasoning` 要独立

一轮的模型输出 = `content`(给用户的**答案**)/ `reasoning`(内部**思考链**)/ `tool_calls`(**动作**)。三者身份不同,`reasoning` 单列而非并进 content,有五个理由:

1. **思考模型本就分两路返回**:qwen thinking、DeepSeek `reasoning_content`、OpenAI o 系列把思考与答案当**两个独立字段**返回(`providers.py` 兼容 `reasoning`/`reasoning_content`)→ 数据结构必须分开接才能如实存。
2. **三样东西混不得**:答案 / 动作 / 思考各有各的处理,搅一起后面判定全乱。
3. **保持完成判定干净**(最关键):完成 = 无 tool_calls + **content 非空**。若把 reasoning 塞进 content,"只想了没答"的回合会**假装有 content → 误判完成**。分开后判定只认 content。
4. **回放策略可控**:思考是**每轮一次性**的,旧 reasoning 回灌下一轮会膨胀上下文、误导模型(provider 普遍建议历史只带 content+tool_calls)。分字段才能"**落库留痕、组装时丢思考留答案**"。
5. **可观测**:单独留思考链便于 trajectory 分析/badcase 复盘,又不污染答案。

harness 实际:分开存在 Message(`messages.py:16`)、持久化序列化(`codec.py`)、token 计数计入(`tokens.py`)。⚠ **两处判定别混**:循环本体的**完成/空响应判定只看 `content`**(`loop.py:292`)→ **纯 reasoning、content 为空的回合 = 空响应(回滚+重试,连续耗尽才 `failed`),不会被当成完成**;而 `plan_view.py:87` 的 `has_content`(含 reasoning)是**另一目的**——剥离 plan 调用时判断该消息删不删,与循环判定无关。

## 2. 退出方式

| status | 触发 | final 内容 | 提交的边界 | 在途处理 |
|---|---|---|---|---|
| `completed` | 模型停手 + 有正文 | 模型答 | completed | 提交 |
| `budget_exhausted`(grace 收尾) | 首次预算耗尽,放一轮收尾 | 模型收尾答 | completed | 提交 |
| `budget_exhausted`(硬停) | grace 已用 / 本地步数尽 | 占位语 | 无(顶部 return) | — |
| `awaiting_confirmation` | 控制工具 ask → 冻结 | "(等待确认)" | awaiting(带 pending) | 提交 |
| `failed`(熔断 tool_failures) | 基础设施连续失败 | 占位语 | failed(留痕) | 提交 |
| `failed`(stall/no_progress/unproductive/model_error/empty/compaction_thrash) | 各类空转/失控 | 占位语 | 无 | 回滚 |
| `interrupted` | 收到中断 | 占位语 | 无 | 回滚 |
| —(续轮) | 正常一批工具跑完 | — | iteration | 提交 → 回顶 |

**完成判定**:唯一判据 = 模型**不再调工具 + 给非空正文**(行为,对齐原生语义)。**不靠 plan**——plan 是模型记账、可捏造、非权威。

**grace**:首次预算耗尽放**一次性**收尾回合,让模型用现有信息给交代。该轮**不执行工具**;status 诚实标 budget_exhausted、边界却标 completed(给了交代);`grace_used` 持久化防崩溃重启重复白拿;只针对共享池(本地步数尽无 grace)。

## 3. 事务性:提交与回滚

每轮是一个事务:顶部 `committed_len` 记回滚点,末尾一次 `_safe_commit` 原子提交一个边界。

**提交 vs 回滚的判据不是"成败",是"本轮有没有产生需保留/恢复的真实状态(副作用/真实事件)"**:
- 给了交代(completed/grace)、要恢复(awaiting 带提案)、有真实副作用(熔断:工具真执行过)→ **提交**;
- 空转/被打断/哑火(stall/中断/空响应)→ **回滚**(`del messages[committed_len:]`,丢本轮在途),退回上一个已提交边界。

**回滚 ≠ 重启**:回滚只清掉**当前这一轮**没提交的在途消息(前面已提交的边界一个不动),然后 run 退出;再试是**新的一次 run_loop**。

### checkpoint(Boundary)存什么
一次提交写三样:`thread_id` + 本轮新增消息(buffer)+ 一个 `Boundary`:
- `status`:iteration / completed / awaiting_confirmation / failed
- `turn_id` / `seq`(单调序号,决定重放顺序)
- `pending_batch`:待确认提案(仅 awaiting 非空)
- `budget_snapshot`:`{iters, tokens, grace_used}`

恢复语义:`load()` **只重建到最后一个 Boundary**,之后的"撕裂尾"(torn tail)静默丢弃 —— 这是"原子提交、不留半截"在恢复侧的保证。

## 4. 持久化与恢复

提交时**双写**(`AuditedConversationStore` 装饰器):
- **Redis** = 活跃会话、热、**恢复源**(先落);
- **PG** = `agentloop_audit` 留痕,可 `read_audit` 重放重建;**目标是长期权威冷存**。审计写失败只 log warning,不阻断已提交边界(best-effort)。

目标全貌:**活跃在 Redis、长期在 PG;重开非活跃会话 → PG 冷加载灌回 Redis;不活跃到期 → Redis TTL 淘汰(PG 仍在)**。幂等账本 `agentloop_idem` 也在 PG。

**现状(2026-07-08 核码)**:双写形状已有;**已接**:① 控制边界 B/C path(`audited_store.py`:C-path fail-cold / B-path best-effort)② Redis TTL(`redis_store.py` EXPIRE/PERSIST/refresh_on_read);**未接**:③ PG->Redis 冷加载(丢 Redis 后从审计账本重建热存,属会话子系统/部署);demo/默认跑 `InMemoryConversationStore`。

## 5. plan:派生而非存储

- **全量覆盖**:plan 工具每次提交**整份快照**(覆盖式,非增量),每项带 `status`(todo/doing/done)+ 可选 `result`/`spec`。
- **从日志派生**:`derive_plan` 倒扫日志、取**最近一条** plan 调用即当前 plan(O(1))。所以"当前 plan = 最近一条快照",始终与日志一致。
- **status 由模型自报**:更新 status = 模型重新提交一份全量快照、在里面改写。引擎从不自动改、不推断 status。
- **非权威**:status 是模型自报、可能不准(标 done ≠ 真做完)。所以**关键判定不依赖它**——完成看停手、生效看读回、结果看真实工具输出。plan 只做展示/组织。

**为什么全量覆盖而非增量**:全量让派生平凡(取最后一条即可,引擎不必理解 plan 语义);增量需引擎能 fold(破瘦引擎)、弱模型发增量更易错且错误累积、对丢失更脆;而 plan 很瘦、省的 token 可忽略。日志里连续的全量快照本身就是历史。

## 6. 健壮性:分层设防(防御纵深)

失败发生在三层,各层各管:

| 防什么 | 机制 |
|---|---|
| 等 I/O 时别占线程 | **async**(await 让出;详见 §10 为什么) |
| 下游不回、卡死 | **墙钟超时** `wait_for`(默认 30s,慢工具放宽;**超时零重试**) |
| 模型瞬时抖动(5xx/超时) | **模型调用指数退避重试**(最多 3 次;空响应回滚重试;幻觉工具名合成可恢复错误) |
| 工具瞬时异常(非超时) | **只读重试 1 次**(退避 0.5s);**控制零重试** |
| 逻辑空转(步数在走、任务没进展) | **无进展核查**(三件套):原地踏步 / 光说不做 / 瞎忙活(详见 §6.1) |
| 基础设施连续失败 | **熔断**(failures ≥ max_tool_failures) |
| 无限跑 | **预算闸 + grace 收尾** |
| 工具结果太长撑爆上下文 | **每工具 `output_budget`**(字符上限,写入日志前 `apply` 截断 + "…");与中圈 compaction、模型 max_tokens 分属三层防撑爆 |

**两条关键区分**:
- **超时零重试,瞬时异常只读重试** —— 超时时工具已跑 30s、可能有副作用,盲目重试不安全。
- **业务否 vs 基础设施失败** —— 工具正常跑完返回领域错误(查无设备)= 业务否(给模型看的反馈,**不计熔断**);工具抛异常崩 = 基础设施失败(**计熔断**)。绝不能混,否则误熔断。

**单次工具失败 ≠ 整轮 failed**:它只返回一条 `is_error` 结果,这轮照常提交、继续;模型下轮看到错误自行调整。只有**连续**失败到熔断阈值才整轮 failed。

**三条贯穿取舍**:① 能软着陆就软着陆(失败翻译成模型可见的结果让它自纠,单点不炸全局);② 诚实不假装(停就带 reason,不烧到天花板、不伪装成功);③ 副作用安全压倒自愈(重试只给只读)。

### 6.1 无进展核查(原称"看门狗")

三个机制,本质都是**"步数在消耗、任务却没往前走"就及早止损**——不等预算烧光,发现空转就停,把剩余预算省给后面/父会话。("止损"是用途比喻;触发依据是**无进展信号**而非"亏损额",故定名**无进展核查**。)

| 子项(白话名) | 代码名 | 抓什么 | 处置 |
|---|---|---|---|
| **原地踏步** | stall | 同一调用(名+参数)连续 3 次 | 回滚、failed(reason=stall) |
| **光说不做** | no_progress | 连续只改 plan、不调真工具 | 先 nudge 怼回执行;连续超限(>2)才回滚 failed |
| **瞎忙活** | unproductive | 一直调工具但**结果全没用**(全 业务否/verify-failed/blocked/空) | 连续 3 批回滚 failed |

- **分工互补**:原地踏步抓"同一招重复"、光说不做抓"只规划不动手"、瞎忙活抓"换着花样调但全失败"——前两个都漏的"忙而无果"由瞎忙活兜。
- **"有用结果"判据**:tool 结果**非错误、有内容、且不以 `[blocked]`/`[error]` 开头**。这正是为什么"**失败必须诚实标 ok=False**"是命根子——一旦把失败包装成 ok=True,瞎忙活就失明(查无设备返 ok=True → 看着像"有用" → 空转抓不住 → 烧预算 → 臆造结果)。
- ⚠ **代码小坑**:瞎忙活(unproductive)触发时 `reason` 填的是 `"no_progress"`(不是 `"unproductive"`)。读日志按**文案**区分:"连续多轮无有效结果"=瞎忙活,"连续多轮只更新计划"=光说不做。

### 6.2 模型调用的额度与超时(单次 vs 累计;中间步如何短/快)

**双层超时(在 provider 层,非循环层)**:每次问模型套两层——① `AsyncOpenAI(timeout=...)`(httpx/网络层);② 再用 `asyncio.wait_for(create(...), timeout)` 包一层(providers.py:98/130)。②必要:**httpx 超时管不到事件循环卡死**(vLLM worker 挂死不关连接、连接没断 httpx 干等),用 wait_for 从事件循环层硬掐。超时 → 抛异常 → `_call_model_with_retry` **重试**(当瞬时抖动)——**对比工具超时不重试**(可能有副作用)。

**单次 `max_tokens` vs 累计 `token_budget`(两层、别混)**:
| | 是什么 | 在哪 | 管什么 |
|---|---|---|---|
| `config.max_tokens` | **单次**调用最大输出 | 请求参数(provider,providers.py:117) | 模型这一轮别说太长 |
| `budget.token_budget` | **整 run 累计**预算 | loop 层(consume/exhausted) | 整条会话总量 |

- ⚠ `max_tokens` 是**天花板不是目标**:模型说完自然停,**降它只防失控、不给正常短输出提速**。
- ⚠ **无 `finish_reason=length` 截断检测**(诚实局限):被截断时 harness 不察觉——正文截半原样返回 / tool_call 截断由 `_safe_json` 兜(参数残但不崩)/ 截在没产出 → 落空响应分支重试。

**中间步如何保持短/快**:
- **现状(无显式硬机制,但够快)**:靠 `enable_thinking=False`(默认,**最大杠杆**——中间变慢主因是思考链)+ 提示词约束 + ReAct 结构(中间步=发个工具调用,天然短)。
- **若要硬约束**:难点 = **调用前不知道哪次是"最终答"**(模型靠"停止发工具"才表示收尾)。两条路:① `tool_choice=required` + `finish` 工具 + 收尾**单独大额度**调用(最硬;侵入协议;弱模型需可靠调 finish);② 全程小 `max_tokens` + 检测 `finish_reason=length` 在收尾**升级大额度**(轻;需补截断检测)。要点 = **把"宣布完成"和"生成答案"拆开**(用动作宣布完成,答案另起大额度调用)。
- **行业做法**:**不靠"限中间输出长度",靠"限思考预算"**——Anthropic `thinking.budget_tokens` / OpenAI `reasoning_effort` / Gemini `thinkingBudget` / qwen `enable_thinking`(harness 用的,**关=最激进档**)。`finish`/`tool_choice=required` 那套行业**主要用于可控/弱模型兜底,非速度**。本项目已在主流路径上;再进一步 = 换到支持**分级思考预算**的模型/配置,而非手搓中间步 max_tokens。

## 7. 控制安全:提议-确认-执行 + 挂起恢复

写操作(改设备)不自动下发,走**两段、跨两次 run_loop 调用**,中间用 awaiting 边界做桥:

1. **子起草 / 主提议**:`propose_control`(只读,is_control=False)起草提案,grounding 校验参数/可控/可逆,登记进父子共享的 ProposalStore(按**父会话 id** 切片,故执行方主才取得到)。
2. **撞闸冻结挂起**:主调 `execute_proposal` → gate 判 ask → `control.freeze` 把**要做的动作锁死**进 awaiting 边界 → 本轮提交、return。**此刻设备未动。**
3. **等确认(事务化,隔多久都能重载,除非过期)**。
4. **恢复执行**:`/confirm` → 第二次 run_loop,**重水化 + `budget.restore`(不重置)**→ **模态门**(pending 未决时只收 resolution/cancel,自由文本新意图不穿过)→ 按 approve/reject 调 `control.resolve`(**引擎直接执行那个冻结的动作,不让模型重发**)→ 占位符原位替换成真实结果 → 提交 iteration 边界 → 进正常循环收尾。

**关键安全点**:
- **恢复由引擎执行冻结动作、模型不重新插手** —— 否则模型可能改主意/幻觉成别的动作,"你确认的"≠"它做的"。冻结保证分毫不差。
- **默认拒绝**:resolution 没明确 approve 的一律 reject。
- **一轮可冻结多个提案**:`pending_batch` 是列表——模型一轮发多个控制调用会被**逐个串行冻结、攒进同一个 awaiting 边界**。确认按动作粒度 `{tool_call_id: approve/reject}`(**可部分批准、部分拒绝**),`cancel` = 整批拒。下发仍**串行、各自独立走幂等键/WAL/读回**。
- **读回对账**:执行后读后端确认是否**真生效**(effective),防"已受理≠已生效"假成功。

### 7.1 防重复下发:WAL + 最多一次(at-most-once)

控制有两个硬约束:**不可逆**(做两次无法撤销)+ **后端无 commandId**(发完无法事后查到底执行没)。最坏窗口:**deviceCtrl 已发出、还没等到返回就崩了**——命令到底到没到设备、状态完全未知。盲目重发可能造成二次执行。WAL(写前账本)专门兜这个窗口。

**前提:幂等键确定性派生** `idem_key = hash(handle+action+params)`(非 uuid4)。这样**重启/重入算出的是同一个 key**,才能在账本里查到上次记录;随机 key 会让 WAL 失效。

**两个不同时刻(别混)**:
| 时刻 | 发生什么 | 账本 | 设备 |
|---|---|---|---|
| **挂起(freeze)** | 动作锁死成提案、提交进 awaiting 边界(会话日志) | **还没 in_flight** | 没动 |
| **确认后(resolve)** | 真下发**前一刻**才 `put in_flight`,下发成功再标 `done` | in_flight→done | 此刻才下发 |

> in_flight 标在 **resolve 里、下发前一刻**,不在冻结时。冻结只是把提案存进 awaiting 边界等确认。

**WAL 时序(在 resolve 内)**:① 先查账本(崩溃恢复优先,只读)→ ② 过 F3 门栓(不可逆硬拦)→ ③ **下发前 put in_flight**(写前)→ ④ 下发 deviceCtrl → ⑤ 成功 update `done`(缓存结果)/ 异常 update `failed`(确定没发出,可重试)→ ⑥ pop 提案。
*为什么"写前"*:只要下发动作开始,账本一定先有 in_flight → 崩了重入一定查得到、知道"发到一半了"。

**重入三态分流**(重启/重复确认都走这里):
| 账本状态 | 含义 | 处置 |
|---|---|---|
| `done` | 确定做过了 | **返缓存,绝不重发**(真幂等) |
| `in_flight` | **发了一半就崩,做没做未知** | **不可逆→绝不重发**(返状态未知);可逆→可幂等重试 |
| `failed` | 抛异常、**确定没发出去** | 重发(真"重试") |
| 无记录 | 还没开始下发 | 首次下发 |

> 核心:`in_flight` 语义是**"状态未知"**,不是"没执行"。所以对不可逆操作是**宁可不发**,不是重试。真能放心(重)发的只有 `failed` 和"无记录"。

**in_flight 是一道栅栏,卡在下发动作正前方**:崩在栅栏前(无记录)= 没下发 = 可安全重来;崩在栅栏后(in_flight 无 done)= 发了一半 = 不可逆绝不重发。

**为什么是 at-most-once 而非 exactly-once**:面对 in_flight 的不可逆操作,重发可能二次执行(灾难)、不发可能这次没成(人工重来)——设计坚定选**不发**:宁可"可能没成",绝不"可能做两次"。这就是**最多一次**(保证绝不超过一次,不保证至少一次)。升 exactly-once **硬依赖后端加 commandId**(同 id 只执行一次且可查状态)——明写的诚实边界。

**三层防御各司其职**:前端禁用(挡重复点击,best-effort)→ 幂等键+WAL(挡漏网重发/重入,真保证只一次)→ 读回对账(确认那一次真生效)。

## 8. 子 agent:递归实例(agent-as-tool)

把一个隔离的子 `run_loop` 包成父可调用的工具——"用组织对抗规模"(主面对的候选少,域内多工具 + 消歧打包进子)。

- **隔离**:子有独立会话(uuid thread_id)、独立消息日志、临时 InMem store(不写父)。父只拿回**一条归一化结果**(像函数返回值,不见局部变量)。
- **不持久化(InMem)+ 崩溃即重跑**:子不落 Redis/PG。理由:子**只读、无副作用** → 没有"真实状态"需保护(对照 §3 提交判据);它唯一有价值的**结论**在父提交那轮时已进父的持久日志。崩在子运行中 → 父那轮没提交 → 重启父从上个 checkpoint **重跑、重新调子**,只读重跑安全、代价仅"多查几次"。用"罕见崩溃重跑一遍读"换掉"嵌套恢复"那一大坨复杂度(KISS)。代价诚实:子若又重又长,重跑浪费——属自觉接受的取舍(共享预算池给重跑兜了上限)。
- **共享**:预算池(子迭代消耗父预算,防烧穿)、中断信号(父停→子在下个边界停,整树同停)、身份(子检索按同一用户权限)、会话 id(子起草的提案记父会话,父才执行得到)。
- **结构性只读**:工厂时拒绝子 toolset 含控制工具 + 运行时 control=None 兜底。**因为子临时、不持久化,承载不了控制三支柱(挂起确认/幂等 WAL/读回留痕),所以根本不能做控制**。
- **深度上限 + 权限 ⊆ 父**:防无限递归、防递归提权。
- **结果归一化**:completed→ok+结论;budget_exhausted/failed→ok=False+"未取得可靠结果别臆造"。

### 8.1 工具规模:分层组织,不靠动态检索

**每层 toolset 全量给模型(无动态检索)**:loop 每轮 `registry.schemas(config.toolset)`(loop.py:268)把**整个 `config.toolset` 的 schema 原样发给模型**,不按本轮意图裁剪/检索。但 `config.toolset` ⊊ registry(只发点名的子集,tools.py:53)。

**主/子各持一份 `(toolset+registry)`**:主 = 顶层小集(超域图 ~7-8);子 agent 各带自己更窄的域内工具集(`make_subagent_tool` 收 `sub_config`+`sub_registry`,且**结构性只读**=工厂拒 is_control)。所以**没有任何一次调用看到"全部工具"**——规模靠**分层组织(用组织对抗规模)**,而非动态工具检索。

**何时才需要上"工具检索"**(触发信号):① 工具多且**不成簇**(切不出干净的域);② 工具**运行时才知道 / 开放可扩展**(没法预编排层级,**最硬触发**);③ **实测**单层因相似工具太多而选错;④ 长尾工具污染每次调用。在那之前,检索是过早优化,且自带**召回风险**(漏召回 = 能力对模型隐形、任务做不了);分层无此风险(层内永远可见)。

**行业五档(规模递增)**:
| 档 | 做法 | 代表 |
|---|---|---|
| ① 静态分组/命名空间 | 手配 toolset、启停 MCP | GitHub MCP toolsets(**=本项目**) |
| ② 分层 / 多 agent | 编排 + 子 agent 各带 toolset | Anthropic 多 agent、OpenAI handoffs、CrewAI(**=本项目**) |
| ③ 工具检索 / RAG over tools | embed + 按 query 取 top-k | LangChain、LlamaIndex `ObjectIndex`、Gorilla/ToolLLM |
| ④ 渐进式披露 | 给搜索元工具,按需 load schema | Anthropic "Tool Search Tool" |
| ⑤ 代码执行 / tools-as-code | 工具当代码库,模型写代码按需调 | CodeAct、smolagents、Anthropic code-exec-with-MCP |

**本项目在 ①②**(已知可编排域 + 强治理,控制安全要边界硬)。扩到开放/海量工具才往 ③→④→⑤ 走。**④⑤ 与"用组织对抗规模"同哲学**(都不全量塞 schema),区别 = **设计时编排(分层)** vs **运行时发现(搜/代码)**。

> 注:工具规模/检索策略与**工具子系统(agent_tools)**治理相关;此处只记内圈侧事实(toolset 全量 per 层 + 分层不检索)与选型判据。

## 9. 并发与中断

- **并发**:一轮内只读工具(allow)用 `asyncio.gather` **并发**跑、**按原调用顺序回填**(保序);控制工具(ask)**串行冻结**,绝不并发(防并发下发危险操作)。
- **中断(两挡)**:
  - **温和停**(协作式):置 `RunControl` 标志,引擎**只在安全点查**(每轮顶部 = 无在途、直接干净退;工具批后 = 有在途、回滚本轮)。绝不在工具执行到一半硬切——**当前工具会先跑完(或到超时)**,所以延迟≈当前工具时延(读类通常 1~2s)。
  - **硬打断**(`asyncio` task.cancel):调用方直接 cancel run_loop 协程,正在 await 的工具**当场中断 → 即时**,用于**语音 barge-in**。当前轮没提交过 → 等于没发生、回到上次 checkpoint(读类无害;若崩在控制下发中,由 §7.1 WAL 兜)。
  - 选用:**显式停止键 / 收尾**走温和停;**说话抢断**走硬打断。两挡都在,策略(新输入是排队还是抢断)由产品层按模态定。
  - 子 agent 共享父的同一信号 → **整棵调用树同停**。

### 9.1 硬打断的安全性:cancel ≈ crash,落在 await 点、复用同一套地基

**两挡共用同一地基:"未提交=未发生" + WAL。** 区别只在"何时停",不在"停后怎么清理"——所以引擎**不需要**为即时打断写专门的清理逻辑。

**对引擎而言,`task.cancel` ≈ crash 同一类**:都是"一个**没提交完的轮**被丢弃"。cancel 的 CancelledError **只落在当前挂起的 await 点**(Python 只在挂起点投递);两个 await 之间是**同步代码,切不断** → 内存记账(append 消息、构造 Boundary、`del` 回滚)**不会被从中间切断**,不会出现"Boundary 建一半"的脏态。

**一轮的 await 点 + cancel 落在各处谁兜**:
| await 点 | 位置 | 落此处谁兜 |
|---|---|---|
| **问模型**(最久,cancel 最常落这) | `_call_model_with_retry`(loop.py:267) | 本轮未提交 → 丢弃,干净 |
| **工具执行**(调后端) | `wait_for(tool.handler)`(dispatch.py:93) | 读类:无副作用干净;**控制类:WAL in_flight 兜** |
| 并发汇合 | `asyncio.gather`(loop.py:406) | 同上 |
| verify / 压缩 | loop.py:394 / 246 | 本轮未提交 → 丢弃 |
| **提交** | `_safe_commit`(loop.py:253…467) | 写库写一半 → **torn tail 丢弃**(load 只到最后完整 Boundary) |

**结论**:cancel 现实中几乎总落在"问模型"或"调工具"。无论落哪——**要么本轮没提交(等于没发生)、要么落在控制下发由 WAL 兜、要么落在写库由 torn-tail 兜**——三类落点都有现成保护。**即时停之所以既即时又安全,不是因为它小心地停在某处,而是事务边界 + WAL 早把"半拉子"全兜住了。**

## 10. 为什么用异步;怎么不卡

内圈几乎全是**等 I/O**(模型/工具/检索/存储)。async 让"等的时候不占线程",撑高并发 + 天然支持一轮内并发。但 **async 不防卡死**——四件事各管一类:

- **async**:等 I/O 时让出 → 撑并发;
- **超时**:下游不回 → 到点强制中断(async 不管这个,必须自己加);
- **无进展核查/熔断/预算**:逻辑空转/无限转 → 有界、必然终止;
- **事务化(每轮 checkpoint)**:逐步完成 + 可续 → 做一步存一步,卡了从最近档接上。

⚠ 工程坑:同步阻塞代码(重 CPU / 阻塞 HTTP 库)混进协程会卡死整个事件循环 → 这类活要丢线程池(`asyncio.to_thread`)。

## 11. 接缝架构 + 可测性

`run_loop` 本体只是**事务循环骨架**;所有政策/治理/IO 是从外面注入的**接缝(Protocol)**,引擎只认协议不认实现:

| 接缝 | 职责 |
|---|---|
| `model_caller` | 问模型(假模型 / 真 qwen) |
| `gate` | allow/ask/deny 权限闸 |
| `control` | 控制 freeze/resolve |
| `verifier` | business_ok 校验("已受理≠已生效") |
| `assembler` | 组装上下文(=中圈) |
| `compaction` | 超阈压缩 |
| `store` | 持久化(InMem / Redis+PG) |
| `run_control` / `budget` / `registry` | 中断 / 预算池 / 工具集 |

买来三件事:**① 可测**(全换 Fake → 引擎确定性 → engine 套实测 16/16 绿;能测的根因是"所有接缝都可换",且 ②问模型 是唯一非确定点);**② 换治理不动循环**(换权限/控制/上下文/存储,循环本体一行不改 = 事务核心 + 可插拔治理);**③ 关注点分离**(引擎管怎么推进,接缝管政策)。

## 附:关键不变量

- 一轮 = 一个事务:整轮提交或整轮回滚,持久日志无脏边界。
- 完成 = 模型停手(行为),与 plan 状态无关。
- 提交/回滚判据 = 有无需保留/恢复的真实状态,不是成败。
- 写操作:提议→冻结→确认→引擎执行(不重插手)+ at-most-once + 读回对账。
- 子 agent:隔离上下文、共享预算/中断/身份、结构性只读、权限 ⊆ 父。
- 唯一非确定点 = 问模型 → 全接缝可换 → 确定性可测。

## 附:诚实边界(设计就绪、未接/待办)
- 持久化:控制边界 B/C path + Redis TTL **已接**;PG->Redis 冷加载未接(会话子系统/部署);默认 InMem。
- 控制:exactly-once 需后端 commandId(当前 at-most-once);读回对账依赖后端可读真实状态。
- 模型调用:单次 `max_tokens` 与累计 `token_budget` 共存,但**无单步自适应额度、无 `finish_reason=length` 截断检测/续写**;中间步保持短/快靠 `enable_thinking=False`+提示词(无硬机制)。要硬约束/分级思考预算需换支持的模型或加 finish-tool 协议(详见 §6.2)。
- 评测:engine 套(16 绿)在桌面,待纳入 repo CI。

## 附:四个情境推演(实战自检)
用真实会发生的情况验证机制是否兜得住。

**① 查询工具调后端、后端 hang 住 40s**
不会卡死、且等不到 40s:执行器 `wait_for(30s)` **到点强制掐断**那条工具 → 返回一条 `is_error` 结果(超时**不重试**)→ **这轮照常提交、继续** → 下轮模型看到"工具超时"自行换查法。单次超时**不**让整轮 failed;只有连续失败到熔断才停。

**② 挂起时用户改口问别的**(没确认、没取消)
**模态门**在 run_loop 入口(主循环之前)拦住:`awaiting + 无 resolution + 无 cancel` → 直接 return 维持挂起、把 pending 再抛回前端 → **模型这轮根本没被调用,新指令不处理**。要查新东西,得先对挂起操作**确认或显式取消**。("提醒"是前端拿到 awaiting 重弹卡,不是模型回应。)

**③ 确认卡被点两次 / `/confirm` 重发**
三层兜:前端点一次即禁用(挡绝大多数)→ 幂等键+WAL(同 key 查到 `done`→返缓存不重发,真保证只一次)→ 读回确认那次真生效。**防重复是幂等键的活,读回只验结果**。

**④ 多步任务跑到第 3 轮进程崩了**
重启后 `load()` **只重建到最后一个 Boundary**(第 2 轮 checkpoint)、第 3 轮的撕裂尾静默丢弃;前两轮成果在(已提交);`budget.restore` 预算也回到第 2 轮(不白送)。续跑由**下一个请求触发**(非进程自愈)。
*特例*:若第 3 轮正崩在**控制下发中**,会话日志丢半截、但真实副作用可能已发生 → 靠 WAL 的 in_flight(§7.1)兜:不可逆绝不重发。
> 与运行时中断的区别:**中断 = 引擎主动 `del` 在途消息**;**崩溃 = load 时丢弃 torn tail**。殊途同归(回到最后 checkpoint),机制不同。
