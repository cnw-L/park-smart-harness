# 园区数字人 · 语音管线设计(对接既有实时协议)

> 研究收敛后的设计文档。**语音管线 = 给既有实时协议加一条 Phase 2 媒体侧管线**,不是重造编排。

## 0. 核心认知(一句话)

> 你的实时协议(主WS `/app/realtime/ws` + Product Gateway + AI Runtime + run/工具/票据/事件)**已经是完整的编排层**。
> **语音管线只是 Phase 2 的"媒体侧桥"**:音频 ↔ ASR/TTS + VAD/打断,对接协议的 `media_session / asr.* / tts.* / barge_in`,**与大脑(现为 `agent_runtime` 包)完全解耦**——契约一样,大脑是谁透明,因为"所有输入最后都归一成 run"。

## 1. 选型结论(含反转记录)

| | 决定 | 理由 |
|---|---|---|
| ✗ **不用 Pipecat** | 否 | 编排已在协议侧 → 框架被掏空(LLM 不在管线里),还和协议的 barge_in/run.cancel 打架(两套编排) |
| ✗ **不用 LiveKit / 不以 WebRTC 为基线** | 否 | **微信小程序做不了标准 WebRTC**;WebSocket 是网页/App/小程序三端唯一公约数 |
| ✓ **FunASR 2pass + CosyVoice 原生 + 薄胶水** | 是 | 你的 6011/6012/6014 就是它们;原生输出与协议 `asr.*/tts.*` 字段几乎 1:1;胶水仅几百行 |

**反转记录(诚实留痕)**:研究早期选过 Pipecat,前提是"Pipecat=编排底座"。协议文档揭示**编排已存在** → 前提没了 → 工程上改选原生+薄胶水。教训:框架的价值是编排,编排外置后框架成负担。

## 2. 架构(语音管线的位置)

```
网页PC / 手机App / 微信小程序
  ├─ 主 WS  /app/realtime/ws ─→ 控制/run/工具/票据/ASR文本/TTS状态 ─→ 既有 Product Gateway + AI Runtime(不动)
  └─ media WS(基线) ──────────→ 音频 binary
                                      ↕
                          ┌──────────────────────────────┐
                          │  语音管线(本文设计,薄胶水)      │
                          │  上行:归一化16k→VAD→FunASR2pass │ → asr.partial / asr.final(+transcript_id)
                          │  下行:订message.delta→聚合+清洗  │ ← message.delta
                          │       →CosyVoice stream→音频     │ → tts.segment + 音频帧
                          │  打断:barge_in→run.cancel        │
                          └──────────────────────────────┘
保留不动:run 编排 / RAG / 工具 / 票据 / 三个模型服务(6011/6012/6014)
```

## 3. 传输原则:传输无关 + 分层可选(地基)

> 部署形态会变(办公PC / 手机App / 小程序 / 也许将来公共kiosk)。设计**不替它拍死一种传输**,而是:

- **双 WS 基线(主WS + media WS)= 协议强制,必做**,不是选择题;
- **media WS = 基线传输**(三端通吃);语音管线**对接 `media_session` 抽象**,传输是谁与它无关(协议的 `media_session.transport` 可协商);
- **重特性全做成可选层、留开关,按需才实现**(否则过度工程):

| 可选层 | 何时启用 | 备注 |
|---|---|---|
| WebRTC 传输 | 原生 App + 弱网 | 小程序永远走 WS;不用 LiveKit 则手搓 aiortc(重) |
| 后端 AEC | 公共外放场景 | 办公/耳机场景靠浏览器 AEC 即可 |
| cam++ 说话人过滤 | 公共多人场景 | 单用户客户端不需要 |

## 3.5 协议契约钉死(实读 app-realtime-protocol.md §15 / §6.7-6.10,2026-06-18)

**media_session.create**(主WS):
```
transport: "ws"(WebRTC 只改这个+token,不改事件模型)
audio_in : codec pcm_s16le / 16000 / 1ch / frame 20ms   ← 上行=16k裸PCM,20ms帧
audio_out: codec opus / 24000 / 1ch                       ← 下行=Opus 24k(!)
options  : vad_mode="server" / barge_in=true / auto_run_on_final=true
```
**media WS 帧协议**:media_session.create →(主WS)media_session.created{media_ws_url, media_token, input_lease}→ 连 /app/media/ws → media.hello{tracks:[audio_in...]} → media.accepted → 双向 binary 帧。**音频帧不进 AppEvent**。`media_token` 绑 `allowed_publish:[audio_in]` / `allowed_subscribe:[audio_out,tts_audio]` + input_lease(麦输入权,单 owner)。

**事件精确 schema**:
```
asr.partial : {text, confidence}
asr.final   : {transcript_id(服务端签发), text, start_ms, end_ms}
tts.segment : {tts_segment_id, track:"tts_audio", text(字幕), start_ms, end_ms, status}
音频binary  : 走 media track tts_audio / audio_out(不在 AppEvent 里)
promotion   : auto_run_on_final=true → 幂等键 tenant_id+conversation_id+media_session_id+transcript_id → run.create
```

**二进制帧格式**(媒体 WS,§15.1):
```
[4 bytes BE header_length][header_length bytes UTF-8 JSON header][media payload]
header: {v, media_session_id, track, frame_id, seq, timestamp_ms, duration_ms,
         codec, sample_rate, channels, flags:{commit,end,key_frame}}
规则:seq 在 media_session+track 内单调;timestamp_ms=媒体时钟;v1 语音帧 20ms;
     max_frame_bytes(见 media.accepted,如6400);音频帧不进 AppEvent。
```
**媒体控制消息**(媒体 WS):
```
media.commit  → 提交输入缓冲,要 ASR 尽快出 final(等价 flags.commit=true)
media.clear   → 清空未提交缓冲,【用于 barge-in / 用户取消说话】← 前端发起打断的入口!
media.backpressure → 服务端要前端降速/暂停上行(缓冲高)
media.close / media.closed
```
**barge-in 处理链**(§15.1):
```
① 服务端 VAD 检测到开口  或  ② 前端发 media.clear
  → 主WS barge_in.detected → 停下行 tts → tts.cancelled
  → run.cancelling → message.cancelled → run.cancelled
  → 新 asr.final 按 auto_run_on_final 创建新 run(新 run_id,可引用 previous_run_id)
注:barge-in 不能取消已进 operation_ticket.executing 的真实操作。
```
**WebRTC/LiveKit**:仅改 `media_session.transport`(带 signaling/room/token),主事件模型不变。

**v1 实现边界(关键)**:`tts.segment` / `barge_in.detected` / `media_session.connected` / `avatar.*` **是预留、v1 可不实现**。v1 必做:asr.partial/final、tts.started/completed/cancelled、media_session.created/closed。

### ⚠️ 三个 refinement(改了之前设计)
1. **下行要加 Opus 24k 编码**:audio_out 是 Opus/24k。CosyVoice 出 24k PCM → **编码成 Opus 24k** 再走 media track。块② 多一步编码。
2. **打断走"双触发":服务端 VAD(默认)+ 前端 media.clear(可选先行)**。`vad_mode="server"` 是默认检测路径(切句/barge-in 在语音管线);**但协议的 barge-in 链第①②条明确:"服务端 VAD 检测开口 *或* 前端发 media.clear" 都能触发**。所以我 §5 教的"前端 VAD 先行"**没被否,而是接回来了**——前端本地探到开口 → 发 `media.clear` + 本地停播,服务端走 barge-in 链。**baseline=服务端 VAD;前端 media.clear 先行=可选加速层(留开关)。** 切句的 final 也有双触发:服务端 VAD,或前端 `flags.commit/media.commit`。
3. **§1 归一化 = media WS 入口的格式校验**:协议规定上行"必须校验格式、采样率、单帧大小"。前端理论上已按 audio_in 发 16k PCM;media WS 入口仍要校验/兜底(我们 §1 的关卡二落在这)。

## 4. 块① 上行设计:音频 → asr.final

```
media WS 音频帧
  ① 解码 + 归一化到 16k        ← §1 "后端兜底归一化"落地点(前端给啥都救)
  ② FunASR fsmn-vad 切句        ← 标准做法自带,出 speech_start/end
  ③ FunASR 2pass:
       6011 流式 → partial      ──映射──→ 主WS asr.partial
       6012 整句 → final(speech_end触发)──→ 主WS asr.final + 签发 transcript_id
  ④ 协议 promotion:asr.final → 幂等 run.create
```

**FunASR 原生 → 协议字段映射(薄胶水核心)**:

| FunASR 2pass 原生 | 协议事件 | 备注 |
|---|---|---|
| `partial` | `asr.partial` | 实时、会变 |
| `sentences[]`(speech_end 锁定) | `asr.final` | 管线签发 `transcript_id` |
| fsmn-vad speech_end | 触发 asr.final + run promotion | 切句引爆点 |
| `spk` 标签(cam++,可选层) | 旁人音过滤 | 仅公共多人场景启用 |

**胶水只干**:① 归一化16k ② FunASR输出→asr.*字段映射 ③ 签发transcript_id ④(可选)主spk过滤。识别/切句逻辑全靠 FunASR runtime。

## 5. 块② 下行设计:message 流 → 音频

```
订阅主WS message.delta(大脑吐的文本流)
  ① 句子聚合(token_buffer:标点 + 字数兜底200)   ← §4,可抄 OpenAvatarChat
  ② 文本清洗(自建:去 markdown/emoji/符号)        ← P0!连 OpenAvatarChat 都缺,必须自写
  ③ CosyVoice stream=True 流式合成 + spk2info_cache ← 收几字出chunk;固定音色白送提速
       音频块 ──→ media WS(下行音频)
       状态   ──→ 主WS tts.started / tts.segment / tts.completed
```

**CosyVoice 原生 → 协议字段映射**:

| CosyVoice 原生 | 协议事件 | 备注 |
|---|---|---|
| `inference_*(stream=True)` chunk | media WS 音频帧 + 主WS `tts.segment` | 边合成边出 |
| 合成开始/结束 | `tts.started` / `tts.completed` | |
| 中止 | `tts.cancelled` | 接块③ |

**关键对接点**:订的是大脑**通过协议吐的 `message.delta`**,不是直连大脑 → 传输/大脑无关原则在下行同样成立。
**胶水只干**:① 聚合(抄 token_buffer)② 清洗(自写,P0)③ chunk→media音频帧+tts.segment 映射。

## 6. 块③ 打断设计:barge_in → run.cancel

**协议已定义的打断流**(runtime-logic §10):
```
用户开口 → barge_in.detected → 停 tts 下行 → tts.cancelled
        → run.cancelling → message.cancelled → run.cancelled
        → 新 asr.final 再 promotion 成新 run
```

**§5 三铁律在协议上的落地**:

**⚠️ 协议选了服务端 VAD(`vad_mode="server"`),打断检测在语音管线、不在前端**,所以三铁律的落地和理论略有出入:

| 铁律(理论) | 协议落地(vad_mode=server) |
|---|---|
| 1. 前端 VAD 先行、本地停播 | **双触发**:baseline=服务端 VAD(语音管线)检测 barge-in;可选=前端探到开口发 `media.clear` + 本地停播(§5 先行接回来了)。两条都进协议 barge-in 链 → 停 tts → `tts.cancelled` → 前端停播 |
| 2. 信令/音频双路径,信号不被音频堵 | **天然满足**:控制走主WS、音频走 media WS,本就分离 |
| 3. LLM/TTS 可取消 | 打断 = `run.cancel`(协议机制);TTS→`tts.cancelled`。**但大脑 `agent_runtime` 的工具/RAG 阻塞步骤要埋 await/检查点才能真停** |

> 注:v1 里 `barge_in.detected` 是预留事件(可不发);服务端 VAD 检测到打断后,直接走 `run.cancel → run.cancelling → message.cancelled → run.cancelled` + `tts.cancelled`,前端据此停播。

**可取消的分层(我们讨论的收敛)**:
- **说话时打断**(纯 message 流式输出阶段):"丢弃流"就够,大脑工具不用埋 await;
- **思考/查询时打断**(run_loop 正调工具/RAG):那些是阻塞步骤、没流可丢 → 工具需可 cancel(埋 await/检查点)。园区"查到一半改主意"会发生,**该埋还是要埋**;
- **设备确认红线**(`operation_ticket.awaiting_confirmation`):天然可打断暂停,用户说"取消"走 `operation_ticket.cancel`,无需特殊机制。

## 9. 一页纸总结

> **语音管线 = 媒体侧薄胶水,把"音频"翻译成你协议的事件、再翻译回"音频"。**
> 上行:归一化16k → FunASR 2pass → asr.partial/final。
> 下行:订 message.delta → 聚合+清洗 → CosyVoice stream → tts.segment+音频。
> 打断:barge_in → run.cancel(双路径天然满足;大脑工具按需埋可取消)。
> 传输:双WS基线、media WS通吃;WebRTC/AEC/cam++ 是可选层留开关。
> 不用 Pipecat、不用 LiveKit;FunASR/CosyVoice 原生 + 薄胶水。
