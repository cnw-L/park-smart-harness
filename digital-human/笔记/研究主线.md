## ① 上行:听懂(VAD + 2pass) — 文档 §3

### 文档理论
双模型 2pass:Paraformer-streaming 全程出 partial(快),SenseVoice 在 speech_end 对整句出 final(准),final **单向覆盖** partial;靠 `cache={}` 滚动状态;`chunk_size=[0,10,5]` 是延迟/精度旋钮;`is_final=True` 补刀防吞尾字。

### 代码核对
- ⚠️ **没有一个参考仓做"双模型 2pass"**:
  - **OAC** `asr/sensevoice/asr_handler_sensevoice.py:122-148`:**只用 SenseVoice**,在 `is_last_data`(speech_end)把整句音频 `model.generate` 一次出 final,**无流式 partial**。partial 的即时反馈在 OAC 里不存在(端点判定交给 silero-VAD handler)。`re.sub(r"<\|.*?\|>", "", ...)` 剥 SenseVoice 的情感/事件标签。
  - **FunSpeech** `app/services/websocket_asr.py`:**单个 Paraformer-streaming**,partial 和 final 来自**同一模型**——中间结果是流式输出(`:530` TranscriptionResultChanged),final 靠句末 `is_final=True` flush(`:417-425`)+ 离线标点。
- ✅ **`chunk_size` 旋钮印证**:`websocket_asr.py:703` `chunk_size = [0, chunk_stride, 5]`,stride∈{4,10}(240ms/600ms 两档),精确对应文档 §3.5 的 `[0,10,5]` 形态与"右5=前看"。
- ✅ **is_final 补刀印证**:`websocket_asr.py:409-425` 句子结束时再调一次 `is_final=True` flush 模型缓存,正是文档 §3.5"防 partial 吞尾字"。
- ✅ **cache 按句清印证**:`websocket_asr.py:478-480` SentenceEnd 后 `audio_cache = {}; punc_cache = {}`,对应文档"清 cache=一句从头"+ §6.5"连接级≠状态级生命周期"。
- ✅ **speech_end 多触发源**:连续空结果计数(`:387-396`,由 `max_sentence_silence` 推算)/ 静音帧(`:400-407`)/ StopTranscription——对应文档 §3.3"speech_end 引爆点"。
- ✅ **ITN 印证**:`websocket_asr.py:928` + `utils/text_processing.py` 用 wetext 做中文 ITN(文档 §17.3)。
- ✅ **空结果拦截印证**:OAC `asr_handler_sensevoice.py:144` `if len(output_text)==0: return`(文档 §11.2 空结果最高频,送 LLM 前拦截)。

> **你自己的部署(6011 Paraformer 流式 + 6012 SenseVoice 整句双模型)比这两个参考仓更"教科书 2pass"。** 参考仓走了"单模型"捷径——OAC 牺牲 partial 换简单,FunSpeech 用同模型 is_final 兼顾。你的双模型方案对标的是文档理论本身,不是这些仓。精读 FunSpeech 句子机的价值在它的**句子状态管理/去重/标点双轨**,不在它的模型架构。

## ③ 打断:双工核心 — 文档 §5(命门)

### 文档理论
前端 VAD 先行本地停播(不等后端);**打断信号走优先级/独立通道,绝不被音频堵**(否则慢 3-5s);LLM/TTS 必须是**可取消异步 task**;后端 cancel + 清队列 + 状态切回。三条解法:逻辑优先级队列(单WS可做)/ 双WS物理分离 / WebRTC天然分离。

### 代码核对(OAC 单 WS 的双工实现 = 本轮最大收获)
- ✅✅ **"纯 WebSocket 能否复刻双工"——能。** `ws_input_delegate.py:1654-1661` `_serve_primary_connection` 并发起 6 个协程,**每通道独立 asyncio 队列**:
  - `_ws_audio_output_task`(AUDIO 队列)/ `_ws_text_output_task`(TEXT)/ `_ws_motion_output_task`(MOTION)/ **`_ws_signal_output_task`(独立 `signal_to_client_queue`)** / `_ws_input_task`(收) / 心跳。
  - 信号有**自己的队列**,不排在音频 FIFO 之后 → 这就是文档 §5.2 的"**逻辑优先级队列(单WS也能做)**"。仅在 `websocket_send_lock`(`:214`)上做单条消息级互斥,阻塞有界(一条消息),不会 3-5s。
- ✅ **上行打断不被堵的根因**:client→server 的 `Interrupt` 是 JSON 文本,在收包循环 `_ws_input_task:1345` **即时处理** → `_handle_interrupt:1211` 立刻 `emit_signal(INTERRUPT)` 给引擎 + 回 `InterruptAccepted`。收/发是 TCP 全双工两个方向,天然不互堵。
- ✅ **可取消 = stream 依赖图级联**:`_handle_avatar_audio_cancel_signal:1251` 注释写明链路 `cancel_streams_by_type(CLIENT_PLAYBACK) → cancel_stream_chain → AVATAR_AUDIO.cancel() → STREAM_CANCEL 信号`。对应文档 §5.2 要点2"cancel 异步 task"。
- ✅ **取消已排期未播块(文档最易漏)**:`_cancelled_stream_keys` 集合(`:222`)+ 发送前幂等拦截(`:1039-1041` / `:946-948`)→ 已标记取消的 stream 直接 skip 不发。对应文档"取消所有已排期未播的块"。
- ✅ **清后端音频缓冲**:打断时 `_opus_encoder.reset()`(`:1216` / `:334`)清残留编码缓冲。
- ✅ **两类打断来源分流**:CLIENT 发起(用户点/前端VAD)走 `_handle_interrupt`;HANDLER 发起(SemanticTurnDetector 语义打断)走 `_handle_server_interrupt_signal:1235` + `InterruptNotification` 通知前端。`reason` 区分 `user_interrupt` / `semantic_interrupt`(`ws_message_protocol.py:240`)。
- ✅ **防回环细节**:`:1584` CLIENT 来源的 INTERRUPT 不回发给客户端,避免无限循环——工程踩坑点。

## ⑨ 误打断判定 + 轮次检测 — 文档 §3.2 / §9(深水区,已贯通 2026-06-17)

OAC 用**两个检测器、两个层级**落地,加上 VAD 共**三层**(超过文档说的两层):

### 第一层 SmartTurnEOU(声学 EOU,轻量)— `vad/smart_turn_eou/eou_handler_smart_turn.py`
- 旁路监听 HUMAN_AUDIO(`input_priority=100`,不消费不阻断 ASR);模型 `smart-turn-v3.1-cpu.onnx`+Whisper 特征,取**最后 8 秒**跑 sigmoid 出"说完概率"(阈值 0.5)。
- 触发:收 VAD 的 `EVT_EARLY_VAD_END` → 判"完成"→ emit **candidate STREAM_END**(`:261`)→ VAD 的 `candidate_end_received` 来源 → 提前结束。
- ✅ 纯声学韵律判 EOU,CPU 可跑,= 文档 §3.2 轮次检测轻量版。

### 第二层 SemanticTurnDetector(LLM 语义,重)— `llm/semantic_turn_detector/semantic_turn_detector_handler.py`
三种 LLM 判断:
- **完成检测**(COMPLETION_PROMPT):未完→`SEMANTIC_WAIT`(延 VAD 不腰斩);完成→submit HUMAN_TEXT。
- **打断检测**(INTERRUPT_PROMPT):数字人说话时插话想打断吗?→`INTERRUPT`。
- **打断意图**(INTERRUPT_INTENT_PROMPT):pure_interrupt vs has_new_topic → 决定打断后要不要把这句当 HUMAN_TEXT 送主 LLM。
- ✅ **级联过滤(文档 §9.6)**:① 启发式 `_is_pure_stop_command:863` 中英停止词表 fast path 不调 LLM(=§9.5 关键词表);② 两 LLM 并行(`:651`)打断一确认立即发不等意图;③ `avatar_was_speaking_at_stream_start` 门控,没在说话 skip。
- ✅ **附和词处理(文档 §9.5)**:INTERRUPT_PROMPT 第4条"嗯/哦/uh/um→不打断",**语义**区分真打断 vs back-channel。
- ✅ **冷却** interrupt_cooldown=1.0s 防抖。
- emit INTERRUPT 后由 InterruptHandler 执行取消(决策/执行解耦,`:989`)。

### ⚠️ 关键分歧:语义路线 vs 声纹路线
- 文档 §9.3/§9.7 主张 **pVAD 声纹认主人**;**OAC 没有 pVAD**,用 `avatar_was_speaking_at_stream_start` 上下文 + LLM 文本语义替代。
- FireRedChat 才走声纹 pVAD 路线(`livekit-plugins-fireredchat-pvad`)。
- → 两流派:**OAC=语义(LLM判内容,能区分附和,无需声纹注册)/ FireRedChat=声纹(判是不是主人)**。园区场景语义路线可能更省事(免注册)。

### ⚠️ 修正 ① 的"无 partial":duplex 模式有 partial ASR
单工主链确实无 partial;但 duplex 下有专门通路(`semantic_turn_detector:294`):数字人说话时用户开口 → 累积音频发 `HUMAN_DUPLEX_AUDIO_PARTIAL` → partial ASR → `HUMAN_DUPLEX_TEXT_PARTIAL` 拿去做打断检测。**partial 只为快速打断判断,非用户字幕。**

### 完整协作图(5 handler)

## ④ 状态机:焊死系统 — 文档 §6 / §11

### 文档理论
每状态各模块工作态;转换时清残留;连接级≠状态级生命周期;真实状态机要补异常(空结果/超时/打断未遂)。

### 代码核对
- ✅ **OAC 引擎级 signal/stream 双管线**:`chat_engine/core/` 把**控制(signal_manager/signal_filter)与数据(stream_manager/stream_filter)分成两套**。`ChatSignalType`(`data_models/chat_signal_type.py`)枚举 = 状态转换事件总线:`SESSION_START / STREAM_BEGIN / STREAM_END / STREAM_CANCEL / INTERRUPT / SEMANTIC_WAIT / ENVIRONMENT_EVENT / SESSION_STOP`。
  - `SEMANTIC_WAIT`(`:13`)= 文档 §3.2 轮次检测"语义没说完,请求延长等待"——引擎内建了!
  - `ENVIRONMENT_EVENT`(`:15`)= Agent 主动事件(超出文档范围,是 agentic 扩展)。
- ✅ **FunSpeech 句子级状态机**:`websocket_asr.py:55` `ConnectionState{READY,STARTED,COMPLETED}` + `sentence_active` 标志,转换时清 cache/buffer(`:472-480`)。是文档 §6 的最小可读样本。
- ✅ **超时/心跳出口**(文档 §11.3"每状态都要超时出口"):OAC `connection_ttl=900s`(`ws_client_handler.py:34`)+ `heartbeat_timeout=30s` + `_heartbeat_monitor_task:1505`。
- ✅ **异常拦截**:空结果拦截(① 已述);打断未遂续接见 FireRedChat `resume_interrupted_agent.py`。

### ⚠️⚠️ 颠覆性发现:OAC 没有文档式状态机(2026-06-17 读 chat_session+stream_manager)
`chat_session.py` 全程**无 IDLE/LISTENING/THINKING/SPEAKING**。真实骨架 = **数据流管线 + 流依赖图 + 信号总线**:
- **每 handler = 一个 pump 线程**(`:342` `handler_pumper`),从输入队列拉 → `handle()` → 提交输出。
- **handler 靠数据类型连接**:声明 inputs 类型→注册成该类型 DataSink;输出→streamer→路由到匹配 sink。= 文档 §8.1"插线板"的字面实现(孔对孔按类型转发)。
- **"状态"是涌现的/分布的**,无中央状态机。文档 §6.2"状态×模块工作态"表 = OAC 里"哪些 handler 队列此刻有数据在流"的自然结果。
- → **重要分歧:文档把状态机当骨架;OAC 骨架是 dataflow+stream图,状态机被流生命周期取代。** 你项目若建在 dataflow 引擎上,"状态"是涌现的;若想简单,显式 FSM 反而更清晰——这是地基选型决策。

### cancel 级联引擎机制(③④ 内核,stream_manager.py)
- 流构成生产依赖图 `LLM流→TTS流→AVATAR_AUDIO流→CLIENT_PLAYBACK流`(`source_streams`/`ancestor_streams` 指上游,`ref_by` 记下游)。
- `cancel_streams_by_type(CLIENT_PLAYBACK)`(`:994`)→ 每活跃播放流 `cancel_stream_chain`(`:959`)→ **向上**取消 cancelable 祖先(=AVATAR_AUDIO/TTS/LLM)+ 目标流必取消;每流发 STREAM_CANCEL,`forward_cancel_signal` **向下**级联 ref_by。**一次打断双向传播:向上杀生产链、向下通知前端停播。**
- `cancelable` 标志定谁被链式杀:MIC_AUDIO/CLIENT_PLAYBACK 建流 `cancelable=False`,LLM/TTS/AVATAR_AUDIO 默认 True。
- `recycle_ttl=10s`(`:881`)结束流留 10s 供下游建依赖+cancel 够到已结束但被引用的流;stream_key 用时间戳基址(`:894`)防重连复用旧 key 致前端丢新音频。

### 文档"转换时清理"等价 = 两层 cancel 拦截(防上句污染下句,文档 §6.5)
不靠清 cache,靠丢弃被取消流的数据:① 生产侧 `stream_data()` 挡新数据;② 消费侧 pump 循环 `:83-88` 处理前查流状态,CANCELLED 就 `continue` 跳过(残留数据已在队列也拦住)。

### 其它引擎级好设计
- ✅ **异常隔离**(`:131-140`):handle() 包 try/except,单 handler 崩不拖垮 pump 线程 = 文档 §11 失败分支。
- ✅ **自动历史**(`:90-169`):STREAM_BEGIN/END 自动记 session_history,流式文本按 chunk 累积 = 多轮记忆(§18.1)内建引擎。
- ✅ **类型重映射**(input/output_type_override):config 改 handler 声明类型 → 同一 SemanticTurnDetector 单工接 HUMAN_TEXT/双工接 HUMAN_DUPLEX_TEXT 不改代码。
- ✅ **信号总线**(signal_manager.py):独立线程按 `(type,source_type,stream_type)` 过滤分发给 listener = 各 handler signal_filters 接收端;替代文档的"状态转换事件"。

### 精读顺序

2. `OAC/src/chat_engine/core/stream_manager.py`(流依赖图+cancel级联,已读重点)

## §1-2 基础认知:PCM + 上传演进(理论×OAC,2026-06-17)

- ✅ **PCM 格式贴合 §1.1**:OAC 内部 16kHz/16-bit/单声道 int16(`ws_input_delegate` `np.frombuffer int16`);下行 TTS 24kHz。
- ⚠️ **多了 Opus 压缩选项**(`ws_opus_codec.py`,默认 20ms/帧):理论 §1.2 主张裸 PCM(零编解码延迟),OAC 加 Opus 是带宽换延迟的工程取舍。format 在 InitializeAvatarSession 声明 PCM|OPUS,**默认 PCM**。
- ⚠️⚠️ **§1.3 重采样坑:OAC 后端兜底不对称**(关键):
  - Opus 路径:`OpusDecoder(sample_rate=16000)` 解码统一转 16k(后端兜底✅,ws_input_delegate:585)。
  - **裸 PCM 路径:不重采样**(`np.frombuffer int16` 原样),只靠前端 `track_constraints sampleRate:16000`(ws_client_handler:202)让浏览器采集端给 16k。
  - → 理论 §7.4 要求的"关卡二后端兜底归一化"**只对 Opus 存在,裸 PCM 没有**。前端不给 16k PCM,后端不救 = §1.3 识别变差的温床。OAC 把归一化责任推给浏览器 getUserMedia。
- ✅ **§2 流式 WS(时代三),但分帧非裸流**:每次发音频 = JSON 头 `SendHumanAudio`(声明 segment_num/binary_size)+ 二进制分段,`BinaryStreamAssembler` 按序重组(`ws_binary_protocol.py`);或 base64 模式塞 JSON。控制 JSON+数据 binary 同 WS 分消息(§7.2)。
- 对比:RTC 客户端走 WebRTC media track,格式 SDP 自动协商 + 框架自动重采样(input16k/output24k)= 裸 PCM"后端不兜底"的反面。
- 落地启示(后议):你若用裸 PCM,**后端入口必须自己加重采样兜底**(OAC 这块不能照抄,它没有);或学 OAC 用 Opus(自带 16k 归一)。
