## 一、弱网、重连与降级策略

### 1.1 目标

语音交互对延迟和连续性敏感。弱网环境下需要保证：

- 用户说完话后，ASR/NLP 仍能拿到完整输入。
- 数字人播报尽可能连贯，不出现爆音、卡顿、重复。
- 断线重连后，会话状态可恢复。
- 极端情况下 graceful 降级，而不是完全不可用。

### 1.2 三层网络问题

| 层级 | 现象 | 影响 |
|---|---|---|
| 应用层 | WS 连接断开 | 事件流中断，session state 可能悬空 |
| 传输层 | 丢包、乱序、抖动 | 音频卡顿、唇形不同步、ASR 质量下降 |
| 物理层 | 带宽骤降、延迟突增 | TTS 无法及时下发，播放缓冲区耗尽 |

### 1.3 连接保活与心跳

```json
// 客户端 → 服务端
{
  "msg_type": "control.ping",
  "payload": { "timestamp": 1234567890, "session_id": "sess-001" }
}

// 服务端 → 客户端
{
  "msg_type": "control.pong",
  "payload": { "timestamp": 1234567890, "server_ts": 1234567895 }
}
```

策略：

- 心跳间隔：5 秒。
- 连续 2 次未收到 pong：触发重连。
- 心跳同时携带往返延迟（RTT），用于动态调整 jitter buffer。

### 1.4 断线重连

#### 重连握手

客户端重连后发送：

```json
{
  "msg_type": "control.resume",
  "payload": {
    "session_id": "sess-001",
    "last_server_seq": 42,
    "last_client_seq": 38,
    "last_stream_id": "st-001"
  }
}
```

服务端响应：

```json
{
  "msg_type": "control.resume_ack",
  "payload": {
    "session_id": "sess-001",
    "resumed_stream_id": "st-001",
    "server_state": "speaking",
    "replay_from_seq": 40
  }
}
```

#### 重连场景矩阵

| 场景 | 服务端处理 |
|---|---|
| 用户正在说话，连接断开 | 缓存上行音频，重连后继续接收；若 VAD 已结束，直接触发 run_loop |
| run_loop 正在运行，连接断开 | 保留 run_loop 结果，重连后从首个未确认 chunk 重发 |
| TTS 正在播报，连接断开 | 重连后下发 `control.clear` + 从断点 seq 重发，或重新开始合成 |
| 重连失败超过阈值 | 服务端优雅结束当前 session，客户端提示网络异常 |

### 1.5 上行音频缓存与补全

客户端需要本地缓存最近 2–5 秒已发送音频。

```text
客户端发送 seq=10,11,12...
          │
          ▼  网络断开
缓存 [10,11,12,13,14]
          │
          ▼  重连成功
补发 missing_seqs 或从 last_client_seq+1 开始全部重发
```

服务端行为：

- 收到补发后按 seq 插入，填充 gap。
- 若 VAD 已结束且 gap 无法补全，用 concealment 或标记 `audio_gap` event。
- 关键尾包必须等补全后再触发 ASR final。

### 1.6 下行 TTS 播放缓冲与追赶

#### Jitter Buffer

客户端维护一个音频播放缓冲区：

```text
目标缓冲深度：200–400 ms（根据 RTT 动态调整）
           │
    ┌──────┴──────┐
    ▼             ▼
  低延迟模式     高鲁棒模式
  100 ms        500 ms
```

- RTT < 100 ms：低延迟，100 ms 缓冲。
- RTT 100–300 ms：标准 200 ms。
- RTT > 300 ms 或抖动大：加大到 400–500 ms，必要时预读 1 秒。

#### 缓冲区下溢（underrun）

当 TTS 下发跟不上播放时：

1. 播放静音帧或环境音。
2. UI 显示“正在思考…”而不是画面定格。
3. 数字人口型切到 idle，不做夸张表情。

#### 重复播放保护

重连后如果客户端已经播放了 seq=40，服务端重发 seq=40 时客户端应丢弃。

```json
{
  "payload": { "seq": 40, "timestamp": 1234568000 }
}
```

客户端用 `(stream_id, seq)` 去重。

### 1.7 降级策略

#### 分级降级

| 等级 | 条件 | 行为 |
|---|---|---|
| 正常 | RTT < 200 ms，丢包 < 1% | 全功能：流式 ASR、流式 TTS、唇形同步 |
| 轻度降级 | RTT 200–500 ms，丢包 1–5% | 增大 jitter buffer，TTS chunk 从 100 ms 加大到 200 ms，减少 viseme 精度 |
| 中度降级 | RTT > 500 ms，丢包 5–10% | 关闭唇形同步，TTS 改为整句下发，ASR 改为 VAD 结束后批量识别 |
| 重度降级 | 频繁断线或丢包 > 10% | 只保留文本对话，语音通道关闭，提示用户切换文字输入 |
| 不可用 | 重连失败 | 结束会话，提示检查网络 |

#### 降级协商

服务端通过 `control.network_adapt` 通知客户端：

```json
{
  "msg_type": "control.network_adapt",
  "payload": {
    "level": "moderate",
    "actions": ["disable_viseme", "increase_tts_chunk_ms"],
    "tts_chunk_ms": 200
  }
}
```

客户端回复确认：

```json
{
  "msg_type": "control.network_adapt_ack",
  "payload": { "level": "moderate", "applied": true }
}
```

### 1.8 状态恢复与幂等

#### Session 状态外置

- 所有会话状态保存在 Redis / PostgreSQL，不依赖 WS 连接内存。
- 重连后服务端根据 `session_id` 恢复状态机。

#### 幂等设计

关键消息带 `msg_id`：

```json
{
  "msg_id": "msg-uuid-001",
  "msg_type": "control.interrupt",
  "payload": { "target_stream_id": "st-001" }
}
```

服务端去重：重复 `msg_id` 只处理一次。

#### Stream 生命周期

```text
stream_id 分配规则：
  - 每次用户 utterance 开始，分配新 stream_id。
  - 同一 utterance 重连后 stream_id 不变。
  - 新 utterance 必须新 stream_id。
```

避免重连后老包和新包混淆。

### 1.9 关键事件日志

| 事件 | 用途 |
|---|---|
| `connection.lost` | 断线时间、最后 seq |
| `connection.resumed` | 重连成功、恢复状态 |
| `audio.retransmit` | 重传发生 |
| `audio.gap` | 无法补全的丢包 |
| `network.degrade` | 降级触发 |
| `jitter.underrun` | 播放缓冲区下溢 |

这些事件应写入 OTel trace，用于后续 badcase 分析。

### 1.10 关键不变量

1. **上行音频丢包尽量补，补不了要标记 gap，不能悄悄吞掉。**
2. **下行 TTS 按 seq/timestamp 去重，不能重复播放。**
3. **重连后 session state 必须可恢复，不能从头开始。**
4. **降级必须双方协商确认，不能单方面静默降级。**
5. **极端网络下优先保文本语义，牺牲唇形和实时性。**

## 二、完整状态机与时序图形式化定义

### 2.1 设计目标

把分包、重传、唇形同步、VAD、打断、弱网重连统一成一个可编码的状态机，满足：

- 状态可枚举。
- 事件驱动。
- 每个迁移有明确守卫条件和副作用。
- 客户端和服务端状态机对称但不必完全一致。

### 2.2 语音会话状态机（客户端视角）

#### 状态集合

| 状态 | 含义 |
|---|---|
| `IDLE` | 未开始或会话已结束 |
| `LISTENING` | 用户正在说话（VAD start 后） |
| `AWAITING_FINAL` | 用户说完，等 ASR final |
| `THINKING` | 已拿到文本，run_loop 运行中 |
| `SPEAKING` | 数字人正在播报 TTS |
| `INTERRUPTED` | 用户打断了播报，正在处理 |
| `WAITING` | 播报结束，等待用户下一轮 |
| `RECONNECTING` | 断线重连中 |
| `DEGRADED` | 降级模式运行中 |

#### 事件集合

| 事件 | 来源 |
|---|---|
| `LOCAL_VAD_START` | 客户端本地 VAD |
| `LOCAL_VAD_END` | 客户端本地 VAD |
| `SERVER_VAD_END` | 服务端精确 VAD |
| `ASR_FINAL` | 服务端 |
| `REPLY_START` | 服务端 |
| `AUDIO_CHUNK` | 服务端 |
| `VISEME_CHUNK` | 服务端 |
| `REPLY_END` | 服务端 |
| `USER_BARGE_IN` | 客户端本地 VAD + 策略 |
| `INTERRUPT_ACK` | 服务端 `control.clear` |
| `NETWORK_LOST` | 本地网络检测 |
| `NETWORK_RESUME` | 重连成功 |
| `DEGRADE_NOTICE` | 服务端 `control.network_adapt` |

#### 状态迁移表

| 当前状态 | 事件 | 守卫条件 | 下一状态 | 副作用 |
|---|---|---|---|---|
| `IDLE` | `LOCAL_VAD_START` | — | `LISTENING` | 开始上传音频，显示聆听动画 |
| `LISTENING` | `LOCAL_VAD_END` | — | `AWAITING_FINAL` | 继续等服务端 VAD end |
| `LISTENING` | `SERVER_VAD_END` | — | `AWAITING_FINAL` | — |
| `AWAITING_FINAL` | `ASR_FINAL` | — | `THINKING` | 提交文本到 run_loop，显示思考 |
| `THINKING` | `REPLY_START` | — | `SPEAKING` | 准备播放缓冲 |
| `THINKING` | `USER_BARGE_IN` | 允许打断 | `LISTENING` | 取消 run_loop |
| `SPEAKING` | `AUDIO_CHUNK` | seq 连续 | `SPEAKING` | 入 jitter buffer |
| `SPEAKING` | `USER_BARGE_IN` | 允许打断 | `INTERRUPTED` | 发 `control.interrupt`，清空缓冲 |
| `SPEAKING` | `REPLY_END` | — | `WAITING` | 切到 idle 表情 |
| `WAITING` | `LOCAL_VAD_START` | — | `LISTENING` | 开始新一轮 |
| `INTERRUPTED` | `INTERRUPT_ACK` | — | `LISTENING` | 若用户仍在说，保持聆听 |
| `INTERRUPTED` | `LOCAL_VAD_END` | 用户已说完 | `AWAITING_FINAL` | 等 ASR final |
| `任意` | `NETWORK_LOST` | — | `RECONNECTING` | 暂停播放，缓存上行 |
| `RECONNECTING` | `NETWORK_RESUME` | 恢复成功 | 原状态 | 补发/重发 |
| `RECONNECTING` | `NETWORK_RESUME` | 恢复失败 | `IDLE` | 提示用户 |
| `任意` | `DEGRADE_NOTICE` | — | `DEGRADED` | 应用降级参数 |
| `DEGRADED` | 网络恢复 | — | 原状态 | 恢复全功能 |

### 2.3 服务端状态机

#### 状态集合

| 状态 | 含义 |
|---|---|
| `IDLE` | 等待用户输入 |
| `ACCUMULATING` | 接收上行音频，VAD 未结束 |
| `RECOGNIZING` | VAD 结束，ASR 后处理 |
| `REASONING` | run_loop 运行中 |
| `SYNTHESIZING` | TTS 合成并下发中 |
| `INTERRUPTED` | 收到打断，清理中 |
| `WAITING` | 等待用户下一轮 |
| `RECONNECTING` | 客户端断线，保持会话 |
| `DEGRADED` | 降级模式 |

#### 事件集合

| 事件 | 来源 |
|---|---|
| `AUDIO_CHUNK` | 客户端 |
| `CLIENT_VAD_START` | 客户端 |
| `CLIENT_VAD_END` | 客户端 |
| `LOCAL_VAD_END` | 服务端精确 VAD |
| `ASR_FINAL` | ASR 引擎 |
| `RUNLOOP_OUTPUT` | harness run_loop |
| `TTS_CHUNK` | TTS 引擎 |
| `INTERRUPT_REQ` | 客户端 |
| `CLIENT_LOST` | 心跳超时 |
| `CLIENT_RESUME` | 重连握手 |
| `NETWORK_ADAPT` | 网络质量评估 |

#### 关键迁移

| 当前状态 | 事件 | 下一状态 | 副作用 |
|---|---|---|---|
| `IDLE` | `CLIENT_VAD_START` | `ACCUMULATING` | 初始化 stream_id |
| `ACCUMULATING` | `LOCAL_VAD_END` | `RECOGNIZING` | ASR final |
| `RECOGNIZING` | `ASR_FINAL` | `REASONING` | 启动 run_loop |
| `REASONING` | `RUNLOOP_OUTPUT` | `SYNTHESIZING` | TTS 合成开始 |
| `SYNTHESIZING` | `INTERRUPT_REQ` | `INTERRUPTED` | 取消 TTS/run_loop，发 `control.clear` |
| `INTERRUPTED` | `CLIENT_VAD_END` + ASR final | `REASONING` | 用新输入启动 run_loop |
| `SYNTHESIZING` | 最后 chunk 发送 | `WAITING` | — |
| `WAITING` | `CLIENT_VAD_START` | `ACCUMULATING` | 新 stream_id |
| `任意` | `CLIENT_LOST` | `RECONNECTING` | 保持状态 N 秒 |
| `RECONNECTING` | `CLIENT_RESUME` | 原状态 | 补发/同步 |

### 2.5 状态机形式化（伪代码）

```python
class VoiceSessionFSM:
    def __init__(self):
        self.state = State.IDLE
        self.current_stream_id = None
        self.audio_buffer = []
        self.tts_queue = []

    async def handle(self, event: VoiceEvent):
        handler = self._transitions.get((self.state, event.type))
        if not handler:
            log.warning(f"no transition for {self.state} + {event.type}")
            return
        await handler(event)

    async def on_vad_start(self, event):
        if self.state in [State.WAITING, State.IDLE, State.SPEAKING]:
            if self.state == State.SPEAKING:
                await self.interrupt()
            self.current_stream_id = new_stream_id()
            self.state = State.LISTENING
            await ws.send_media_vad_start(self.current_stream_id)

    async def on_interrupt(self, event):
        if self.state == State.SPEAKING:
            await ws.send_control_interrupt(self.current_stream_id)
            await tts_engine.clear()
            self.tts_queue.clear()
            self.state = State.INTERRUPTED

    async def on_asr_final(self, event):
        if self.state == State.AWAITING_FINAL:
            await harness.run_loop(event.text, self.current_stream_id)
            self.state = State.THINKING

    async def on_tts_chunk(self, event):
        if self.state == State.THINKING:
            self.state = State.SPEAKING
        if self.state == State.SPEAKING:
            self.tts_queue.append(event)
            await ws.send_media_audio(event)
```

### 2.6 关键不变量

1. **客户端和服务端状态机事件不对称但语义对齐**（客户端关注播放，服务端关注推理）。
2. **`stream_id` 是跨重连的语音流标识，不是 WS 连接标识。**
3. **打断必须两端同时进入 `INTERRUPTED`，不能只清一端。**
4. **`WAITING` 和 `LISTENING` 必须区分，避免把静默等待误判为用户开始说话。**
5. **状态迁移的守卫条件必须明确写出，不能隐含在副作用里。**
