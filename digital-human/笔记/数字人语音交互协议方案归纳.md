## 0. 三个候选方案

| 方案 | 连接形态 | 典型代表 |
|---|---|---|
| **单 WS 多路复用** | 一条 WebSocket,`text` 帧走控制/事件,`binary` 帧走音频 | OpenAI Realtime API WebSocket、阿里云 ISI、FunASR 默认 WS |
| **双 WebSocket** | 主 WS 走 run/工具/票据/事件;从 WS 在会话生命周期内挂载,只走音频 binary | LiveKit 模式、自研"信令主 + 媒体从" |
| **WS + WebRTC** | WS 只作信令(WebRTC 建连前的 SDP/ICE);音频/视频走 WebRTC 独立 UDP track | LiveTalking、OpenAvatarChat WebUI、FireRedChat(LiveKit) |

---

## 1. 单 WS 多路复用 · 结论

**v0/v1 纯语音场景的基线选择。**

### 1.1 为什么够用

- **纯语音流量小**:16 kHz/16 bit/单声道 PCM,20 ms 帧 = 640 B/帧;即使流式 TTS 回传,带宽也远低于视频。TCP 的按序重传在弱网偶发抖动时可通过小帧粒度缓解,不会成为瓶颈。
- **HoL 阻塞可控**:WebSocket 下打断"慢 3-5 秒"的真凶通常不是 TCP HoL,而是"大段 TTS 音频把控制帧堵在后面"或"客户端没及时清播放缓冲"。 mitigation = **20 ms 小帧 + 客户端本地 VAD 先行停播 + 后端硬 cancel**。
- **三端公约数**:网页、App、微信小程序都能走标准 WebSocket;微信小程序没有标准 WebRTC,且旧基础库对并发 WS 有限制(早期 2 条/域名,新版 5 条)。
- **与现有协议对齐**:项目已有主 WS `/app/realtime/ws` 承载 run/工具/票据/事件,单 WS 方案让语音作为该连接的"媒体扩展",不引入新的连接生命周期。

### 1.2 实际限制

- 单 WS 的**控制帧仍和音频帧共享同一条 TCP**,极端拥塞下控制帧理论上会被音频队列阻塞;工程上靠"小帧 + 独立发送协程 + 客户端本地先停"把感知延迟压到可接受范围。
- 单 WS 不能承载**高清形象视频流**(服务器渲染的 MuseTalk/Wav2Lip 视频);只能支持本地轻量形象(Lottie/2D lip-sync/简单口型)。

### 1.3 落地形态(v1)

```
客户端 ──单 WS /app/realtime/ws──→ 网关
  text 帧: media_session.create / media.commit / media.clear / run 事件 / asr.* / tts.*
  binary 帧: audio_in(上行 PCM 16k) / tts_audio(下行 PCM 24k)
```

媒体面只做"翻译":音频 ↔ 协议事件;编排(run/工具/上下文)完全委托大脑。

## 2. 双 WebSocket · 结论

**可选升级层,不是 v1 必做。** 形态为"信令 WS 为主,音频 WS 为从,从连接被会话生命周期约束"。

### 2.1 优势

- **物理分离,控制永不被音频堵**:主 WS 只跑轻量 JSON,媒体 WS 只跑音频 binary。打断信令(`media.clear` / `barge_in`)走主 WS,天然避开大段 TTS 音频的队列竞争。
- **生命周期可收敛**:音频 WS 由 `media_session.create` 签发 `media_ws_url` + `media_token`,在 `media_session.closed` 时统一回收;token 绑定 `allowed_publish` / `allowed_subscribe`,从连接受主会话约束。
- **便于独立扩展**:媒体 WS 可单独做粘性 LB、独立流控/背压(`media.backpressure`)、独立编解码(Opus 24k)。

### 2.2 实际成本(不能忽略)

| 成本 | 说明 |
|---|---|
| 多一条连接 | 客户端、网关、LB、防火墙都要多维护一条长连接;重连/断连场景翻倍。 |
| 粘性 LB | 媒体 WS 通常需要和主 WS 落到同一后端,或至少共享会话状态。 |
| 跨连接调试 | 问题定位时要同时看两条连接的时序,日志/抓包复杂度上升。 |
| 小程序连接预算 | 小程序最多 5 条并发 WS,双 WS 占 2 条,若还有其他业务 WS 需提前规划。 |
| 不解决根本痛点 | 对纯语音,单 WS 的打断延迟已可通过小帧 + 客户端清缓冲降到可接受;升级到双 WS 的边际收益有限。 |

### 2.3 何时启用

- 发现单 WS 在真实弱网下打断信令仍被音频阻塞,且优化小帧/客户端清缓冲后仍不达标;
- 需要把媒体层独立部署、独立扩容;
- 为后续引入形象/视频流提前预留媒体通道(但形象真上来后通常直接走 WebRTC)。

## 3. WS + WebRTC · 结论

**面向"高清形象 + 弱网 + 原生 App"的下一阶段方案,不是 v1 基线。**

### 3.1 优势

- **UDP 无 HoL 阻塞**:丢包直接跳过,不阻塞后续帧,对视频流和弱网语音更友好。
- **内置媒体栈**:AEC(回声消除)、Jitter Buffer、PLC(丢包隐藏)、自动码率适配,减少自研媒体工程。
- **形象刚需**:服务器渲染的 HD avatar(MuseTalk/Wav2Lip)需要 25-30 fps 视频流,WebSocket(TCP)扛视频会卡顿累积。

### 3.2 劣势

| 劣势 | 说明 |
|---|---|
| 部署复杂 | 需要 STUN/TURN/SFU,跨 NAT/防火墙成本远高于 WS。 |
| 无标准小程序支持 | 微信小程序没有标准 WebRTC,只能走 WS 或特定厂商 SDK。 |
| 信令仍需 WS | WebRTC 本身只传媒体,建连、状态、事件仍需 WS 作信令。 |
| 团队/工期成本 | 需要专门熟悉 WebRTC/SFU 的工程师,维护量显著高于 WS。 |

### 3.3 何时启用

- 明确需要**服务器渲染的高清数字人形象**(不只是本地 Lottie/2D);
- 运行在**原生 App/PC 浏览器**,且网络质量差、UDP 收益明显;
- 团队有 SFU/WebRTC 运维能力。

## 4. 形象(Avatar)与协议的关系

这是协议选型的关键分水岭:

| 形象形态 | 能否用单 WS | 推荐协议 | 原因 |
|---|---|---|---|
| 无形象 / 纯语音 | ✅ | 单 WS | 流量小,WS 足够。 |
| 本地 Lottie / 2D 口型 / 简单 lip-sync | ✅ | 单 WS | 口型由本地动画驱动,只需 TTS 音频;WS 传音频即可。 |
| 服务器渲染 HD 形象(MuseTalk/Wav2Lip 视频流) | ❌ | WS + WebRTC | 视频流量大,TCP HoL/卡顿不可接受。 |
| 微信小程序 | ✅ 仅本地轻形象 | 单 WS | 小程序无标准 WebRTC,且并发 WS 有限,只能承载轻量本地形象。 |

**核心判断**:"要不要传视频"是 WS 与 WebRTC 的分水岭,不是"要不要实时"。

## 5. 决策维度汇总

| 维度 | 单 WS | 双 WS | WS + WebRTC |
|---|---|---|---|
| **端到端延迟(纯语音)** | 可接受(20 ms 帧 + 客户端清缓冲) | 更优(控制不堵) | 最优(UDP 无 HoL) |
| **弱网鲁棒性** | 一般 | 一般 | 优 |
| **部署/运维复杂度** | 低 | 中 | 高 |
| **小程序支持** | ✅ | ⚠️ 占连接预算 | ❌ 无标准支持 |
| **高清形象支持** | ❌ | ❌ | ✅ |
| **本地轻形象支持** | ✅ | ✅ | 大材小用 |
| **打断实现难度** | 低 | 低 | 低 |
| **与现有协议兼容性** | 最好(直接复用主 WS) | 中(需新增媒体 WS) | 低(新增信令+媒体两层) |

## 6. 阶段推进建议

| 阶段 | 目标 | 协议选择 | 形象 | 备注 |
|---|---|---|---|---|
| **v0/v1 · 纯语音 MLP** | 跑通实时语音问答、打断、状态机 | **单 WS 多路复用** | 无 | 与现有 `/app/realtime/ws` 完全对齐,真机已验。 |
| **Phase 1 · 语音增强** | 室外嘈杂场景、PTT、独立媒体层扩展 | **双 WS**(可选升级) | 本地轻形象(Lottie/2D) | 仅在单 WS 优化后仍不达标,或需要独立媒体部署时启用。 |
| **Phase 2 · 高清数字人** | 服务器渲染 HD avatar、弱网原生 App | **WS + WebRTC** | 服务器 MuseTalk/Wav2Lip | 需要补充 SFU/TURN 和 WebRTC 团队能力。 |

## 7. 关键工程纪律

1. **媒体面只做翻译,不做编排**:音频 ↔ ASR/TTS + VAD/打断;run/工具/上下文/权威全委托大脑。
2. **打断三板斧**:客户端本地 VAD 先行停播 + `media.clear` + 后端硬 `task.cancel`。连接数不是关键,**客户端清缓冲**才是。
3. **传输无关 + 分层可选**:协议抽象(`media_session.transport`)预留切换位,但实际实现按阶段推进,不预先过度工程。
4. **小程序是硬约束**:标准 WebRTC 不可用,并发 WS 有限,任何方案必须先保证小程序能跑。

## 9. 一页纸结论

> **v1 纯语音 = 单 WS 多路复用,足够、最简、与现有协议完全对齐。**
> **双 WS 是可选项**,在"信令主 + 媒体从、会话挂载"模型下干净,但引入额外连接和运维成本,非 v1 必做。
> **WS + WebRTC 是形象阶段选项**,只在需要服务器渲染高清 avatar 或原生 App 弱网优化时启用。
> **协议选型的真正分水岭是"形象形态"**:纯语音/本地轻形象 → WS;服务器 HD 形象 → WebRTC。
