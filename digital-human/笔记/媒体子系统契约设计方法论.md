# 媒体子系统契约设计方法论

> 基于 `park-app-realtime.v1` 既有协议、单 WS 多路复用实现现状、阿里 ISI / LiveKit / FireRedChat / Pipecat 等行业生产级实践，提炼媒体/语音子系统的契约设计方法论。
> 本文是设计共识，不是字段表；具体字段和流程以 `docs/app-realtime-protocol.md`、`docs/app-frontend-realtime-contract.md` 和 `语音交互子系统-设计.md` 为准。

---

## 1. 核心原则

### 1.1 契约描述的是"承诺"，不是"结构"

好的契约回答三个问题：

```text
1. 谁（哪一层）能发什么事件？
2. 事件发出去后，系统保证什么、不保证什么？
3. 失败时，调用方如何得知并恢复？
```

字段只是承载承诺的载体。讨论契约时，先确定"不变量"，再确定字段。

### 1.2 语音事件与编排事件必须解耦

| 层级 | 标识 | 职责 | 例子 |
|---|---|---|---|
| 传输层 | 连接 ID | 维持 WebSocket 连接 | 心跳、重连 |
| 会话层 | `media_session_id` | 一次媒体会话生命周期 | `media_session.created` |
| 语音层 | `transcript_id` | 一句语音的识别/合成周期 | `asr.partial/final`、`tts.*` |
| 编排层 | `run_id` | 一次 AI 执行 | `run.created`、`run.cancelled` |
| 消息层 | `message_id` | 消息实体 | `message.delta`、`message.completed` |

语音层事件只描述"声音发生了什么"，不直接引用 `run_id`。`asr.final` 到 `run.create` 的晋升由后端统一处理（`auto_run_on_final`），不是前端的职责。

### 1.3 信号语义优先于命令语义

高频、易抖动的交互（如打断）应该设计为"状态请求信号"，而不是"一次性命令"。

- 命令语义：`CancelRunX` → 找不到 X 就报错
- 信号语义：`请进入 LISTENING 状态` → 已经在 LISTENING 就静默忽略

`media.clear` 是信号：它表达"用户开始新输入，请清理旧输出"。

### 1.4 幂等是副作用命令的必选项

所有会改变状态的命令都必须支持幂等：

```text
run.create
run.cancel
media_session.create
media_session.close
operation_ticket.confirm
operation_ticket.cancel
ui.intent.result
```

幂等通过 `idempotency_key` 实现。重复提交应返回同一终态或当前状态，而不是报错。

**信号 vs 命令**：`media.clear`、`media.commit` 是高频、易抖动的**状态请求信号**，不是副作用命令。信号重复发送应静默忽略，不需要 `idempotency_key`，也不返回同步 ack。结果通过后续事件异步体现。

## 2. 单 WS 多路复用的契约方法论

### 2.1 为什么单连接足够

质疑："音频会堵住控制消息。"

解决方式不是靠加连接，而是靠应用层并发模型：

```text
单条 WS 连接
  └── 统一发送锁（仅保护一次 send_text/send_bytes）
       ├── 文本输出队列 + 发送协程
       ├── 音频输出队列 + 发送协程
       └── 信号输出队列 + 发送协程（可插队）
```

控制消息不进入音频队列，直接由信号发送协程处理。即使音频队列堆积，打断延迟也只取决于 RTT + 服务端 cancel 处理时间。

### 2.2 text 帧与 binary 帧的分工

| 帧类型 | 用途 | 说明 |
|---|---|---|
| `text` JSON | 控制/事件/配置 | 人可读、可回放、可调试 |
| `binary` | 音频 payload | 紧凑、低解析开销 |

text 帧处理慢不会阻塞 binary 帧接收；binary 帧处理慢也不会阻塞 text 帧解析，因为 WebSocket 底层帧是独立的。

### 2.3 binary 帧必须自描述

推荐格式：

```text
[4 字节大端 = JSON header 长度][JSON header(UTF-8)][payload]
```

header 字段冻结表：

| 字段 | 类型 | 必填 | 说明 | 约束 |
|---|---|---|---|---|
| `v` | string | 是 | 媒体子协议版本 | 独立版本，如 `park-media.v1` |
| `type` | string | 是 | binary 帧类型 | 当前：`media.audio.frame`；预留：`media.video.frame` |
| `media_session_id` | string | 是 | 所属媒体会话 | 与 text 帧 `media_session_id` 一致 |
| `track` | string | 是 | track 名称 | `audio_in` / `tts_audio` / 预留 `avatar.video` / `lip_sync` |
| `seq` | uint64 | 是 | track 内递增序号 | per-track，从 0 或 1 开始，必须单调递增 |
| `timestamp_ms` | uint64 | 是 | 会话内相对媒体时钟 | 从 `media_session.created` 起算，单位 ms；用于延迟统计，不是 wall clock |
| `codec` | string | 是 | payload 编码 | `pcm16`、`opus`、`aac` 等；v1 固定 `pcm16` |
| `sample_rate` | int | 是 | 采样率（Hz） | `audio_in` 固定 16000，`tts_audio` 固定 24000 |
| `channels` | int | 是 | 通道数 | v1 固定 1 |
| `flags` | int | 否 | 帧标志位（bitmap） | v1 只用 bit0=key_frame, bit1=silence；bit2-7 预留 |
| `pts` | uint64 | 否 | 播放时间戳 | 音视频同步用，v1 可选 |
| `duration_ms` | int | 是 | 帧时长 | 默认 20ms，可显式声明 |

header 字段规则：
- 解析器必须忽略未知字段，不能因未知字段报错或断开连接
- 新增字段必须 additive-only，不能修改已有字段语义
- `seq` 跳号表示丢包，但不能作为业务正确性的唯一依据
- `timestamp_ms` 与 `pts` 解耦：`timestamp_ms` 用于延迟统计，`pts` 用于播放同步

为什么保留 header：
- 未来同一条连接可能承载 `audio_in`、`tts_audio`、`avatar.video`、`lip_sync` 等多个 track
- 便于定位丢包、乱序、延迟问题
- 与 text 协议版本独立演进

关键约束：
- `v` 与主协议 `v` 独立，media 子协议可单独升级
- 解析器必须允许未知字段，禁止 strict 模式
- `seq` 是 per-track，不是 per-connection
- `timestamp_ms` 是**相对媒体时钟**，从 `media_session.created` 起算，单位 ms
- `timestamp_ms` 与 `pts` 解耦：`timestamp_ms` 用于延迟统计，`pts` 用于播放同步

### 2.4 上行与下行的帧策略

| 方向 | 推荐策略 | 理由 |
|---|---|---|
| 上行音频 | 20 ms 小帧直发 | 延迟最低、打断最灵敏、无需组装 |
| 下行 TTS 音频 | 20 ms 小帧直发 | 同上 |
| 上行文件/整段音频 | JSON 头 + 分段 binary | 大文件需要组装和进度 |
| 下行 avatar 视频 | 按 codec 分帧（如 H.264 NALU） | 未来扩展 |

## 3. 事件设计方法论

### 3.1 事件命名：描述"发生了什么"

| 不推荐 | 推荐 |
|---|---|
| `SendHumanAudio` | `media.audio.frame` |
| `EchoAvatarAudio` | `tts.audio.frame` |
| `InterruptAccepted` | `barge_in.detected` |
| `StopTTS` | `tts.cancelled` |
| `VadStart` | `speech_started` |
| `VadEnd` | `speech_stopped` |

阿里 ISI 的 `SentenceBegin` / `SentenceEnd`、LiveKit 的 `user_started_speaking` / `user_stopped_speaking`、Pipecat 的 `UserStartedSpeakingFrame` 都是这种风格。

### 3.2 事件不变量

每个事件都应该有一份"承诺清单"：

| 事件 | 前置条件 | 后置保证 |
|---|---|---|
| `speech_started` | 服务端 VAD 检测到用户开始说话 | 后续会收到该 `transcript_id` 的 `asr.partial`，直到 `speech_stopped` 或 `media.clear` |
| `speech_stopped` | 已收到同一句的 `speech_started` | 后续会收到该 `transcript_id` 的 `asr.final` |
| `asr.final` | 已收到该句的 `asr.partial`（可能为空） | 同一 `transcript_id` 不再发 partial |
| `tts.started` | 已决定为该文本合成语音 | 后续会收到该 TTS 的音频帧，直到 completed/cancelled |
| `tts.segment` | 服务端按句子/语义切分后发出 | 携带 `tts_segment_id`、`text`、`start_ms`、`end_ms` |
| `tts.completed` | 该 TTS 全部音频发完 | 同一 `tts_segment_id` 不再发音频 |
| `tts.cancelled` | 已发 `tts.started` | 该 TTS 不再发任何音频帧 |
| `run.cancelled` | 已发 `run.created` | 该 run 不再发 `message.delta` |
| `media.clear` | media_session 已建立 | 服务端会进入 LISTENING 状态；如原在 SPEAKING，会触发 tts/run cancelled |

### 3.3 异步结果 vs 同步 ack

- 命令的**送达**由 WebSocket send 保证（TCP 可靠）。
- 命令的**业务结果**必须异步返回，不依赖同步 ack。
- `media.clear` 不需要专门的 `media.cleared`；结果通过 `tts.cancelled` / `run.cancelled` 体现。
- 如前端需要"服务端已收到"的确认，可加轻量 `media.clear_received`，但不能把它当成功标志。

### 3.4 语音事件不绑 run_id

```text
asr.final {
  transcript_id: "transcript_001",
  text: "查询A栋告警",
  // 不携带 run_id
}
```

晋升逻辑在后端完成：

```text
if auto_run_on_final:
  run.create(transcript_id=transcript_001, input=text)
```

这样语音层可以独立测试、独立复用，不被编排层语义污染。

## 4. `media.clear` 完整状态机

### 4.1 四态定义

| 状态 | 含义 | ASR | LLM/TTS | 播放 |
|---|---|---|---|---|
| `IDLE` | 一轮结束后的空闲态 | 待命 | 无 | 无 |
| `LISTENING` | 用户正在说话 | 工作 | 无 | 无 |
| `THINKING` | 已出 `asr.final`，LLM 生成中 | 待命 | 可能未开始 | 无 |
| `SPEAKING` | LLM/TTS 输出中，可被打断 | 视 `echo_guard` | 工作中 | 工作中 |

`IDLE` 和 `LISTENING` 在实现上经常合并，但概念上 `IDLE` 表示"上一轮的输出已经完全结束"。

### 4.2 状态转换总表

| 当前状态 | 事件 | 下一状态 | 清理/动作 | 输出事件 |
|---|---|---|---|---|
| `IDLE` | `speech_start` | `LISTENING` | 生成新 `transcript_id` | 无 |
| `IDLE` | `media.clear` | `IDLE` | 无 | 无 |
| `IDLE` | `media.commit` | `IDLE` | 无 | 无 |
| `LISTENING` | `media.clear` | `LISTENING` | 清 ASR 缓冲，废弃当前 `transcript_id`，生成新 `transcript_id` | 无 |
| `LISTENING` | `speech_end` | `THINKING` | 触发 `asr.final` | `asr.final` |
| `LISTENING` | `media.commit` | `THINKING` | PTT 强制出 `asr.final` | `asr.final` |
| `THINKING` | `tts.started` | `SPEAKING` | 无 | `tts.started` |
| `THINKING` | `run.failed` / `message.failed` | `IDLE` | 释放资源 | `run.failed` |
| `THINKING` | `media.clear` | `LISTENING` | 硬 cancel 当前 run | `run.cancelling` → `run.cancelled`（若已输出 `message.delta` 则加 `message.cancelled`） |
| `SPEAKING` | `tts.completed` + `message.completed` | `IDLE` | 无 | 无 |
| `SPEAKING` | `tts.completed`（message 未完） | `THINKING` | 等待下一段 TTS | 无 |
| `SPEAKING` | `media.clear` | `LISTENING` | 硬 cancel run + TTS，清空下行音频缓冲 | `tts.cancelled` + `run.cancelled`（可能加 `message.cancelled`） |
| `SPEAKING` | `speech_start`（`echo_guard=false`） | `LISTENING` | 同 `media.clear` | 同 `media.clear` |
| `SPEAKING` | `speech_start`（`echo_guard=true`） | `SPEAKING` | 服务端丢弃 ASR 结果 | 无 |

### 4.3 `media.clear` 的信号语义

`media.clear` 不是"取消某个对象"，而是"请求进入 `LISTENING` 状态并清理残留"。它是**信号**，不是副作用命令，因此：

- 不需要 `idempotency_key`；
- 不需要同步 ack；
- 重复发送无副作用；
- 结果通过 `tts.cancelled` / `run.cancelled` 异步体现。

| 当前状态 | `media.clear` 行为 | 幂等结果 |
|---|---|---|
| `IDLE` | 已在目标状态，忽略 | 无变化 |
| `LISTENING` | 清输入缓冲，生成新 `transcript_id` | 当前正在听的句子被废弃 |
| `THINKING` | cancel 当前 run | 如果 run 已结束，返回当前终态 |
| `SPEAKING` | cancel run + TTS + 清缓冲 | 如果已在 `LISTENING`，忽略 |

**关键：重复发送 `media.clear` 不能报错。** 它只保证"系统处于 `LISTENING` 状态，没有遗留输出"。

### 4.4 事件输出顺序

`media.clear` 从 `SPEAKING` 触发时，事件应按以下顺序发出：

```text
tts.cancelled          (TTS 已启动)
message.cancelled      (可选：message 已有输出)
run.cancelled          (run 终态)
```

`tts.cancelled` 在 `run.cancelled` 之前，因为 TTS 是媒体层子资源，run 是编排层终态。

`message.cancelled` 是否必须：
- 如果 `message.delta` 已经发过，必须发 `message.cancelled`，否则前端会一直等待 `message.completed`。
- 如果 `message.delta` 还没发过，可以只发 `run.cancelled`。

### 4.5 与 `echo_guard` 的关系

| 模式 | 行为 | 打断来源 |
|---|---|---|
| `echo_guard=true`（默认） | 助手出声期间，服务端丢弃该会话 ASR 结果 | 只能来自前端本地 VAD + `media.clear` |
| `echo_guard=false` | 服务端 VAD 继续工作，检测到语音视同 `media.clear` | 前端或服务端 VAD 都可以 |

`echo_guard=true` 是简单可靠默认：没有 AEC 的设备不会自打断。`echo_guard=false` 需要前端声明有 AEC 能力，并经 `media_session.created` 回显启用。

### 4.6 与 `media.commit`（PTT）的关系

| 场景 | `media.commit` | `media.clear` |
|---|---|---|
| 用户按住 PTT 说完后松开 | 强制出 `asr.final`，进入 `THINKING` | 无 |
| 用户按住 PTT 过程中想取消当前句 | 无 | 清输入缓冲，保持在 `LISTENING` |
| 助手回答过程中用户再次按住 PTT | 无 | 打断当前回答，进入 `LISTENING` |

PTT 不是完全无打断，而是**用户主动控制输入边界**，barge-in 由用户显式触发。

### 4.7 关键不变量

```text
1. 任意时刻，一个 media_session 最多只有一个进行中的 transcript。
2. asr.final 之后，同一个 transcript_id 不会再发 asr.partial。
3. tts.started 之后，如果没有 tts.cancelled/completed，tts 音频帧不会停止。
4. media.clear 之后，系统必须处于 LISTENING 状态；任何残留输出必须被清理。
5. run.cancelled 之后，该 run_id 不会再发 message.delta。
6. 状态转换时，上一状态的缓存/缓冲/队列必须清空，不能污染下一轮。
```

## 5. 打断（barge-in）的契约语义

### 5.1 打断是 first-class 事件

打断不是异常，是正常的用户交互方式。契约层面要提供：

- 上行：`media.clear`（用户开始新输入的信号）
- 下行：`tts.cancelled`、`message.cancelled`、`run.cancelled`
- 可选：`barge_in.detected`（服务端确认检测到有效打断）

### 5.2 客户端先行策略

为了把感知延迟降到 0：

1. 前端本地 VAD 检测到持续语音（200-300 ms 门限）
2. 立即 stop 所有 playingSources + 清空播放队列
3. 发送 `media.clear`
4. 继续发送新音频帧

"听到即停"的精确截断依赖 `tts.segment` 做 refinement，v1 可以不做，但契约应预留。

### 5.3 服务端硬 cancel

`media.clear` 触发后，服务端必须：

1. 进入 LISTENING 状态
2. 硬 cancel 当前 run / TTS 任务
3. 清空下行音频缓冲
4. 发送 `tts.cancelled` 和 `run.cancelled`

全链路必须异步：`graph.astream` → `supervise` → `await tool.run` → `httpx.AsyncClient` / `Milvus await`，没有同步阻塞点。

## 6. 错误契约方法论

### 5.1 统一 envelope + 分层错误码

采用通用 `error` 事件，错误码按业务域区分：

```json
{
  "type": "error",
  "payload": {
    "error_code": "AUDIO_FORMAT_ERROR",
    "message": "前端发送的音频格式与服务端协商不一致",
    "retryable": false,
    "request_id": "req_001"
  }
}
```

错误码分类：
- `VALIDATION_ERROR` / `UNSUPPORTED_COMMAND`：协议层
- `AUDIO_FORMAT_ERROR` / `BINARY_DATA_ERROR`：媒体层
- `MODEL_OPTION_*` / `PROVIDER_*`：模型层
- `TOOL_TIMEOUT` / `JAVA_API_*`：工具/业务层
- `OPERATION_TICKET_*`：操作票层

### 5.2 同步错误 vs 异步错误

| 类型 | 场景 | 返回方式 |
|---|---|---|
| 同步错误 | 格式错误、鉴权失败、命令不支持 | 对应该命令的 `error` 事件 |
| 异步错误 | ASR 断开、TTS 失败、上游不可用 | 异步 `media_session.error`、`tts.error` 或通用 `error` |

### 5.3 错误恢复策略必须在契约中定义

不能只在文档写"前端应该提示用户"。例如：

- `AUDIO_FORMAT_ERROR`：服务端回 capability，前端按 capability 重协商
- `ASR_UPSTREAM_UNAVAILABLE`：进入 `media_session.error`，前端停录并提示重说
- `HEARTBEAT_TIMEOUT`：服务端主动关连接，前端重连

## 6. 可观测契约

### 6.1 metrics 是生产必备

没有 metrics，打断体验优化就是盲调。协议应预留 `media.metrics.collected`。

#### 6.1.1 `media.metrics.collected` 字段冻结表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `media_session_id` | string | 是 | 所属媒体会话 |
| `transcript_id` | string | 条件 | 与该 metrics 相关的语音句 ID；整句级 metrics 必填，会话级可选 |
| `run_id` | string | 条件 | 若该 metrics 与某次 run 相关则填；无 run 关联时不填 |
| `message_id` | string | 条件 | 若与某条助手消息相关则填 |
| `collected_at_ms` | uint64 | 是 | 服务端生成该 metrics 的时间戳 |
| `kind` | string | 是 | metrics 类型：`turn`（整句）、`interrupt`（打断）、`session`（会话聚合） |
| `stages` | object | 否 | 各阶段延迟 |
| `stages.vad_trigger_ms` | int | 否 | 从音频进入服务端到 VAD 触发 speech_start 的延迟 |
| `stages.asr_first_partial_ms` | int | 否 | 从 speech_start 到首个 asr.partial 的延迟 |
| `stages.asr_final_ms` | int | 否 | 从 speech_end 到 asr.final 的延迟 |
| `stages.llm_first_token_ms` | int | 否 | 从 asr.final（或 run.create）到首个 message.delta 的延迟 |
| `stages.tts_first_packet_ms` | int | 否 | 从首个 message.delta 到首个 tts 音频帧的延迟 |
| `stages.client_playback_start_ms` | int | 否 | 从首个 tts 音频帧到客户端实际开始播放的延迟（需客户端回报） |
| `stages.total_response_ms` | int | 否 | 从 speech_end 到客户端开始播放的总延迟 |
| `interrupt` | object | 否 | 打断相关指标 |
| `interrupt.barge_in_latency_ms` | int | 否 | 从用户开始说话到 TTS 实际停止的延迟 |
| `interrupt.false_interrupt` | bool | 否 | 是否被判定为误打断 |
| `interrupt.cancelled_at_ms` | uint64 | 否 | 服务端收到 media.clear 的时间戳 |
| `interrupt.user_speech_start_ms` | uint64 | 否 | 用户实际开始说话的时间戳（前端或 VAD 提供） |
| `quality` | object | 否 | 质量指标 |
| `quality.asr_confidence` | float | 否 | ASR 置信度 |
| `quality.tts_mos` | float | 否 | TTS 质量评分，预留 |
| `network` | object | 否 | 网络指标 |
| `network.uplink_packet_loss_rate` | float | 否 | 上行丢包率 |
| `network.downlink_packet_loss_rate` | float | 否 | 下行丢包率 |
| `network.rtt_ms` | int | 否 | 往返延迟 |

#### 6.1.2 metrics 发送策略

| metrics 类型 | 发送时机 | 必填字段 |
|---|---|---|
| `turn` | 一轮对话结束（`message.completed` 或 `run.cancelled`）后 | `media_session_id`、`transcript_id`、`run_id`、`kind=turn`、`stages.*` |
| `interrupt` | 每次 `media.clear` 触发打断后 | `media_session_id`、`transcript_id`、`run_id`、`kind=interrupt`、`interrupt.*` |
| `session` | 会话关闭或周期性上报 | `media_session_id`、`kind=session`、`network.*` |

v1 策略：
- 协议先定义结构和事件名
- 后端 v1 可以只发 `turn` 类型的部分字段，甚至暂时不发
- 前端必须能兼容接收但不强依赖

### 6.2 session 状态事件

```json
{
  "type": "media.session.status",
  "payload": {
    "media_session_id": "...",
    "status": "healthy",
    "uplink": { "packets_received": 1234, "packet_loss_rate": 0.001 },
    "downlink": { "packets_sent": 1234, "buffer_ms": 40 }
  }
}
```

用于弱网诊断、buffer 状态监控、自动降级决策。

#### 6.2.1 `media.session.status` 字段冻结表

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `media_session_id` | string | 是 | 所属媒体会话 |
| `status` | string | 是 | `healthy`、`degraded`、`recovering`、`closed` |
| `reported_at_ms` | uint64 | 是 | 服务端生成状态的时间戳 |
| `uplink.packets_received` | uint64 | 否 | 服务端收到上行音频包数 |
| `uplink.bytes_received` | uint64 | 否 | 服务端收到上行音频字节数 |
| `uplink.packet_loss_rate` | float | 否 | 上行丢包率估算 |
| `uplink.jitter_ms` | int | 否 | 上行抖动 |
| `downlink.packets_sent` | uint64 | 否 | 服务端发送下行音频包数 |
| `downlink.bytes_sent` | uint64 | 否 | 服务端发送下行音频字节数 |
| `downlink.buffer_ms` | int | 否 | 服务端下行缓冲时长 |
| `downlink.packet_loss_rate` | float | 否 | 下行丢包率估算 |
| `degradation_reason` | string | 否 | 降级原因码，如 `HIGH_PACKET_LOSS`、`HIGH_RTT` |
| `recommended_action` | string | 否 | 建议前端动作，如 `none`、`reduce_bitrate`、`switch_to_ptt` |

发送策略：
- 正常每 5-10 秒发送一次
- 状态变化时立即发送
- 降级时必须带 `degradation_reason` 和 `recommended_action`

## 7. 版本与演进策略

### 7.1 独立子协议版本

- 主协议：`park-app-realtime.v1`
- 媒体二进制协议：`park-media.v1`

两者独立演进。升级 media 帧格式不需要升级主协议版本。

### 7.2 capability negotiation

参考阿里 ISI 的 payload 配置能力：

- `media_session.create` 携带客户端请求的能力
- `media_session.created` 回显服务端实际启用的能力
- 未启用的能力不产生对应事件，前端不依赖

```json
// media_session.create
{
  "audio_in": { "codec": "pcm16", "sample_rate": 16000 },
  "audio_out": { "codec": "pcm16", "sample_rate": 24000 },
  "features": [
    { "feature": "auto_run_on_final", "enabled": true, "required": true },
    { "feature": "echo_guard", "enabled": true, "required": false },
    { "feature": "client_aec", "enabled": true, "required": false }
  ]
}

// media_session.created
{
  "audio_in": { "codec": "pcm16", "sample_rate": 16000 },
  "audio_out": { "codec": "pcm16", "sample_rate": 24000 },
  "features": [
    { "feature": "auto_run_on_final", "enabled": true },
    { "feature": "echo_guard", "enabled": false }
  ],
  "disabled_features": [
    { "feature": "echo_guard", "reason_code": "CLIENT_AEC_NOT_DETECTED", "message": "前端未声明 AEC 能力" }
  ]
}
```

### 7.3 加性演进（additive-only）

- 只增加新字段、新事件、新 capability
- 不删除旧字段，不修改已有字段语义
- 解析器忽略未知字段
- 重大变更通过版本号升级解决

## 8. 与行业做法的对照

| 方法论维度 | 阿里 ISI | LiveKit | FireRedChat | Pipecat | 本项目 |
|---|---|---|---|---|---|
| 传输复用 | 单 WS text+binary | WebRTC + data channel | WebRTC | frame 流 | 单 WS text+binary |
| 音频帧格式 | binary 裸发 | WebRTC track | WebRTC track | 20 ms PCM | JSON header + PCM |
| 会话标识 | `task_id` | room/participant | room/participant | frame 上下文 | `media_session_id` + `transcript_id` |
| 事件命名 | `SentenceBegin/End` | `user_started_speaking` | `UserStartedSpeaking` | `StartInterruptionFrame` | `speech_started` / `speech_stopped` |
| 打断语义 | `StopTranscription` | `agent_speech_interrupted` | 打断 pipeline | upstream propagation | `media.clear` + 本地停播 |
| 幂等 | 请求级 | 无强调 | 无强调 | 无强调 | 命令级 `idempotency_key` |
| 可观测 | 基本日志 | `metrics_collected` | T90/APT/误打断 | frame tracing | 协议预留，v1 可不发 |
| 错误分层 | `TaskFailed` | 异常 | 日志 | pipeline error | 通用 `error` + 业务错误码 |

我们项目在**协议工程化**（幂等、session/run 分层、错误码体系、恢复机制）上比多数开源项目更完整；主要补强点是**可观测契约**和**media 子协议独立版本化**。

## 9. 关键决策结论

### 9.1 `media.clear` 是信号，不需要同步 ack，也不需要 `idempotency_key`

- 表达"请进入 LISTENING 状态"
- 重复发送无副作用
- 结果通过 `tts.cancelled` / `run.cancelled` 异步体现

### 9.2 binary 帧保留 JSON header，但极简且独立版本化

- `v` 独立为 `park-media.v1`
- 允许未知字段
- `seq` per-track，`timestamp_ms` 为相对媒体时钟（从 `media_session.created` 起算）

### 9.3 `transcript_id` 由服务端签发，与 `run_id` 解耦

- `asr.final` 不携带 `run_id`
- `auto_run_on_final` 的晋升逻辑在后端统一完成

### 9.4 可观测事件纳入协议，v1 可延迟实现

- `media.metrics.collected`
- `media.session.status`
- `media.session.state_changed`（可选，用于数字人/诊断）

### 9.5 错误契约采用统一 envelope + 分层错误码

- 一个 `error` 事件类型
- 错误码按业务域区分
- 同步/异步错误路径明确
