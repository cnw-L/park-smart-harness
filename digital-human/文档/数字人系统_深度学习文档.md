# 导论:从一个真实问题出发

整个学习始于一个具体的、很多人都遇到过的问题:

> **"我部署了 SenseVoice、FireRedASR 这些评分很高的模型,但采集上传后,识别效果却很一般。"**

这个问题的答案,是理解整个系统的钥匙:

> **问题几乎从不在模型本身,而在工程链路。高分模型 + 错误的工程链路 = 差的实际效果。**

具体来说,"识别效果一般"最常见的根因是:
- 用了"整段思路的模型"去做"实时切片"(模型与场景错配)
- 浏览器采集的 48kHz 音频没有重采样到 16kHz(格式错配)
- 缺少正确的 VAD 切句(用定时切片代替了语义切句)
- 连接复用时状态没清理(上一句污染下一句)

要真正解决,不能只调模型参数,必须理解整个实时语音/数字人系统是怎么运转的。这份文档就是这套理解的完整地图。

**全局心智地图(先建立整体感):**

```
① 上行(听懂):  用户说话 → VAD切句 → 2pass识别 → final文本
② 下行(开口):  文本 → LLM流式 → 句子聚合 → 流式TTS → 排期播放
③ 打断(双工):  前端清播放 + 后端cancel任务 + 信号分离传输
④ 状态机(焊死): 每状态各模块工作态 + 转换时清理
⑤ 形象(可选):  TTS音频分叉 → 口型同步 → 音视频对齐推流

贯穿全局:传输层(WebSocket/WebRTC)+ 模块化架构
深入生产:误打断、状态机异常、并发资源、形象工程
```

记住一句话贯穿始终:**主干假设"一切顺利",而真实工程的难点几乎都在"不顺利"——这就是"深水区"存在的意义,也是 demo 能跑和能上线之间的全部差距。**

# 第一部 · 基础认知层

## 第 1 章 声音的本质:PCM

### 1.1 PCM 是什么

声音在计算机里,本质是**一串数字**。麦克风按固定频率测量声波振幅,每次记一个整数,排成一队,这就是 PCM(Pulse Code Modulation,脉冲编码调制)。

```
真实声波(连续曲线)
   ↓ 每秒测16000次,每次记一个数
[12, 45, 88, 120, 67, -30, ...]  ← 这串数就是 PCM
```

三个属性决定一段 PCM:
- **采样率** 16000(每秒测几次,写作 16kHz)
- **位深** 16-bit(每个数用16位记,范围 -32768~32767)
- **声道** 单声道(1条)

PCM 是声音**最原始、未经压缩**的形态。MP3、Opus 是把 PCM 压缩后的样子(体积小但要解码);WAV 基本就是 PCM 加个文件头。

### 1.2 为什么实时识别要用裸 PCM(三个原因)

这是个反直觉的点:**越现代的实时系统,反而用越"原始"的格式(从压缩的 MP3 退回裸 PCM)**。原因:

**① 延迟**——压缩格式要编码+解码,且常需攒满一帧(如 Opus 一帧20ms)才能编。这些时间与实时低延迟冲突。裸 PCM 采到即发,零解码延迟。

**② 精度**——有损压缩为减小体积主动丢弃人耳不敏感的信息(不是"损坏",是主动丢弃)。但丢掉的细节可能正是 ASR 模型需要的声学特征,导致识别精度下降。

**③ 处理便利**——裸 PCM 可任意切块,便于流式喂入和 VAD 切句,不受编码帧边界约束。

代价是 PCM 体积大、占带宽。但实时场景值得"用带宽换延迟"。

### 1.3 一个关键的坑

浏览器麦克风采集的音频**默认通常是 48kHz**,而模型要 16kHz。如果不重采样直接喂模型,采样点的时间含义错位,模型相当于听到"变速"的声音,识别会显著变差。

**这正是"识别效果一般"最常见的根因之一。** 前端采集后,必须把 48kHz 重采样到 16kHz、整理成单声道 16-bit 裸 PCM,再发出去。

## 第 2 章 上传方式的演进:从文件到流

### 2.1 三个时代

**时代一:整段文件上传(HTTP)**
录完整段→打包成 WAV/MP3 文件→HTTP POST 上传→等服务端识别完→返回文字。缺点:必须说完才识别,一句话要等好几秒。但文件有头有尾,边界清晰,适合"整段干净音频"的模型。

**时代二:定时切片(HTTP 过渡)**
把长音频每隔几秒切一段分别上传。问题:切在哪不知道(可能切断一个字),每段重建连接。**这就是"识别效果差"的另一个常见根因——定时切片而非语义切片。** 是个很快被淘汰的过渡产物。

**时代三:流式上传(WebSocket)**
建立长连接,持续推 PCM 流,服务端边收边识别边返回。边说边出字,百毫秒级延迟。这是实时数字人的主流方案(WebRTC 也可承担,见第7章)。

### 2.2 新老对比

| 维度 | 老(整段HTTP) | 新(流式WebSocket) |
|------|------------|------------------|
| 协议 | HTTP POST 短连接 | WebSocket 长连接 |
| 格式 | WAV/MP3 文件(有头尾) | 裸PCM流(无边界) |
| 边界 | 文件头尾天然有 | 靠VAD检测 |
| 录制 | MediaRecorder | AudioWorklet |
| 实时性 | 说完才识别(秒级) | 边说边出(百毫秒) |

### 2.3 一个关键转变

注意"边界"那一行:文件有头尾(天然边界),但流没有尾。**流式系统靠 VAD 来"探测"出一句话的起止边界**,而不是靠文件头尾。这就引出了下一章的核心——VAD。

# 第二部 · 核心链路层

## 第 3 章 上行链路:听懂(VAD + 2pass)

上行解决"把用户说的话变成文字"。它有两个核心:VAD(切句)和 2pass(双模型识别)。

### 3.1 VAD:整个上行的地基

**核心机制:VAD 对每一块音频持续检测,但输出不是"每块的有声/无声标签",而是两个转折点:** speech_start(说话开始)、speech_end(说话结束)。

比喻:像门口保安,每个人都看一眼(每块都检测),但只在第一个人进门、最后一个人离开时按铃(只在转折点触发动作)。中间连续说话的块,VAD 只是默默确认"还在说",不触发动作。

**VAD 只做声学判断,不懂语义。** 它靠能量/频谱判断"有没有人声、停没停",完全不理解你说的内容。这是它的根本局限。

### 3.2 VAD vs 轮次检测(一个重要区分)

正因为 VAD 不懂语义,它会犯一个经典错误:

```
用户说:"我想订一张去北京的票...(停顿2秒)...明天的"
  VAD视角:停顿2秒 → 以为说完了 → 触发 → 把话截断 ✗
  问题:VAD不懂"明天的还没说出来,语义没完整"
```

要解决,需要在 VAD 之上加一层**轮次检测(turn detection)**:
```
VAD:      声学层面 —— 有没有声音、声音停了没(不懂内容)
轮次检测:  语义层面 —— 这个想法表达完整了没(懂内容)
```

起步用 VAD 够,轮次检测是后期优化。

### 3.3 speech_end:上行的引爆点

VAD 产生的 speech_end 这一个事件,**同时触发三件事**:
1. 整句送 SenseVoice 出 final
2. 清 cache/buffer 重置状态
3. 触发下游 LLM

整个上行的复杂度,就是围绕"准确地在对的时刻产生这个事件"。VAD 调不好,引爆点错位,整个对话节奏全乱。

### 3.4 2pass:为什么要两个模型

**实时性和精度本质矛盾,单模型只能取一头:**
```
只用流式模型:实时✓ 但精度低,partial跳字易错
只用整句模型:精度✓ 但要等说完才识别,无实时反馈
```

**所以双模型分工:**
- **Paraformer-streaming**:用户说话全程工作,出 partial(快,即时反馈)
- **SenseVoice**:speech_end 那一刻工作,对早已攒好的整句音频识别,出 final(准)

**精妙的时间同步:** 因为流式那遍在说话全程已在跑,整句音频在说完时就现成了,SenseVoice 立刻能识别,所以 final 几乎话音刚落就出来,不让用户额外等待。

注意:不是"两模型互相纠错",是 SenseVoice **单向覆盖** Paraformer 的草稿。partial 是草稿(快但可能错),final 是定稿(慢但准),final 直接覆盖 partial。

### 3.5 流式识别的 cache 机制

Paraformer-streaming 靠 `cache={}` 字典在 chunk 间滚动状态。模型每次把中间状态写回 cache,下次带着来才能续上上下文。

**清空 cache = 切断上下文 = 一句话从头。** 状态机里"一句结束"做的就是清 cache。

`chunk_size=[0,10,5]`(官方示例之一,也常见 `[5,10,5]`):三个数单位约60ms/份。中间10=当前块(约600ms),右5=前看(看未来约300ms提精度,代价+约300ms延迟),左=回看历史块数。**这三个数是延迟/精度旋钮**,具体取值以你用的模型/官方示例为准。

**一个吞字坑(is_final):** 流式因有前看,说完时手里还攒着没吐的尾字。必须再调一次 `generate(is_final=True)` 让它"全吐出来",否则 partial 结尾总缺最后一两字,会出现"partial 比 final 短一截"的诡异现象。

### 3.6 双缓冲:上行的核心结构

```
每块音频进来:
  ① 先过VAD → 拿speech_start/speech_end
  ② 在说话状态时,同一份音频进两条路:
       online_buffer → 喂流式ASR出partial(快)
       offline_buffer → 攒整句,到speech_end一次性喂SenseVoice出final(准)
  ③ speech_end → 出final + 清cache/buffer重置
```

**状态是 per-connection 的:** 每个用户一个 Session,各自的 cache 互不干扰,并发隔离靠这个。

## 第 4 章 下行链路:开口(LLM→聚合→TTS→播放)

下行解决"把回答变成数字人嘴里的声音"。它的核心难点和上行不同——上行难在"切句",下行难在**"让用户尽快听到第一个字"(首包延迟)**。

### 4.1 首包延迟的问题

反面例子:等 LLM 想完整段(3s)→等 TTS 合成完整段(2s)→才播 = 用户等5秒。下行全部工程就是把这5秒压到1秒内,靠**流水线接力**。

### 4.2 三棒接力

```
LLM ──token──> 句子聚合 ──句子──> TTS ──音频块──> 排期播放
(一字字吐)     (攒成句)        (边收边合成)     (边收边播)
```

**第一棒 LLM 流式吐字:** 一个字一个字往外吐,不用等想完整段。

**第二棒 句子聚合(最易忽略的桥):** 不能每来一字就送 TTS(会一顿一顿)。要攒到语义完整的小片段(逗号/句号)再整块送。
- 攒太碎→声音断续;攒太久→首字延迟高
- 实战写法:**标点 + 字数兜底** 双条件(防 LLM 吐长串不打标点时卡住)

**第三棒 TTS 流式合成:** 选支持流式的(CosyVoice2),边收文字边出音频,收5字即出首包(150ms),而非整句收完才出第一个音。

### 4.3 三棒的时间重叠

```
LLM:   今天天气不错,│适合出门。│正好可以...
                    ↓送          ↓送
TTS:               合成"今天天气不错"  合成"适合出门"
                            ↓出音频块        ↓出音频块
播放:                      ▶播放...        ▶接着播...

关键:用户听到"今天天气不错"时,LLM还在生成"正好可以..."
```

这个时间重叠就是首包从5秒压到1秒的原因。延迟公式:
```
用户感知延迟 = LLM吐出首个可合成片段的时间 + TTS首包时间
→ 两头都要快:句子聚合别攒太久 + 选首包快的TTS
```

### 4.4 上下行的对称与区别

```
上行: 音频流 → VAD切句 → 流式ASR+整句 → 文本
下行: 文本流 → 句子聚合 → 流式TTS → 音频

"VAD切句" ←对应→ "句子聚合"(都是把流切成块再送下一环)
```

**但切的依据不同(关键洞察):**
```
上行手里是音频,音频无标点 → 得用VAD探测边界(会探错→切断/黏连)→ 难
下行手里是文本,标点现成   → 直接读标点(几乎不错)→ 送分题
```

所以上行核心难点在"切句(VAD)",下行核心难点在"流水线延迟"。

### 4.5 排期播放(前端,且是打断的前置)

**矛盾:音频块陆续到达(网络不均匀),但播放要连续不卡顿不重叠。**

错误做法:来一块播一块→块没到时静音(卡顿)、两块同时到时重叠(鬼畜)。

**正确做法:排期播放。** 维护"播放游标"nextPlayTime,每块的播放开始时刻 = 上一块的结束时刻,严丝合缝排队。用 Web Audio API 的 `source.start(nextPlayTime)` 精确排期。

**关键:把每个排期的 source 记进一个列表(playingSources)** —— 这是打断的"遥控器"。

**为什么这是打断前置:** 下行流畅时,前端可能已排期了好几块(已收到、已设定start时刻、在队列等)。这些块的start时刻已定,不停它们就会自动响。所以打断必须:停正在播的 + **取消所有已排期未播的(最易漏!)** + 重置游标。

## 第 5 章 打断:双工的核心

打断 = 在 SPEAKING 状态(数字人正说)时,用户插话,系统暴力中止下行、干净切回 LISTENING。它不是某个模型的功能,是编排层状态机的事。打断是整个系统的"集大成者"——它依赖前面每一环都做对。

### 5.1 完整流程(前端 + 后端 + 信号)

```
触发: 前端VAD检测到用户开口(本地,最快,不等网络往返)
  │
  ├─ 前端立即(不等后端):
  │    ① 停所有正在播+已排期的音频块(用playingSources列表逐个stop)
  │    ② 清空播放队列
  │    ③ 重置播放游标到currentTime
  │
  ├─ 同时发"打断"信号给后端:
  │    走优先级/独立通道,绝不被音频流堵 ← 核心陷阱解法
  │
  └─ 后端收到信号:
       ④ cancel LLM任务(前提:它是可取消的异步task)
       ⑤ cancel TTS任务
       ⑥ 停推音频 + 清后端音频缓冲(fire-and-forget非阻塞)
       ⑦ 状态机 SPEAKING→LISTENING(干净,不留残留)
```

### 5.2 三个深层要点

**要点1:后端为什么要 cancel**
前端停了播放,但后端不知道,还在埋头干活(LLM 还在生成、TTS 还在合成、还在推音频)。不停后端,新块又源源推来,前端清不完。

**要点2:可取消是写下行时决定的(最反直觉)**
LLM/TTS 必须跑在 `asyncio.create_task` 里、存句柄,打断时 `task.cancel()` 才能中止。若是同步阻塞调用,cancel 不掉——会把当前调用跑完才停,数字人多说一截。
- 更深:`cancel()` 不是立刻杀,是在协程下一个 `await` 点抛 CancelledError。重的同步调用要包进 `run_in_executor` 成为 await 点,cancel 才及时。
- **所以"打断能力"在写下行代码时就预留好了,不是事后能加的。**

**要点3:核心陷阱——信号被音频堵(WebSocket下打断慢3-5秒的真凶)**
```
打断信号和下行音频走同一条通道顺序发送
  → WebSocket正忙着推大块TTS音频
  → 小的打断信号排在音频块后面被堵
  → 等音频推完才轮到 → 延迟3-5秒
```
解法:
- 逻辑优先级队列(单WS也能做):控制消息插队
- **双WebSocket物理分离**(控制一条、音频一条):打断信号永不被堵
- WebRTC天然分离(media track + data channel)

### 5.3 漏清队列的连锁后果

```
没清排期队列 →
  ① 旧排期块继续播,数字人停不下来(违和)
  ② 新一轮音频append到旧队列后,新内容排队尾,延迟雪球越滚越大
  ③ 继续播的声音被麦克风回采 → 当成用户说话 → 污染识别/误触发
防线: 彻底清队列(根治) + AEC消残余回声(兜底)
```

### 5.4 三条铁律

```
1. 前端VAD先行,本地停播放,不等后端往返 → 保证"快"
2. 打断信号必须走优先级/独立通道,不被音频堵 → 避免3-5秒延迟
3. LLM/TTS必须是可取消的异步任务 → 否则cancel不掉,慢半拍
   (这个能力在写下行时就要预留,不是事后能加)
```

## 第 6 章 状态机:把系统焊死

前面的链路是"血肉",状态机是把它们焊成一个整体的"骨架"。它的真正价值不是"流程图",而是精确定义:每个状态下各模块的工作态、双工矛盾在哪解决、转换时清什么。

### 6.1 模块的三种工作态

```
工作(active):  正在处理数据、产出
待命(standby): 开着等触发,不产出(如VAD等用户开口)
关闭(off):     完全不工作
```

### 6.2 状态-模块对照表(核心)

```
状态        VAD      ASR        LLM      TTS       播放
─────────────────────────────────────────────────────────
IDLE       待命     关         关       关        关
LISTENING  工作     工作        关       关        关
THINKING   待命     关         工作      待命→工作   待命→工作
SPEAKING   工作★    待命/轻量★   收尾      工作       工作
─────────────────────────────────────────────────────────
★ = 双工核心难点都在这两格
```

- **IDLE:** 唯一醒着的是 VAD(门铃)。所以 IDLE 可与 LISTENING 合并。
- **LISTENING:** 上行全速(VAD+ASR工作),后面全关。
- **THINKING/SPEAKING 常交融:** 因流水线接力,LLM 还在生成(THINKING),TTS/播放已开始(SPEAKING)。理论图泾渭分明,实际交叠。

### 6.3 SPEAKING:双工矛盾的全部所在

**为什么 SPEAKING 时 VAD 必须开着:** 打断要靠它。一说话就关 VAD,用户开口察觉不到,打断不可能。

**由此引出双工核心矛盾:**
```
SPEAKING时:数字人声音在播(扬声器) + VAD开着听(麦克风)
  → 麦克风可能把数字人自己的声音收进去
  → VAD以为"用户在说话" → 误打断 → 数字人自己打断自己
```

**所有双工技巧都是为解决这一个矛盾(在状态机视角下全部归位):**
1. AEC回声消除:把数字人声音从麦克风信号消掉(治本)
2. 半双工降级:SPEAKING时提高VAD阈值,只有明显人声才算打断(治标有效)
3. pVAD/声纹:只认主说话人,过滤其他声音
4. 文本比对:识别内容若和正在播的TTS高度重合,判为回声非打断

### 6.4 状态转换时的清理(焊死系统的关键)

每条转换挂对应清理动作:
```
LISTENING→THINKING(speech_end): 出final + 清ASR cache/buffer + 启动LLM
SPEAKING→LISTENING(打断): cancel LLM/TTS + 清播放队列+重置游标 + 清后端缓冲
任何→IDLE(会话结束): 清所有cache/buffer/队列 + 释放任务
```

**核心原则:每次状态切换,必须把上一状态的残留清干净。** 之前反复强调的清cache/清队列/cancel任务,本质都是转换时的清理动作。

### 6.5 贯穿全局的铁律:连接生命周期 ≠ 状态生命周期

```
连接生命周期(会话级): 整个会话开着,会话结束才关
状态/缓存生命周期(句子级): 每句speech_end要清cache/buffer
两者错开! 连接没断但状态每句清,否则上句污染下句 → "越用越乱"的bug
```

# 第三部 · 传输与架构层

## 第 7 章 WebSocket 与 WebRTC:关系的彻底厘清

这是最容易绕晕、也最影响选型的一块。彻底厘清它,你的传输决策就有了根基。

### 7.1 行业标准:不是二选一,是分层各管一段

```
用户浏览器 ──WebRTC──> 你的服务器 ──WebSocket──> AI模型(FunASR/CosyVoice)
         (面向用户那段)         (面向模型那段)
```
- 面向用户那段:行业默认 WebRTC(网络不可控、自带AEC、UDP抗丢包)
- 面向模型那段:WebSocket(对接模型现成协议)

### 7.2 五个关键认知(逐个厘清)

**认知1:WebSocket 不是 WebRTC 的"基础",是它的"信令媒人"。**
WebRTC 建连前要交换暗号(SDP/ICE),常借 WebSocket 传。牵完线音频走 WebRTC 独立 UDP 通道,不经过 WebSocket。

**认知2:"WebSocket 裹着 WebRTC 传音频"——错。**
音频根本不在 WebSocket 管子里,WebRTC 走独立 UDP,没东西被"裹着"。正确:WebSocket 是助产士(帮接生),不是容器(装载)。

**认知3:连接是会话级的。**
```
会话开始: WebSocket握手 → WebRTC一次性建立
会话期间: 通道复用(说多句答多句都用它)
一句话结束(speech_end): 不关通道
整个会话结束(用户离开): 才关通道
```
连接是"会话级",不是"音频段级"的反复起关。

**认知4:根本权衡 TCP vs UDP(这是设计决策的底层根因)。**
```
WebSocket(TCP): 保证不丢、按序到达 → 丢包必重传、后面包要等它 → 会卡顿累积
WebRTC(UDP):   丢包直接跳过不重传 → 丢一帧无感,不卡
```

**认知5:几条连接?三种方案。**
| 方案 | 连接数 | 说明 |
|------|--------|------|
| 单WebSocket(FunASR默认) | 1条 | 控制+音频一条,JSON配置+二进制PCM。起步推荐 |
| 双WebSocket | 2条 | 控制/音频分离,打断信号不被音频堵 |
| WebRTC方案 | WS(信令)+WebRTC媒体流 | 最专业,部署最重 |

建议:**起步单WebSocket跑通,遇到打断被音频堵再升级双WebSocket。**

### 7.3 纯语音 vs 加视频:决策的分水岭(重要)

```
纯语音(数据小):
  WebSocket(TCP)够 —— 量小,丢包重传影响不大

加视频(数据大,是音频几十倍):
  WebSocket(TCP): 流量大→丢包多→频繁重传+保序等待 → 卡顿累积 ✗
  WebRTC(UDP):   丢包直接跳过 → 丢一帧人眼无感 → 流畅 ✓

核心:视频流量大,放大了TCP"丢包重传卡顿"的缺陷,
     而UDP"丢包就跳过"恰好适合视频(丢一帧无所谓,卡顿才致命)
```

**所以你的传输选型本质取决于"要不要传视频":纯语音→WebSocket足够;要形象/视频→认真考虑WebRTC。**

### 7.4 格式归一化(回应最初的识别问题)

不同前端格式不一(48k/44.1k、双声道、Float32...),两道关卡归一化:
- 关卡一(前端):采集时重采样到16k/单声道/16bit再发(自律,不可靠)
- 关卡二(通信模块入口):强制把任何输入转成标准格式(兜底,必须有)

WebRTC 格式协商自动(SDP握手+框架自带重采样);WebSocket 要自己在协议第一帧声明格式(FunASR的wav_format/audio_fs字段)+服务端自己归一化。

## 第 9 章 误打断判定(双工的命门)

### 9.1 误判来源:五种

SPEAKING 时,VAD 可能把这些误判成"用户要打断":
```
① 数字人自己的声音(回采)        ← 最主要,外放尤其严重
② 用户附和词:"嗯""对""是的"     ← back-channel,没想打断,只是回应
③ 环境噪声:关门、键盘、背景音乐
④ 旁边别人说话(非目标用户)
⑤ 用户的呼吸、咳嗽
```

本质是精度/召回平衡:判太松→误打断频繁;判太严→真打断打不了。

### 9.2 三层防御(剥洋葱,每层一个问题)

```
最外层:"这是人声吗?"      → 不是 → 噪声 → 普通VAD挡
中间层:"这是主人的人声吗?"  → 不是 → 回声/旁人 → AEC + pVAD挡
最内层:"主人想打断吗?"     → 不是 → 附和 → 时长/语义挡
```

**关键提醒(易错):普通VAD只能挡噪声(最外层)。它挡不了任何人声——数字人的声音、旁人的声音都是人声。要挡人声里"不该触发的",主要靠AEC和pVAD;单纯调VAD阈值(半双工降级)只能部分缓解,压不到位。**

### 9.3 第二层核心:pVAD(个性化VAD)

普通VAD缺陷:只判"有没有人声",不判"是不是该听的人"。

pVAD升级:**认主人。**
```
普通VAD: 听到声音 → "有人说话" → 触发
pVAD:    听到声音 → "是主人的声音吗?"(声纹比对)
                  → 是主人 → 触发;不是(回声/旁人/噪声)→ 忽略
像门禁刷脸:是主人才开门
```

技术(FireRedChat):因果卷积流式推理,目标说话人声纹嵌入(ECAPA-TDNN)+梅尔频谱拼接,GRU建时序,10ms分辨率输出说话概率。

**pVAD 严格定位(最易错,钉死):**
```
pVAD 只干一件事:比对声纹,回答"是不是主人"
  · 不管声音长短
  · 不管是不是附和
  · 不判断意图
三组件分工:
  AEC: 消数字人回声
  pVAD: 判"是不是主人"(声纹)← 只管这个
  时长过滤: 判"附和(短)还是打断(长)"← 这才管长短
```

### 9.4 关键数据:速度 vs 误打断是跷跷板

```
系统          T90(打断速度)   误打断率
Ten          90ms(最快)      78.1%(灾难)
LiveKit      140ms            33.4%(高)
FireRedChat  170ms(略慢)     10.2%(低)

铁律:
· 快系统"听到就触发"→ 快,但噪声/回声/附和全触发 → 误打断飙升
· 慢系统"听到先核实(是不是主人?是不是真打断?)"→ 慢30ms,误打断暴跌
· 宁可慢30-50ms,也要压住误打断("宁慢勿误")
· 误打断(数字人无故闭嘴)比漏打断(用户多说一次)更伤体验
· 据该论文,没有"目标说话人识别"(pVAD)的系统,误打断率明显偏高(30%量级)
```

### 9.5 第三层:附和(back-channel)判定 —— pVAD盲区

**难点:"嗯""对"恰恰是主人说的,pVAD判"是主人",拦不住。** 需另一机制区分"真打断"vs"附和"。

```
方法一 时长/能量过滤(简单,推荐起步):
  真打断会说完整一句(长),附和就一两字(短)
  阈值设"宁漏附和勿误真打断" → 先解决80%
方法二 关键词(附和词表:嗯/对/是的/哦...)
方法三 语义意图判断(EoT,最准最重,留给疑难)
```

### 9.6 级联过滤 + pVAD兜底(进阶设计)

```
级联过滤(省算力):
  便宜过滤器在前(时长/能量/AEC):挡明显的(噪声/短附和/回声)
  pVAD在最后兜底:筛剩的"长且响"疑难,由它最终裁定是不是主人

红线(关键):
  "长且响"是"启动pVAD"的触发条件,不是"判定打断"的结论
  → 可用便宜手段减少pVAD调用频率(优化)
  → 但不能用便宜手段替代pVAD判断(否则旁人长音误打断)
兜底方向:pVAD拿不准时倾向"不打断"(呼应宁慢勿误)
```

### 9.7 一个精妙设计:pVAD做裁判,识别用原始音频

```
pVAD去噪音频: 干净,适合"判断是不是主人"
但去噪损伤音质 → 拿去识别会掉精度
所以:
  判断谁在说 → 用pVAD处理的(去噪)
  实际识别   → 用原始未去噪音频(细节全)
  靠时间戳对齐:pVAD说"3.2s-5.1s是主人",从原始音频截这段去识别
一句话:pVAD是裁判(判谁在说),不是加工厂(不加工识别音频)
```

## 第 11 章 真实状态机(异常处理)

### 11.1 4状态版漏掉的:全是异常
```
· 用户说了,ASR识别出空(没听清/纯噪声)
· LLM调用超时/报错
· TTS合成失败
· 网络突然断了
· 用户说到一半停很久(在想 vs 说完了?)
· 用户打断到一半又不说了
· 用户一直不说话(超时)
```

### 11.2 几个高频异常的标准应对
```
空结果(最高频):
  节点:出final、送LLM之前拦截
  纯空→静默忽略回LISTENING;连续多次→追问"没听清,再说一遍?"
  绝不能送LLM(否则对空输入瞎回答)

LLM超时/报错:
  慢但没超时→垫话"让我想想"争取时间
  真超时/报错→固定兜底话术,不死等重试

停顿歧义:
  VAD先粗判端点,轮次检测在"该结束时"做精判
  语义完整→转THINKING;没完→继续等

打断未遂:
  方案①续接上次结果(丝滑但复杂)— 成熟后用
  方案②固定回答/转LISTENING等待(简单)— 起步用

超时管理:
  无语音30s→"还在吗";长时间无交互→结束会话释放资源(对并发关键)
```

### 11.3 五原则
```
1. 每个状态都要有"超时"出口(不能永久卡住)
2. 每个外部调用(ASR/LLM/TTS)都要有"失败分支"
3. 空结果、异常输入,进入下一状态前拦截
4. 状态转换原子化(要么完整转换,要么回滚)
5. 任何异常路径最终回到"安全状态"(LISTENING/IDLE),系统永不"死"
```

### 11.4 答异常题心法
```
结构: 是什么 → 不处理会怎样 → 怎么应对(明确动作)
招式库: 超时 / 兜底话术 / 拦截 / 重试 / 降级 / 追问 / 恢复
任何异常,从招式库选组合就是应对方案
```

## 第 12 章 形象工程(Avatar)

### 12.1 本质:挂在语音链路上的一层
```
纯语音: ...→ TTS出音频 → 播放声音
加形象: ...→ TTS出音频 ─┬─→ 播放声音(耳朵)
                        └─→ 驱动口型 → 渲染画面(眼睛)
形象是在TTS音频这个点"分叉"出的新链路。音频一份两用。
所以形象"可砍"——砍掉语音链路不受影响。
```

### 12.2 MuseTalk为什么能实时
```
准备阶段(对话前,一次性):拿静默人物视频(闭嘴)→人脸检测/解析/VAE编码→生成avatar
实时阶段(对话中):只跑UNet+VAE解码器(音频→嘴型)→30fps+
关键:形象不是凭空生成,是拿你准备好的人物视频实时改它的嘴
```

口型吃流式音频:TTS音频块→buffer→whisper-tiny编码成特征→UNet生成嘴型→VAE解码出帧。

### 12.3 硬约束与核心旋钮
```
硬约束:25fps(MuseTalk训练于此),整链路锁这个节奏
       两个判据:inferfps(GPU算口型速度)、finalfps(推流速度),都要≥25
核心旋钮:batch_size(默认4)
  大→GPU并行充分,吞吐高(并发好),单次延迟高
  小→单次快,GPU利用率低
  → 调延迟/帧率/并发都看它,直接接并发的批处理
```

### 12.4 为什么实时只能用 MuseTalk 类
```
口型同步类(MuseTalk/Wav2Lip): 快,实时,但只动嘴
扩散类(EMO/Vasa-1): 效果电影级,但生成几秒视频要几分钟,无法实时
→ 追实时,只能在口型同步类里选(物理限制)
```

### 12.5 Avatar技术版图(MuseTalk只是其一)
```
2D口型替换: MuseTalk(实时首选,真人感) / Wav2Lip(老,糊) / SadTalker(能动头但慢)
2.5D:       DH_live(极轻,移动端/小程序,口型质量略低)
卡通Live2D:  Live2D(不要真人感时,几乎不吃GPU,性价比之王)
3D:         LAM(3D高斯泼溅,客户端渲染,给服务端减负) / 传统3D(高定制)
端到端:      EMO/Vasa-1(惊艳但不实时,只离线)

选型逻辑:
  先问"要不要真人脸"——不要→Live2D(省到极致)
  要→PC真人MuseTalk / 移动DH_live / 3D+服务端减负LAM
```

### 12.6 渲染在哪做(关系减负)
```
服务端渲染(RTC Client): GPU渲染成视频推H.264 → GPU压力全在服务端
客户端渲染(LAM Client): 只算驱动参数,浏览器渲染 → 服务端轻
```

### 12.7 形象给打断和传输的额外影响
```
打断: 除停TTS、清音频,还要停MuseTalk产帧循环+清视频帧队列
传输: 加视频后WebSocket吃力(TCP丢包卡顿)→ 倾向WebRTC
     → 形象是"WebSocket vs WebRTC"决策的真正分水岭
```

## 第 13 章 并发与资源

### 13.1 核心认知:在线 ≠ 并发峰值
```
在线总数: 打开页面的总人数(餐厅一天来的顾客)
并发峰值: 某一瞬间真正占用GPU的人数(同时在店吃饭的人)

为什么峰值<<总数:
  对话是轮流的 → 任何瞬间大部分人在沉默(思考/等待/停顿)
  只有"在说话"(占ASR)和"在听"(占TTS/口型)的人才占GPU

配GPU看峰值,不看总数 → 把需求和成本砍掉一大半
  1000在线 ≠ 1000路GPU,可能只需200-300路峰值
  并发峰值 ≈ 在线总数 × 活跃率
```

### 13.2 易错:峰值是"相加"不是"取公共"
```
说话的人 ≠ 听的人 → 两批不同用户,不重叠 → 没有"公共部分",是"相加"
单服务峰值: 各服务各自看"最多多少人同时用它"(ASR看说话,TTS看听)
整体活跃: 各服务在用人数相加(150说+150听=300活跃)
正因各服务并发不同、用户不同 → 必须独立部署各自配资源
```

### 13.3 五个解法
```
① 模型拆分独立部署: ASR/TTS/口型各放不同卡,不互抢(防阻塞)
   → 更值钱:按瓶颈精确扩容,只给不够的(通常口型)加卡,不整套翻倍(省钱)
② 批处理(batching): GPU算1个和4个耗时差不多,攒齐一起算,吞吐翻几倍
③ 超时与资源回收: 僵尸连接占资源,空闲超时→断开释放,资源才能循环
④ 排队/限流/降级: 超载时有损服务而非全崩(口型25→15fps,或暂关形象)
⑤ 多机+负载均衡+Session管理: 突破单机连接上限,Session外置或会话粘性
```

### 13.4 一个重要结论:口型是并发最大杀手
```
口型(MuseTalk)最重,几乎总是瓶颈,扩容时总在给它加卡
→ "砍形象"或"用LAM客户端渲染"(口型甩给浏览器)能消掉最贵瓶颈
→ 并发能力成倍提升,省下最多的卡
→ 给"减负"一个量化理由:不只省GPU,直接决定能服务几个人
```

## 第 17 章 识别质量:热词 / 中英混合 / ITN

### 17.1 热词:零成本解决"识别效果差"的钥匙

原理:基于WFST(加权有限状态转换器),为特定词汇分配权重调整识别概率。
处理链路:声学模型→热词干预→语言模型→标点断句。

**典型痛点:** 通用识别把"心肌梗死"误识为"心急梗死"、"区块链"拆成"区块连"。配热词后专业术语准确率可提升到98%+。

**配置方法(可直接用):**
```
1. 创建UTF-8文件 hotwords.txt
2. 每行 "热词 权重":
     阿里巴巴 20
     心肌梗死 60
3. 启动挂: --hotword /path/to/hotwords.txt
   或 AutoModel.generate时传 hotword="魔搭, FunASR"
```

**约束(官方建议):** 热词长度≤10,个数≤1k,权重1~100。专业术语建议60-80。

**对你的意义:你最初"识别效果一般",很可能配个业务热词表就好一大半。这是几乎零成本、立竿见影的优化。**

### 17.2 中英混合:原生支持,有选型讲究

SenseVoice/Paraformer 本身支持中英混合("打开folder")。
```python
model = AutoModel(model="SenseVoiceSmall", vad_model="fsmn-vad", punc_model="ct-punc")
result = model.generate(input="mixed.wav", hotword="魔搭, FunASR")  # 热词也支持中英混合
```

选型提醒:英文占比高/多语种 → 可考虑 Qwen3-ASR(52语言)/GLM-ASR-Nano(17语言,方言优化);中英为主 → SenseVoice够用。

### 17.3 ITN:数字日期规范化

```
作用: "二零二六年"→"2026年","百分之五十"→"50%"
配置: --itn-dir 或 generate时 use_itn=True
注意: ITN可能帮倒忙(有时就想要中文数字),按场景测
影响: 不开ITN,识别出的"一千两百"传给LLM/TTS会别扭
```

### 17.4 一个新发现:说话人分离可部分替代pVAD

FunASR 2026/05支持流式WebSocket(VAD+说话人分离+热词)。
SenseVoice配 vad_model+spk_model+punc_model 可获得带说话人标签的逐句结果。
→ 说话人分离能区分不同说话人,和pVAD"认主人"思路相通
→ 可能是比自己集成pVAD更省事的路子,落地时评估

## 第 18 章 LLM 环:对话大脑 + 文本清洗

> 之前把LLM当黑盒,这章补上。LLM决定数字人"聪不聪明、像不像"。

### 18.1 对话历史管理(多轮记忆)
```
每轮把历史拼进输入:
  [system:人设] [user:第1句][assistant:回答1]...[user:当前句] → 生成
问题: 历史越积越长 → 超上下文窗口 + 变慢 + 变贵
解法: 每隔几轮生成摘要,用摘要代替久远历史(近的留原文,远的压摘要)
```

### 18.2 system prompt 定人设
```
[system] 你是亲切的客服,口语化,简洁不超两句,不用书面语,不用列表和符号...
对语音数字人的特殊要求:明确"输出适合朗读的口语",禁markdown/列表/长句
→ 这直接关系下面的文本清洗
```

### 18.3 最高频实战坑:LLM输出 → TTS输入的文本清洗(必踩)

**LLM吐出的文本直接喂TTS会出大问题:**
```
· Markdown: **加粗** `代码` ## → TTS会把"星号星号"读出来!
· 列表符号: 1. 2. - * → 读"一点 二点 减号"
· Emoji: 😊 → 不知怎么读,或读"笑脸"
· 特殊符号: () [] / @ # → 读成乱七八糟
· 代码块: ```...``` → 绝对不能读
· 数字单位: "100%" "3.14" → 读法要规范化
```

**所以"句子聚合"那一步实际要做两件事:**
```
LLM token流 → ① 切句(攒到标点)
           → ② 文本清洗(去markdown/符号/emoji,数字规范化)
           → 才能送TTS
```

**文本清洗标准处理:** 去markdown标记、去/转emoji、去无法朗读的符号(或转可读如"/"→"或")、数字单位可读化、处理括号注释。

**这是缺口里对你最实际的一条:漏了它,数字人会念"星号星号你好星号星号",非常出戏。**

### 18.4 多队列并行(印证流水线)
```
三队列接力: 句子队列(LLM) → TTS队列(音频) → 视频帧队列(口型)
各队列各自线程并行 → 第一句处理完就播,不等后面
为什么以句子为单位: TTS要上下文定语调停顿韵律,MuseTalk要一定音频长度做唇形同步
→ 这是"句子聚合不能切太碎"的实证
```

### 18.5 工具调用(Agent,简要)
```
数字人要查天气/数据库 → LLM带function calling
但工具调用增加延迟(等工具返回),实时场景要权衡
起步: 纯对话不带工具;需要再上
```

## 第 19 章 端到端延迟预算(优化的地图)

> 之前有"首包延迟公式",这章做一次完整的端到端拆解,优化时知道砍哪段。

### 19.1 完整延迟链(从用户说完到数字人开口)
```
用户说完最后一个字
  ↓ ① VAD端点判定(等静音确认)        典型 300-700ms ← 大头,可调静音阈值
  ↓ ② 整句ASR出final(SenseVoice)     典型 100-300ms
  ↓ ③ LLM首token                     典型 200-800ms ← 大头,看模型和是否流式
  ↓ ④ 句子聚合(攒到第一个标点)        典型 50-200ms
  ↓ ⑤ TTS首包(CosyVoice2)            典型 150-300ms
  ↓ ⑥ (有形象)首帧口型               典型 +100-300ms
  ↓ ⑦ 网络传输                       典型 50-150ms
  ↓ 数字人开口
纯语音总计 ≈ 1-2秒;含形象 ≈ 2-3秒(印证OpenAvatarChat标称2.2s)
```

### 19.2 优化优先级(砍大头)
```
最大的两块: ① VAD端点判定 和 ③ LLM首token
  · VAD: 调静音阈值(但太短会切断)/ 上轮次检测做更快的端点判断
  · LLM: 选更快的模型/确保流式/句子聚合第一个标点就送(别等长句)
其次: ⑤TTS首包(选首包快的CosyVoice2)、⑥形象(砍掉或客户端渲染)
网络: ②③④可流水线重叠,不是简单相加
```

### 19.3 关键认知:不是简单相加,是流水线重叠
```
因为流水线接力,③④⑤⑥在时间上部分重叠
  LLM还在生成后半句,前半句已在TTS合成
所以实际总延迟 < 各段简单相加
但①②是串行的(必须先识别完才能给LLM)→ 这两段是硬延迟,最该优化
```

```
误打断率: SPEAKING时误触发打断的比例(对标FireRedChat 10%)
首包延迟: 监控TTS首包、整体首响
形象: inferfps/finalfps 是否≥25
```

### 20.2 上线监控
```
· 每个环节(ASR/LLM/TTS/口型)的耗时埋点
· 异常率(空结果率、超时率、报错率)
· 并发数、GPU利用率、僵尸连接数
· 用户行为(打断频率、对话轮数、放弃率)
```

### 20.3 安全与合规(轻量但必须有)
```
· 用户违规输入 → 拦截或引导
· LLM不当输出 → 加审核/过滤层
· 录音隐私合规 → 告知、脱敏、留存policy
· 这些是上线的"门槛",不是优化项
```

# 附录 · 易错点速查

```
1. PCM: 实时不用压缩,核心原因是"延迟"(编解码+攒帧)
2. VAD: 输出是speech_start/end两个转折点,不是每块一个标签;只懂声学不懂语义
3. 2pass: 是SenseVoice单向覆盖partial,不是互相纠错
4. is_final: 说完要补一刀,否则partial吞尾字
5. 下行: 句子聚合用标点切(文本有现成标点),上行用VAD切(音频无标点)
6. 排期播放: 打断最易漏"取消已排期未播的块"
7. 打断: 能力在写下行时就预留(可取消异步task),不是事后能加
8. 打断慢3-5秒: 信号被音频流堵,要走优先级/独立通道
9. 状态机: 连接生命周期(会话级)≠状态生命周期(句子级)
10. WebSocket vs WebRTC: WS是WebRTC的信令媒人,不是容器;音频走WebRTC独立UDP
11. 传输选型: 纯语音WS够,加视频转WebRTC(根因是TCP丢包卡顿 vs UDP丢包跳过)
12. 误打断三层: 普通VAD只挡噪声,挡不了任何人声(数字人/旁人声都要AEC+pVAD)
13. pVAD: 只判"是不是主人"(声纹),不管长短/意图;可做兜底但不能被便宜手段替代
14. 速度vs误打断: 跷跷板,宁慢勿误;据FireRedChat论文,无目标说话人识别误打断率偏高(30%量级)
15. 并发: 算"峰值"不算"在线总数"(对话轮流,大部分人沉默)
16. 并发峰值: 各服务"相加"不是"取公共"(说话的≠听的,两批人)
17. 独立部署: 防阻塞 + 按瓶颈精确扩容(省钱)
18. 口型: 并发最大杀手,砍它或客户端渲染能成倍提并发
19. 形象: 是WebSocket→WebRTC决策的真正分水岭
20. 异常处理: 招式库=超时/兜底/拦截/重试/降级/追问/恢复
21. 热词: 识别专有名词出错,先配hotwords.txt(权重60-80),零成本立竿见影
22. ITN: 数字日期规范化,但可能帮倒忙(有时要中文数字),按场景测
23. LLM→TTS: 必须文本清洗(去markdown/emoji/符号),否则念"星号星号"出戏
24. 文本清洗: 放在句子聚合那一步(切句+清洗一起做),不是独立环节
25. 对话历史: 越积越长会爆上下文,远的压成摘要
26. 延迟大头: 通常是①VAD端点判定 和 ③LLM首token,优先砍这两段
27. 延迟非相加: 流水线重叠,总延迟<各段相加;但①②串行是硬延迟
28. 说话人分离: FunASR新功能,可能比自建pVAD更省事地实现"认主人"
```
