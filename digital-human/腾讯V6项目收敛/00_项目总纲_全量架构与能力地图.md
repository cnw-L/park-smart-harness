## 1.5 实际代码盘点（2026-06-22，重要修正）

> 关键事实：`harness` 的大脑**不是设计稿，是一套功能基本完成的真实代码**（`smart_park_assistant/src/`，约 7,500 行 Python）。
> **定位（作者澄清）**：这是**之前完整的旧代码**，功能基本做完，但**理念可能与最新收敛设计（`harness-park-design` 的定稿文档）不完全对齐**——代码写在前、设计收敛在后。
> 所以下面的覆盖度按「功能已实现」上调，但每一项都附带一个隐含前提：**需做一次「代码 ⇄ 最新设计」对齐审计**，确认旧代码的理念没跑偏（典型疑点见本节末）。
> 另：**业务域的后端叶子大多是桩**（各域注释明写 `v1 全桩，真后端是下一个 plan`）——即「中枢功能真、业务叶子桩」。

|---|---|---|---|
| `agent_loop/` | ~2,662 | 事务型 ReAct 引擎：迭代提交/中断回滚/挂起恢复、gate(ask/allow/deny)、control(冻结-确认-解析)、budget+grace、repair 序列修复、verify 接缝、stall/no_progress 看门狗、redis+pg 双 store、压缩 | 🟢 **真实引擎** |
| `agent_context/` | ~867 | 上下文五层组装：assembler/compactor/history/knowledge/memory/plan_view/principal/tokens | 🟢 真实 |
| `agent_tools/` | ~1,434 | 工具治理：catalog（带 group/risk/permission/output_budget 元数据，读控分叉注册期钉死）、grounding、gate、proposal/execute_proposal（控制两段）、4 超域 | 🟢 治理真实，**域叶子=桩** |
| `harness_rag/` | ~2,540 | Milvus 向量检索：两遍召回、rerank、query rewrite、small-to-big 父块回捞、**权限过滤(permission_tags/role_scope/department_scope) 已编码** | 🟢 **真实 RAG** |

**控制安全红线在代码里是真的**：`catalog.py` 把读/控分叉做成注册期不变量（`risk∈{control,ticket,execute} ⟺ tool.is_control`，不一致直接 `raise`）；`loop.py` 的 gate 对控制类一律 `freeze`→挂起→确认→解析，`execute` 永远 deny；`harness_rag` 的权限过滤字段在检索层强制注入（身份来自登录态，绝不模型自报）。**即「越权动作率→0」「数据隔离」不是承诺，是已编码的结构。**

**对收敛的修正**：
1. **覆盖度上调（带前提）**：②AI 引擎层、③能力层治理、4.6 AI 原生（RAG/工具治理/MCP 雏形）从「设计」升「功能已实现」——但前提是通过「代码 ⇄ 最新设计」对齐审计；理念若已跑偏，部分模块要按定稿改造而非直接复用。
2. **真正的空白更清楚**：(a) **域后端叶子是桩**——要接 `agent_runtime` 真后端 gateway；(b) **商业/导航两域无工具**；(c) **语音/形象外壳尚无代码**（`数字人研究` 仍是设计）；(d) **仓内无测试**（见下）。
3. **测试是第一空白**：代码已成型却**这 4 个 src 包里没有测试文件**（README 提的「16+ 测试绿」在仓的 `tests/` 不在这些 src 下）。代码越真，缺测试的风险越高——`01` 文档因此是最高优先。
4. **新增：理念对齐审计**——旧代码 ⇄ 定稿设计做一次逐模块核对，凡不齐处要么改代码、要么更新设计留痕（不能两份并存当真相）。

**理念对齐疑点 → 已审计（结论见 [`03_代码设计对齐审计`](03_代码设计对齐审计.md)）**：三个疑点全部解除——
- ✅ `plan.py` **无 DAG 残留**（spec 不含 depends_on，并串靠循环动态），已是 todo 列表。
- ✅ `loop.py` **事务化已落全**，且实现到定稿 §七「下一步」清单（空→重试/stall/awaiting_confirmation/预算 rehydrate 全有）。
- ✅ `assembler.py` 功能标签分层、丢弃/裁剪/context awareness 与上下文定稿一致。
- **结论**：理念审计通过，旧代码可放心作基线；真正待补 = 后端真化 + verify 规则 + 测试 + 商业/导航域（分期工程，非返工）。

## 4. 一个关键分歧必须留痕：plan vs 条件 DAG

腾讯 2.2.2 要求「基于 **DAG/工作流引擎** 支持子 Agent 串行/并行/条件分支编排」。
你的 harness 设计**明确不采纳条件 DAG**，改用 `plan = 带 status 的 todo 列表`（`总纲 §三`）：理由是 DAG 是静态冻结图，而真实 harness 靠 ReAct 的重试/重规划动态——并行=模型一轮多 tool_call、串行=ReAct 天然顺序、重试=循环动态，都不需要图。

**收敛动作**：这不是 bug，是经过论证的工程选择。但既然是给腾讯口径对齐，**必须在方案里写一段「编排范式说明」**：说明 todo 列表如何等价满足腾讯的「串行/并行/条件分支 + 编排成功率≥90% + 上下文传递≥98%」验收，否则评标时会被当成「未实现 DAG」。测试方案里也要用腾讯的编排测试集证明等价性（见 `01` 文档）。
