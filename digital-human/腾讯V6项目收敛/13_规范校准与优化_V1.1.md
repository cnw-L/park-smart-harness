# 规范校准与优化报告(V1.0 → V1.1)

> 用途:用 2026 最新行业资料逐条校准两份 V1.0 规范(《测试与评测规范》《可观测性设计规范》),给「确认 / 修正 / 补充 + 建议改法 + 引用」。两份 V1.0 方向稳健,本报告是把"参考/宜自核"的点钉实 + 补 2026 新进展。
> 方法:2 路并行行业研究 + 交叉核实。日期 2026-06-24。

---

## 0. 必改清单(优先级最高,先动这几条)

1. **【测评】≥500 样本量** → 不是硬门槛,改为"按目标效应量 + 95% CI 反推,500 仅为分辨 ~7pp 差异的下限,并报告 95% CI"。**这是最大风险点**(把统计后果当成了固定门槛)。
2. **【可观测】平台开销 12–15%** → 软化为"与埋点深度强相关,深度 step-level 埋点典型 ~15%,异步/批量导出可显著降",**别当普适常数**(单一基准)。
3. **【可观测】缺 trace 存储后端** → 栈里补 **Grafana Tempo**(metrics 大规模可上 Mimir);并评估 **SigNoz/ClickStack** 降运维。
4. **【测评】judge 校准** → 把"5–10% 人审"绑定 **Cohen's kappa 阈值(地板 0.6)+ 定期重校**。
5. **【可观测】OTel GenAI 约定** → 写明:**已拆独立仓库** `open-telemetry/semantic-conventions-genai`(CI 引用指新仓)+ v1.37 起消息记录重构 + opt-in 用法。

## A. 《测试与评测规范》校准(8 条)

| # | 原主张 | 校准结论 | 建议改法 / 补充 |
|---|---|---|---|
| 1 | 可信样本量 **≥500** | **修正** | 500 是"分辨 ~7pp 差异、95%置信80%power"的统计后果,非硬口径:4pp≈1580/组、2pp≈6300。**<几百条不应用 CLT 构造 CI**(LLM eval 样本相关、非独立,arXiv 2503.01747)。改写为"按目标效应量+95% CI 反推 + 报告 ±1.96·SE" [来源](https://arxiv.org/pdf/2503.01747) |
| 2 | **proxy state-based eval** | **确认(单一前沿)** | arXiv 2602.16246 真实:LLM 从 trace 推断后端终态、judge 对照规格判完成;人-LLM 一致 >90%、默认配置幻觉近零。**标注前沿、需自验**;仅用于业务结果,安全红线仍走确定性 engine 套 [来源](https://arxiv.org/abs/2602.16246) |
| 3 | **GEPA 优于 MIPROv2** | **确认(强证据,ICLR 2026 Oral)** | 聚合 **+13% vs MIPROv2 +5.6%**(两倍多),少用 35x rollouts;`pip install gepa` / `dspy.GEPA` 本地可跑、读失败 trace 反思优化。可放心写入"自动优化首选" [来源](https://arxiv.org/abs/2507.19457) |
| 4 | 在线采样 **100% 启发式 + 5–15% judge** | **确认** | 落在行业区间(5–20%)偏保守端,合理。**补:错误/异常 trace 应 100% 送 judge**(非仅采样);judge 成本控在生产 LLM 成本 10–15% 内 [来源](https://futureagi.com/blog/llm-as-judge-best-practices-2026) |
| 5 | judge 校准 **5–10% 人审** | **确认 + 补阈值** | 绑 **Cohen's kappa**:>0.8 强 / >0.6 可接受 / <0.4 rubric 有歧义需重写;抽 100–300 条、2–3 标注者建 gold-set;**月度跑、kappa 降即告警、季度刷 gold-set** [来源](https://futureagi.com/blog/llm-as-judge-best-practices-2026) |
| 6 | 轨迹 **superset/unordered + state-based**(弃 strict) | **确认(2026 仍共识)** | agentevals 已标准化 4 模式。**补:τ²-bench 出了 Verified 修正版**(原任务/评判与策略不一致);proxy-state 是 state-based 最新延伸 [来源](https://github.com/amazon-agi/tau2-bench-verified) |
| 7 | 工具链 DeepEval/agentevals/RAGAS 等 | **确认 + 补** | promptfoo MIT/local-first(红队强);DeepEval Apache 2.0;RAGAS Apache 2.0 纯开源;**agentevals 显式纳入**;**ARES 缺 2026 更新→标"信息不足、核实后再纳入"**。三大工具均开源 + 本地判官 [来源](https://genai.qa/blog/promptfoo-vs-deepeval-vs-ragas/) |
| 8 | 学术对照物 | **补 2026 新基准** | 补 **TAU3-Bench**(长程多轮+模拟用户)、**Terminal-Bench**(89 任务、出口码/文件 diff 确定性评分)、**GAIA**(真实多步助手)、**τ²-bench-Verified**、**proxy-state(2602.16246)**。**提醒:不同 benchmark 测不同维度,别合并成单一排名** [来源](https://benchlm.ai/benchmarks/tau3Bench) |

## B. 《可观测性设计规范》校准(9 条)

| # | 原主张 | 校准结论 | 建议改法 / 补充 |
|---|---|---|---|
| 1 | OTel GenAI 约定未冻结 | **修正/补** | 仍 experimental;**但已拆到独立仓库** `open-telemetry/semantic-conventions-genai`(主仓 `model/gen-ai`/`openai`/`mcp` 废弃,**CI 引用指新仓**);**v1.37 起消息记录重构**(`gen_ai.input.messages`/`output.messages`/`system_instructions` 属性 或 `gen_ai.client.inference.operation.details` event);opt-in 设 `gen_ai_latest_experimental`;semconv 已 v1.42.x [来源](https://github.com/open-telemetry/semantic-conventions/releases/tag/v1.37.0) |
| 2 | 平台开销 **12–15%** | **软化(单一来源)** | 仅 1 个多 agent 基准 Langfuse ~15%,**场景依赖**(step-level 深埋更高、异步/批量导出可降)。改"与埋点深度强相关,深度典型 ~15%,异步批量导出可显著降",不当常数 [来源](https://laminar.sh/article/2026-04-23-top-6-agent-observability-platforms) |
| 3 | OpenInference / OpenLLMetry | **确认 + 补选型** | 均 Apache 2.0。OpenInference(Arize/Phoenix 默认)是 `gen_ai.*` 的 **superset、非一一对应**;**OpenLLMetry(Traceloop)原生 emit `gen_ai.*`、明确含 vLLM → 对你的栈(vLLM+需 gen_ai.*)更贴合**。注:vLLM 是 OpenAI 兼容端点,靠 OpenAI client 自动埋点拦截 [来源](https://futureagi.com/blog/openinference-vs-openllmetry-vs-openlit-2026/) |
| 4 | Collector agent→gateway + tail-sampling(loadbalancing 按 trace_id) | **确认(de facto 标准)** | 官方背书。**重要补:用 `spanmetrics` connector 派生 RED 指标,必须在采样前从 100% 流量派生**(forward connector 分两步),否则指标只反映被采样子集 [来源](https://opentelemetry.io/docs/collector/deployment/gateway/) |
| 5 | SLO + burn-rate 告警 | **确认(Google SRE 标准)** | 补 multi-window multi-burn-rate 三档(30 天预算):**1h@14.4×→页面**、**6h@6×→页面/工单**、**3d@1×→工单** [来源](https://sre.google/workbook/alerting-on-slos/) |
| 6 | 三支柱栈 OTel+Collector+Langfuse+Prom+Grafana+Loki | **确认 + 重要补** | (a) **缺 trace 存储后端 → 补 Grafana Tempo**(大规模 metrics 上 Mimir);(b) 2026 统一替代 **SigNoz / ClickStack**(单 ClickHouse + SQL,免三套查询语言 PromQL/LogQL/TraceQL);**几十人自托管可评估降运维**(LGTM 占平台工程 20–30% 时间)[来源](https://signoz.io/blog/grafana-alternatives/) |
| 7 | TTFT/TPOT/Goodput + DCGM | **确认定义 / 修正阈值** | 定义清晰(TTFT=到首 token;TPOT=(端到端−TTFT)/(out−1);Goodput=满足 SLO 的吞吐)。**无通用标准阈值→按业务 SLO**;**vLLM 默认 SLA TTFT 3000ms/TPOT 100ms 作基线**;DCGM exporter 是 GPU 监控事实标准 [来源](https://bentoml.com/llm/inference-optimization/llm-inference-metrics) |
| 8 | PII 脱敏放 Collector processor | **确认 + 修正分层** | Collector 是推荐位但**第二道防线**;官方最佳实践"**尽早过滤、理想在 instrumentation 层**";脱敏须在 routing/export 前;processor 选 **redaction / transform(OTTL)/ attributes**;**等保双管齐下**(源头不记敏感 + Collector 脱敏)[来源](https://opentelemetry.io/docs/security/handling-sensitive-data/) |
| 9 | 2026 新内容 | **补** | (a) GenAI semconv 独立仓库;(b) **MCP tracing 已纳入 semconv**(`openinference-instrumentation-mcp` 自动 client↔server context 传播→span 归同一 trace,你 harness 若用 MCP 工具应埋);(c) **OTel Weaver**(从 semconv 生成/校验代码,保 attribute 一致);(d) 坑:**~85% GenAI 部署裸跑无可观测**→规范应强制"埋点先行" [来源](https://opentelemetry.io/blog/2025/ai-agent-observability/) |

## C. 诚实标注(改前先看强弱)

- **强共识(可放心写死)**:GEPA>MIPROv2(顶会 Oral)、judge 校准绑 kappa、轨迹用 superset/state-based、Collector tail-sampling 两层 + spanmetrics 采样前派生、SLO multi-burn-rate 三档、PII 尽早过滤、OTel GenAI 拆独立仓库。
- **单一来源/前沿(标注、需自验)**:proxy state-based eval(2602.16246)、平台开销具体数字、SigNoz/ClickStack 降运维比例、~85% 裸跑。
- **定义强但阈值非通用(按本项目 SLO 定)**:TTFT/TPOT 阈值(vLLM 默认 3000/100ms 仅基线)、样本量(按效应量反推)。

## D. 落地动作(把校准并回两份规范)

1. **测评规范**:§8 样本量改"效应量+CI 反推";§5/§10 judge 校准绑 kappa≥0.6 + 错误 trace 100% judge;§11 补 τ²-Verified;附录补 TAU3/Terminal-Bench/GAIA;§7 ARES 标"待核"。
