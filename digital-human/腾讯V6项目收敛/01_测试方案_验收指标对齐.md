## 0. 测试分层与总原则

```
L0 单元/契约测试  ── 每模块 + MCP 工具输出契约（harness 注册表 output_hint）
L1 子系统测试     ── 上行ASR / 下行TTS / 打断 / 内圈循环 / 上下文 各自达标
L2 集成/端到端    ── 跨 Agent 联动（停车→导航→食堂）+ 语音外壳↔大脑接缝
L3 非功能         ── 并发压测 / 安全攻击 / 降级逐一关闭 / 可用性
L4 验收（UAT）    ── 甲方测试集 + 试运营 2 周统计
```

> **代码现状对测试优先级的影响（2026-06-22）**：大脑已是真实代码（`agent_loop`/`agent_context`/`agent_tools`/`harness_rag`，约 7,500 行），但**这 4 个 src 包里没有测试文件**，且业务域后端叶子大多是桩。这决定了测试要分两批打：
> - **【先打·引擎层】** 对已成型的真实代码补单元/子系统测试——尤其 `loop.py` 的状态机（挂起恢复/中断回滚/看门狗/熔断）、`gate` 读控分叉、`control` 两段、`harness_rag` 权限过滤与两遍召回。这些**现在就能测**（用 Fake 后端/桩），不依赖甲方。
> - **【后打·集成层】** 业务指标（食堂延迟/停车同步/导航精度等）依赖真后端 gateway 接入，桩态测不了真数；先建测试框架占位，后端接通即填数。
>
> **三条总原则**：
1. **评测先行**（承袭 harness `实施计划` Phase 1 = 评测基线先于功能）：每个能力上线前先有它的测试集和通过线。
2. **指标可复算**：每条指标记录 测试集规模 / P 值口径(P80/P95/P99) / 原始数据留存，避免「自评虚高」（README 已警惕 Ten 78%/FireRedChat 10% 误打断数据来自论文自评）。
3. **红线优先**：`错误/越权动作率→0` 是事务系统红线，任何一次越权执行即判失败，优先级高于所有体验指标。

## 0.6 测试方法论（2026 行业对齐，已查证）

测 LLM agent 不能套传统确定性测试，业界共识是分层 + 拆套：

1. **拆两套**：确定性引擎逻辑（工具路由/参数解析/状态机/闸/降级）用**传统单测 + mock LLM**，每次提交跑；模型行为质量用**真模型评测**，多次取平均、nightly 跑、阈值门卡部署。用 Pytest markers 分开。
2. **三层评测**：最终结果（黑盒）/ 轨迹（玻璃盒，比对工具调用序列）/ 单步（白盒，像推理单测）。
3. **state-based 评测（优先用于控制类）**：不判文字/轨迹，**比对动作前后的后端状态**——确定、无评分波动、可精确给分（含安全扣分）。你的"下发→读回→对账"天生是 state-based 落点。
4. **吸收波动**：真模型评测跑 3+ 次取平均。
5. **落地**：见现成可跑目录 `编排测试集/`（cases.yaml 已按 engine/model 两套分、控制类用 expect_state）。

> 来源：[SitePoint](https://www.sitepoint.com/testing-ai-agents-deterministic-evaluation-in-a-non-deterministic-world/) · [MLOps Community](https://home.mlops.community/public/blogs/effective-practices-for-mocking-llm-responses-during-the-software-development-lifecycle) · [Confident AI](https://www.confident-ai.com/blog/llm-agent-evaluation-complete-guide) · [LangChain](https://www.langchain.com/resources/llm-evaluation-framework)

## 3. 打断 / 误打断（双工核心，2.2.2 多轮 + 体验）

腾讯没给打断的独立数值指标，但它是「对话联动≤500ms」「降级≤3s」「多轮体验」的隐含支撑。**自定测试集**：

| 测试项 | 自定通过线 | 测试集构造 | 方法 |
|---|---|---|---|
| 正常打断响应 | 用户开口→停播 ≤300ms | ≥50 组「播报中插话」 | 打点：开口检测→tts.cancelled→前端停播 |
| 打断后新轮 | 新 asr.final→新 run 正确创建 | 同上 | 核对 run_id/previous_run_id 链 |
| **误打断率** | 自定 ≤10%（对标 FireRedChat，谨慎采信） | ≥100 组含附和词（"嗯""对""哦"）、背景人声、咳嗽 | 语义路线判定：不该打断的没打断 |
| 思考期打断 | 工具/RAG 阻塞步可 cancel | ≥30 组「查到一半改主意」 | 验证埋了 await/检查点 |
| 设备确认期打断 | 走 operation_ticket.cancel 不误执行 | ≥20 组确认态说"取消" | **接红线测试（§5）** |

**关联资产**：误打断走语义路线（落地方案，不上 pVAD 声纹）——测试要专门验证开放园区多人场景下语义路线是否够；若误打断率超线，触发「是否补 pVAD」的决策。

## 5. 控制安全红线（harness 最强项，必须有测试背书）

> 这是事务系统的**红线**，优先级最高：`错误动作率→0`、`越权动作率→0`。腾讯对应「市民越权访问员工内容=0」「敏感信息泄露=0」+ 设备控制不可逆。

| 测试项 | 通过线 | 测试集构造 | 方法 |
|---|---|---|---|
| 越权数据访问 | =0 | 市民身份尝试访问员工食堂/停车/活动 ≥100 例 | 验证不进候选集 + 后端数据过滤双层 |
| 越权设备控制 | =0 | 无权限身份尝试控制设备 ≥50 例 | 验证 deny（不进候选集） |
| 不可逆控制必确认 | 100% | 所有 control_ticket 类动作 | 验证 execute 永远 deny、必走 prepare→确认 |
| 下发-读回-对账 | 100% 对账 | 设备控制 ≥50 例 | deviceCtrl→getDevicePage 读回比对字典 |
| 确认期幂等 | 重放不重发 | 确认后重复触发 ≥20 例 | 验证幂等键（工单 id），不重复执行 |
| 错听控制兜底 | 误执行=0 | ASR 脏输入下的控制指令 ≥50 例 | grounding 消歧 + 确认闸兜底（不预清洗 ASR） |

**硬依赖**（必须在测试报告里标红）：后端 `deviceCtrl` 加 `commandId`+幂等前，不可逆控制不能上线（harness `内圈循环-收敛定稿` 已锁定）。**这是测试前置条件，不是测试项。**

## 6. 子 Agent / 业务指标（附录 A 食堂/通行/商业/导航/报事/活动/综合）

业务域指标多为「数据延迟/准确率/成功率」，依赖甲方系统对接，**列入 L2 集成测试**，本期先建测试框架，对接就绪后填数。重点几条：

| 域 | 关键指标 | 备注 |
|---|---|---|
| 食堂 | 拥堵延迟≤15s / 预测误差≤3min(P80) / 推荐命中≥70% | 依赖传感器对接 |
| 通行 | 接驳GPS≤10s / 到站预测≤2min(P80) / 停车同步≤5s | 依赖 GPS+停车 API |
| 导航 | 室外≤3m / 室内≤5m / 楼层识别≥95% / 路线≤3s / **无障碍 POI 100%（一票否决）** | 依赖腾讯地图 SDK |
