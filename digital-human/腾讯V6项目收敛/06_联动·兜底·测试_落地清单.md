## 一、联动（跨工具编排）

### 1.1 你的编排模型（一句话讲法）

> 主会话用 plan 调度 5 类工具；**串行/并行/条件**都不是静态图，而是 ReAct 循环动态跑出来的：
> - **并行** = 模型一轮发多个 function call，引擎 `asyncio.gather` 并发执行只读工具（保序）；
> - **串行** = plan 分步，按 todo 顺序推进；
> - **条件** = 上一步结果回灌上下文，模型下一轮据此决定走哪步。
> - **上下文传递** = 子 agent 回结构化结果给主会话、主会话重组（即开即退、结构化、不丢不重）。

### 1.2 你最强的联动链（讲这条，别讲停车导航）

```
设备管理(查状态/候选消歧)
  → 执行工具(propose_control 冻结 → 用户确认 → deviceCtrl 下发)
    → 运行管理(getDevicePage 读回 → 对账目标值)
```
这是有护城河的联动：读/控分叉 + 确认闸 + 读回对账，全链路在一个会话里。

### 1.3 缺口（要补才能讲查询型联动）

- **导航不在你 5 类工具里**。若要"停车（生活服务）→ 导航 → 食堂（生活服务）"这种经典查询联动，需新增导航工具（自建或接腾讯地图 MCP）。**在补之前，对外用 1.2 的控制链当联动样板。**

## 二、兜底（失败处理）—— 4 件可落地的事

### 2.1 失败可见性：is_error 回灌（已有，点明即可）

工具失败 → 结果消息标 `is_error=True` → 进上下文 → 模型下一轮看到 → **自然重规划**。
你的引擎已有：`outcome.disposition=="failed"` 计 failures；verify `business_ok=False` → `[verify-failed]` 前缀 + is_error。**不需要单独的失败处理器。**

### 2.2 要补：工具调用硬超时（对齐"≤3s 降级"）

现状：只有模型调用有重试，**工具调用没有硬超时**。在工具执行处包一层：

```python
# 工具执行包超时（落在 executor.execute_one 或其外层包装）
import asyncio
async def call_with_timeout(coro, timeout_s: float, tool_name: str):
    try:
        return await asyncio.wait_for(coro, timeout=timeout_s)   # 默认 3s
    except asyncio.TimeoutError:
        return ToolResult(ok=False, error=f"[timeout>{timeout_s}s] {tool_name}")  # → is_error 回灌 + 触发降级
```
- 只读类超时 → 当失败回灌，模型重规划或走降级。
- 控制类**不静默超时**：超时必须明确告知"未确认是否生效"，走读回对账复核。

### 2.3 要补：每个工具的降级路径（fallback_policy）

`ToolSpec` 现在有 `group/risk/permission/output_budget/over_budget`，**还没有 `fallback_policy`**。补一个字段，注册期校验"控制类必须有降级文案"：

```python
@dataclass(frozen=True)
class ToolSpec:
    ...
    fallback_policy: FallbackPolicy | None = None   # 新增

@dataclass(frozen=True)
class FallbackPolicy:
    mode: str          # "retry_once" | "skip" | "degrade"
    degrade_to: str    # 降级去向，如 "静态食堂大屏数据" / "原停车App跳转"
    user_mst: str      # 给用户的文案：降级了什么 + 还能用什么
```
**纪律：未填 fallback_policy 的工具不许注册上线**（在 `catalog.register` 里 assert）。

降级三档：瞬时抖动 → `retry_once`（只读/幂等才重试）；非关键步 → `skip`（模型据 is_error 自跳）；能力不可用 → `degrade`（走 degrade_to + 报 user_msg）。

### 2.4 用户可见 + 红线

- plan 显化给用户：失败步标出 + 一句降级文案（"实时排队暂不可用，已切到食堂大屏数据"）。
- **红线**：执行工具（控制类）失败**绝不静默**；不可逆操作未确认成功就如实告知，不假装完成。

## 三、测试（编排/多步链路）—— 轨迹评测

### 3.0 先拆两套（行业标准，别混着测）

- **engine 套**：用**可控假模型**（按用例预设吐 function_call）测引擎确定性逻辑（闸/降级/控制时序/状态）→ 每次提交跑、应 100% 绿。
- **model 套**：用**真 qwen** 测工具选择/编排质量 → 多次取平均、nightly 跑、统计性通过线。
- 混在一起测，"引擎对不对"和"模型准不准"两个都测不准。

### 3.0.1 控制类优先用 state-based（基于状态）评测

不看文字、不看轨迹,**断言后端最终真实状态**(空调最终=24度、读回 verified)。确定、无评分波动——你的"下发→读回→对账"就是状态读回,天生适合。轨迹/结果评测作辅助。

### 3.1 编排测试集（先建这个，已写好可拷 → `编排测试集/`）

建 `tests/eval/`，每组一个 case：

```yaml
# case_control_chain_01.yaml
input: "把 3 号楼会议室空调调到 24 度"
principal: { role: 员工, permissions: [device:read, device:control] }
expect_tool_sequence:                 # 期望工具调用序列（顺序可含并发组）
  - 设备管理.device_status            # 查 + 消歧
  - 执行工具.propose_control          # 产提案
  - 执行工具.execute_proposal         # 确认后下发
  - 运行管理.device_readback          # 读回对账
expect_context_pass:                  # 期望透传的关键字段（上游→下游）
  - { from: device_status.device_id, to: propose_control.device_id }
  - { from: propose_control.target_value, to: execute_proposal.value }
expect_result: { applied: true, verified: true }
```

### 3.2 跑链路 + trace 断言

```python
async def run_case(case):
    trace = []                         # 每步: {tool, args, result, is_error}
    result = await run_loop(... hooks=record_into(trace) ...)   # 用 FakeBackendClient
    return trace, result
```

### 3.3 两个指标怎么算（可纯程序化）

```python
# 编排成功率 = 全链路跑通且结果正确 / 总用例
orch_success = sum(result_matches(t.result, c.expect_result) for c in cases) / len(cases)

# 上下文传递完整率 = 命中的字段透传 / 应透传字段总数（逐 span 比对，不用模型判）
def ctx_pass_rate(trace, expect_pass):
    hit = sum(1 for p in expect_pass if field_in_downstream_args(trace, p))
    return hit / len(expect_pass)
```
- 目标：编排成功率 ≥90%、上下文传递完整率 ≥98%。
- **规则为主**（序列对不对、字段透传——代码断言）+ **LLM-as-judge 仅辅**（判最终回答是否满足意图）。

### 3.4 必测的另两类

- **越权红线**：市民 principal 调员工工具 → 断言 `CatalogGate` 返回 deny、动作执行数 = 0。
- **降级路径**：逐一把工具关掉（或注入 timeout）→ 断言降级生效 + user_msg 出现。

### 3.5 为什么现在就能做

全部用 `FakeBackendClient` → 确定性、不依赖真后端、可进 CI 防回归。**这是你代码已具备、却还没写的最高 ROI 测试。**
