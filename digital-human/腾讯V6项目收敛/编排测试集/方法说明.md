# 假模型测试 · 完整方法说明

> 本文讲清楚 `test_engine.py` 背后的完整方法:理念 → 逻辑路径 → 真实机制 → 一条铁律 → 与真模型测试的关系 → 行业背书。
> 配套代码:`test_engine.py`(已实测 8/8 绿)· `cases.yaml`(场景库)。
> 日期 2026-06-23。

---

## 一、理念(为什么这么做)

1. **agent 系统 = 代码(harness/引擎)+ 模型(qwen),必须分开评。** 行业原话:"harness 决定了什么是可能的,你评的是系统、不只是模型。"
2. **代码是确定的,模型是不确定的。** 同样输入,代码永远同样输出;qwen 不是。要把不确定隔离出来,先把确定的焊死。
3. **没有基线就无法归因。** 不先证"系统能正确走完这条流程",模型一失败,你分不清是代码/设计的锅还是 qwen 的锅。
4. **先立一条"可信基线"。** 用假模型(把模型每步决定写死)证明"代码能正确走完、且这条流程可达",这条被验证过的轨迹就成为 **gold trajectory(黄金/参考轨迹)= 基线**。
5. **之后只考一件事:设计好的 qwen 能不能自己复现这条基线。** 不一致 → 锅只可能在 qwen/设计 → 调 prompt/工具描述/grounding,**不动代码**。
6. **安全红线(越权/控制/超时/失败)不靠模型自觉**,靠确定性手段(假模型 + 故障注入)**强制造出来**验引擎兜底。

---

## 二、逻辑路径(一条线走下来)

```
0. 定义场景   每条:用户输入 → 期望工具序列(模型每步该调什么)→ 期望最终状态
        │
1. 假模型阶段(engine 套,确定性)
   把"期望工具序列"写成剧本喂假模型 → 跑真引擎(真工具/Fake后端/内存store)
   验两件:① 代码能正确执行这条流程(可达性)
           ② 闸/确认/降级/状态机走对(引擎规矩)
   全绿 = 代码焊死 +【这条轨迹被认证为可信基线】
        │
2. 固化基线   验证过的轨迹 = gold trajectory + 期望最终状态(state-based)
        │
3. 真模型阶段(model 套,统计)
   同一批场景,真 qwen 跑 → 拿实际轨迹比对基线:
     · trajectory match(用 in_order:主干顺序对、允许多走一步)
     · 最终状态 state-based(后端真状态对不对)
     · 任务完成 LLM-as-judge(办成没,判官用本地 qwen)
   一致 = 符合设计预期
        │
4. 归因与迭代   不一致 → 代码已焊死,锅在 qwen/设计
   → 调 prompt / 工具描述 / 超域组织 / grounding(非代码)→ 回 3 再跑
        │
5. 安全/异常分支(只在 engine 套)
   越权/超时/失败 用假模型 + 故障注入强制触发 → 验引擎拦截/降级
   (不指望真 qwen 去复现异常)
        │
6. 上线后   生产 trace + 在线 eval + 漂移告警 + badcase 回流
   → 回流补进场景库 → 回到 0,闭环
```

## 三、真实机制(剧本怎么给假模型、引擎怎么靠它编排)

### 3.1 剧本 = 一个 `list[ModelTurn]`

模型本质 = 逐轮输出"意图/决定"。一条 `ModelTurn` 就是模型这一轮的输出:要么调工具,要么给文本答案。剧本就是把每轮的输出按顺序排成列表:

```python
script = [
    ModelTurn(content="", tool_calls=[ToolCallReq(id="c1", name="device_status",
                                                  arguments={"target": "3F会议室空调"})]),  # 第1轮决定
    ModelTurn(content="", tool_calls=[ToolCallReq(id="c2", name="propose_control",
                                                  arguments={"device_id": "AC-3F", "value": 24})]),  # 第2轮
    ModelTurn(content="", tool_calls=[ToolCallReq(id="c3", name="execute_proposal",
                                                  arguments={"handle": "..."})]),  # 第3轮
    ModelTurn(content="已调到24度", tool_calls=[]),  # 第4轮:文本收尾,无工具 → 引擎判完成
]
```

### 3.2 把剧本给假模型 = 构造 `FakeModelCaller(script)`

```python
fake = FakeModelCaller(script)   # 内部:self._turns=script; self._i=0(游标)
```
它内部就两样:**剧本 + 游标**。每被调一次,吐 `self._turns[i]`,然后 `i += 1`。**一个"被问到就按顺序念下一句"的复读机。**

### 3.3 把假模型交给引擎 = `run_loop(..., model_caller=fake)`

引擎不关心它是真 qwen 还是假模型——因为 `ModelCaller` 是个**协议**(鸭子类型):只要"能被 `await model_caller(config, messages, schemas)` 调、返回一个 `ModelTurn`"即可。真 qwen 调用器和 `FakeModelCaller` 都满足 → **可无缝替换。这是整套成立的接缝。**

### 3.4 引擎编排 = while 循环,每迭代调一次模型、吃一句剧本

```
while True:
   ① 组装上下文:当前 messages → prompt
   ② turn = await model_caller(config, prompt, schemas)   ← 假模型吐剧本第 i 句
   ③ 看 turn.tool_calls:
        有 → 逐个 gate.classify(call) → allow:执行工具 / ask:冻结挂起 / deny:拦截
             → 每个结果 append 进 messages
        无 + 有 content → 判 completed,return
   ④ commit 这一轮 → 回 while 顶
```
**关键:剧本第 N 句 ⟺ 引擎第 N 轮迭代的"模型回答"。** 引擎每迭代问一次,假模型答一句(游标 +1)。**编排由引擎做,假模型只提供"这一轮模型会说什么";引擎根据这句的内容决定怎么走。**

### 3.5 逐迭代 trace(把空调调 24 度)

| 迭代 | ①组装 | ②吐剧本 | ③引擎编排 |
|---|---|---|---|
| 1 | [user] | device_status | gate=allow(只读)→ 执行(真工具/Fake后端,拿设备数据)→ 结果 append |
| 2 | +设备数据 | propose_control | 执行 → 子 agent 产提案、存 handle → append |
| 3 | +提案 | execute_proposal | gate=ask(is_control)→ **freeze、不执行** → 挂起,return awaiting |
| — | 用户确认后第二次 `run_loop(resolution=approve)` | (不问模型)| control.resolve → **真执行一次** → 继续 |
| 4 | +执行结果 | 文本 | 无 tool_call + 有正文 → **completed**,return |

### 3.6 断言 = 读引擎返回 + 控制桩计数

```python
res = await run_loop(... model_caller=fake ...)
assert res.status == "completed"
assert control.execute_count == 1     # 控制恰好一次(读 FakeControlCapability 计数)
```

## 四、一条铁律:只喂"决定",不喂"结果"

剧本里放的是**模型的决定**(调哪个工具/给答案),**不是工具的结果**。结果是**引擎拿你的决定去跑真工具(或 Fake 后端)产生的**。

```
剧本(你写) : "调 device_status(target=3F空调)"          ← 模型的决定
引擎(它做) : 真去调 → 后端返回 {device_id:AC-3F, 温度:28}  ← 结果,不是你写的
剧本(你写) : "调 propose_control(device_id=AC-3F,value=24)" ← 下一步决定
```

**为什么**:若把结果也写死喂进去,就成了自说自话——引擎什么都没干,等于没测。**只喂决定、让引擎自己跑出结果**,测的才是真东西:引擎接不接得住这串决定、路由/过闸/执行对不对、把结果穿回去对不对、最后按设计收没收住任务。

> 一句话:**模型=出决定的机器,假模型=把决定写死的复读机,引擎=接住决定去干活的人。测的永远是"接住决定去干活"这部分,即代码。**

## 五、与真模型测试的关系(一库两用,共享同一条基线)

| | 假模型套(engine) | 真模型套(model) |
|---|---|---|
| 模型行为 | **你写死(剧本)** | **qwen 自己产**,是被测对象 |
| 期望工具序列的角色 | **剧本来源**(照着喂) | **gold 对照**(拿 qwen 结果去比) |
| 测什么 | 模型这么做了,**引擎反应对不对**(+ 证流程可达) | **qwen 自己做得对不对** |

- **同一条标准流程被两套共享**:假模型套**证**它"代码可执行、正确"→ 它有资格当 gold;真模型套拿**同一条**当 gold,看 qwen 复不复现。两者 gold **必须是同一条**。
- 越权/超时类**只放 engine 套**(真 qwen 没法稳定触发异常);选工具判断类**只放 model 套**(写死就绕过了要测的 qwen);主流程类**两套都跑**。

## 六、行业背书与术语(都查证过)

- **gold / reference trajectory**:期望动作序列;有它后判"每步选对工具没"是二元确定的比对(LangChain/agentevals、Google Vertex、Strands)。
- **hard-code 参考轨迹**:对良好定义的工作流,直接写死一条参考轨迹逐步比对——正是"确立标准流程"。
- **mock LLM 确定化**:为可复现,mock 掉 LLM,让集成测试确认 agent 调对工具、参数对——正是"假模型先消除代码问题"。
- **"harness 决定什么是可能的,评的是系统、不只是模型"**——正是"先证系统可达,再单独考模型"。
- **trajectory match 两档**:`exact_match`(同工具同序)/ `in_order_match`(含参考工具同序、可有多余)。model 套对照建议用 in_order。
- **state-based 评测**:比对后端动作前后状态,确定无波动,控制类优先。
- **LLM-as-judge**:主观项(任务完成/回答质量)用,判官跑本地。
